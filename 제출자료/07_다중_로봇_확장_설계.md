# 다중 로봇 확장 설계

**프로젝트명** 컨베이어 기반 재활용 분류 협동로봇
**작성일** 2026-09-10
**문서 버전** 2.0

---

## 1. 문서 개요

### 1-1. 목적

본 문서는 현재 단일 로봇 구성을 다중 로봇으로 확장할 때
필요한 변경사항과 한계를 정리한다.

### 1-2. 문서의 성격

**"확장 가능하다"를 주장하는 문서가 아니다.**

**"확장하려면 무엇이 필요하고 한계가 어디인지 안다"를 기술한다.**

**실제로 여러 대를 연결해 운용한 경험은 없다.** 아래 내용은
현재 구조를 코드로 확인해 도출한 것이다.

---

## 2. 현재 구성

### 2-1. 물리 구성

```
제어 PC 1대   Intel Core i7-13620H (16스레드), 31GiB, RTX 4060 8GB
  고정 카메라 (USB)
  손목 카메라 (USB)
  컨베이어 (시리얼)
  로봇 (이더넷 192.168.1.100)
  그리퍼 (이더넷 192.168.1.1)

별도 PC 1대   화면, 데이터베이스 (172.24.0.31)
```

### 2-2. 초기 설계와의 차이

**초기 설계는 관제 PC와 로봇 PC를 나누는 2대 구성이었다.**

**분리하려던 근거**

```
연산 자원 배치     추론은 GPU가 있는 쪽에서
물리적 위치        카메라와 컨베이어는 벨트 옆, 로봇은 로봇 옆
장애 격리          한쪽이 죽어도 다른 쪽은 살아있다
```

**분리하지 않은 이유**

**USB 대역폭 경합을 해소하려는 것이 실질적 동기였는데, 실측으로
경합이 확인되지 않았다.**

```
손목 카메라 가동 상태에서 고정 카메라 검출률 측정
손목 카메라 정지 상태에서 동일 측정
→ 두 조건 결과가 사실상 동일 (각 450프레임 이상)
```

**따라서 분리의 실익이 없다고 판단했다.**

### 2-3. 분리했을 때의 대가

**분리는 이점만 있는 것이 아니다.**

```
네트워크 의존      단절 시 대응이 필요하다 (워치독 설계)
동기화 부담        두 PC의 코드를 맞춰야 한다
디버깅 복잡도      문제가 어느 PC에서 발생했는지 먼저 가려야 한다
```

**단일 구성은 이 셋이 없다.**

## 3. 다중 로봇 확장 시 필요한 변경

### 3-1. 토픽 네임스페이스 분리

**[확인 완료] 모든 토픽과 서비스가 코드에 절대 경로로
하드코딩되어 있다.**

**조사 결과**

| 대상 | 방식 |
|---|---|
| `/ui/state`, `/ui/alert`, `/ui/detections` | 절대 경로 |
| `/conveyor_command` (발행·구독) | 절대 경로 |
| `/voice_command`, `/voice/tts/say` | 절대 경로 |
| `/recycle_detection/detections` (발행·구독) | 절대 경로 |
| 로봇 서비스 전체 | 절대 경로 리터럴 |
| 그리퍼 서비스 | 절대 경로 리터럴 |

**상대 경로나 파라미터 조립은 없다.**

**따라서 네임스페이스 인자만으로는 아무것도 바뀌지 않는다.**

**필요한 작업**

```
방법 1   토픽마다 개별 리매핑을 명시
         -r /ui/state:=/robot1/ui/state  (전 토픽 반복)

방법 2   코드를 상대 경로로 변경
         한 번 고치면 이후 네임스페이스 인자로 해결
```

**방법 2가 근본적이나 코드 수정이 필요하다.**

### 3-2. 노드 이름 충돌

**노드 이름도 리터럴 문자열로 지정되어 있다.**

**같은 이름의 노드가 둘 이상 뜨면 통신에 문제가 생긴다.**

**확장 시 노드 이름도 함께 분리해야 한다.**

### 3-3. 제어 노드 인스턴스 분리

**현재 제어 노드 하나가 추적부터 로봇 제어까지 전부 담당한다.**

```
한 인스턴스 = 한 로봇
```

**로봇이 둘이면 인스턴스를 둘 띄우거나 노드를 쪼개야 한다.**

**인스턴스를 둘 띄우는 방식**

```
장점   코드 수정이 없다
단점   각 인스턴스가 자기 카메라를 봐야 한다
       검출 노드도 인스턴스마다 필요하다
```

**노드를 쪼개는 방식**

```
검출·추적 노드     라인 전체를 담당
로봇 제어 노드      로봇마다 하나
```

**후자가 자원 효율은 좋으나 구조 변경이 크다.**

### 3-4. 캘리브레이션 분리

**좌표 변환 파라미터는 카메라와 로봇의 상대 위치에 종속된다.**

```
카메라 내부 파라미터   카메라마다 다르다
카메라-로봇 변환       조합마다 다르다
벨트 평면              라인마다 다르다
경험적 보정            조합마다 다르다
```

**즉 카메라-로봇 쌍마다 별도 캘리브레이션이 필요하다.**

**설정 파일도 쌍마다 분리해야 한다.**

**이것이 확장 시 가장 시간이 많이 드는 작업이다.** 본 프로젝트에서
캘리브레이션에 세 차례 실패하며 상당한 시간을 썼다.

### 3-5. 추론 처리량

**현재 실측 — GPU 전환 완료(10일차 오후)**

| 항목 | CPU 추론(전환 전) | GPU 추론(현재) |
|---|---|---|
| 카메라 프레임 | 7.5Hz | 7.5Hz |
| 검출 발행 | 7.42Hz | 7.49Hz |
| 추론 장치 | CPU | **GPU(RTX 4060, VRAM 8188MiB)** |
| 검출 노드 CPU 점유 | 약 44%(7코어 상당) | **약 30%/1600% = 0.3코어 상당** |
| GPU 사용률 | 0% | 약 5% |
| VRAM 사용 | — | 335MiB / 8188MiB |
| 유휴 시 CPU | 약 3.1% | 약 3.1% |
| 메모리 사용 | 31GiB 중 2.6% | 동일 |

**GPU 전환으로 검출 1개당 CPU 점유가 약 23배 줄었다(7코어→0.3코어).**
발행률은 카메라 자체 상한(7.5Hz)에 묶여 있어 거의 안 바뀐다 —
처리량은 전환 전부터 이미 충분했고, 전환의 효과는 처리량이
아니라 자원 여유에 있다.

**CPU 기준 라인 수 단순 추정 (참고용, 아래 단서 필수)**

```
GPU 전환 후 검출 1개당 CPU   약 0.3코어(16코어 중)
유휴 여유                    약 15코어 이상
→ CPU만 보면 라인 수십 개까지 여유 (단순 나눗셈)
```

**GPU 기준 라인 수 단순 추정도 같이 필요하다 — 전환 후에는
GPU가 새 병목 후보다.**

```
GPU 사용률 1개당   약 5%
VRAM 1개당         약 335MiB (8188MiB 중)
→ GPU 사용률로는 약 20개, VRAM으로는 약 24개가 산술 상한
```

**위 두 추정 모두 참고용일 뿐 확정 상한이 아니다** — 단순
나눗셈이라 라인당 다른 병목(네트워크, USB 대역폭, 카메라 수,
GPU 컨텍스트 전환 오버헤드, 배치되지 않은 개별 추론 호출의
비선형 비용)을 전혀 반영하지 않는다. **정확한 상한은 실제로
두 번째 라인을 붙여 재실측해야 한다.** 다만 GPU 전환 자체가
CPU 병목을 사실상 해소했다는 점은 실측으로 확정됐다 — 확장
설계의 최우선 선행조건이었던 "GPU 전환"은 완료됐고, 남은
질문은 "정확히 몇 개까지"로 좁혀졌다.

### 3-6. 컨베이어 제어 분리

**컨베이어 노드는 시리얼 포트를 단독 소유한다.**

**라인마다 컨베이어가 있으면 노드도 라인마다 필요하다.**

**정지 사유 집합도 라인별로 분리해야 한다.** 한 라인의 정지가
다른 라인을 멈추면 안 된다.

### 3-7. 데이터베이스 스키마

**[확인 완료] 라인 또는 로봇 식별자 필드가 없다.**

**세 테이블 어디에도 해당 항목이 없다.**

```
waste_type        클래스별 처리 규칙
processing_log    처리 이력
robot_event       처리 건에 딸린 이벤트
```

**확장 시 처리 이력과 이벤트 테이블에 식별자 컬럼을 추가해야
한다.** 그렇지 않으면 어느 라인에서 나온 기록인지 구분할 수
없다.

### 3-8. 화면

**화면은 라인별 상태를 구분해 표시해야 한다.**

**현재 화면은 단일 라인을 전제한다.**

## 4. 확장 구성안

### 4-1. 최소 확장 (2개 라인)

```
관제 PC (GPU)
  라인 1 카메라 + 검출
  라인 2 카메라 + 검출
  라인 1 제어 노드 (네임스페이스 분리)
  라인 2 제어 노드 (네임스페이스 분리)
  컨베이어 노드 2개

로봇 2대 (이더넷)
```

**필요 조건**

```
추론이 두 라인을 감당해야 한다 (GPU 전환 완료됨 — 위 3-5절)
USB 포트가 카메라 수만큼 필요하다
카메라-로봇 쌍마다 캘리브레이션
토픽·노드 이름 분리
데이터베이스 스키마에 라인 식별자 추가
```

### 4-2. 확장 시 우선 확인할 것

```
1. 실제 라인 추가 후 GPU/CPU 점유율 재실측 (정확한 라인 수 상한 확정 —
   위 3-5절 단순추정은 참고용, 실측 전까지 확정 아님)
2. 토픽 리매핑 방식 결정 (개별 리매핑 vs 코드 수정)
3. USB 대역폭 (카메라 수 증가 시)
4. 캘리브레이션 소요 시간
```

**1번이 라인 수 상한을 정한다.**

## 5. 확장하지 않는 것이 나은 경우

**아래 조건이면 단일 라인을 유지하는 편이 낫다.**

```
처리량이 부족하지 않다
공간이 제한된다
캘리브레이션·유지보수 인력이 부족하다
```

**본 프로젝트 규모에서는 단일 라인으로 충분하다.**

## 6. 현재 시스템의 확장 준비도

| 항목 | 상태 | 필요 작업 |
|---|---|---|
| 토픽 이름 | 절대 경로 하드코딩 | 개별 리매핑 또는 상대 경로 전환 |
| 노드 이름 | 리터럴 하드코딩 | 분리 필요 |
| 제어 노드 | 1인스턴스 1로봇 | 인스턴스 복제 또는 노드 분리 |
| 캘리브레이션 | 단일 쌍 | 쌍마다 수행 |
| 설정 파일 | 단일 | 라인별 분리 |
| 컨베이어 | 단일 | 라인별 노드 |
| 화면 | 단일 라인 | 라인 구분 표시 |
| 데이터베이스 | 라인 식별자 없음 | 컬럼 추가 |
| 추론 처리량 | GPU 전환 완료(약 5%/335MiB 점유) | 라인 추가 후 재실측으로 정확한 상한 확정 |

**"코드 수정 없이 확장 가능"한 항목은 없다.**

---

## 7. 요약

**현재 시스템은 단일 로봇 구성이다.**

**확장하려면 아홉 개 항목의 변경이 필요하다.** 토픽·노드 이름
분리, 제어 노드 인스턴스 분리, 쌍별 캘리브레이션, 라인별 설정
분리, 데이터베이스 스키마 확장이 주된 작업이다.

**토픽 이름이 전부 절대 경로로 하드코딩되어 있어, 네임스페이스
인자만으로는 분리되지 않는다.** 개별 리매핑을 나열하거나 코드를
상대 경로로 바꿔야 한다.

**캘리브레이션이 가장 시간이 많이 드는 작업이다.**

**라인 수 상한은 추론 처리량이 정한다.** GPU 전환이 완료되어
검출 노드 하나의 점유가 CPU 44%(7코어)에서 GPU 5%/0.3코어로
크게 줄었다 — 단순 나눗셈으로는 CPU/GPU 어느 쪽도 두 라인
수준에서 막히지 않지만, 이건 다른 병목을 뺀 참고값일 뿐이라
정확한 상한은 실제 라인 추가 후 재실측이 필요하다(3-5절).

**실제로 여러 대를 연결해 운용한 적은 없다.**
