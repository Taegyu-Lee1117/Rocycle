## 1. 문서 개요

본 문서는 시스템을 실제로 운용하고 유지보수하는 데 필요한 절차를
정리한다.

**모든 명령은 관제 PC 실측 기준이다.**

## 2. 기동 절차

### 2-1. 공통 선행 명령

**모든 터미널에서 먼저 실행한다.**

```bash
source /opt/ros/jazzy/setup.bash
source /home/rokey/cobot2_ws/install/setup.bash
source /home/rokey/Rocycle_Project/ros2_ws/install/setup.bash
export ROS_DOMAIN_ID=30
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
```

**`cobot2_ws`가 필요한 이유**: 로봇 메시지 정의와 기동 패키지가
여기 있다. 빠뜨리면 제어 노드가 시작되지 않는다.

### 2-2. [중요] 로봇 시작 자세

**로봇을 홈 자세로 보내고 시작하면 안 된다.**

**이유**: 기준 무게를 로봇의 현재 자세에서 측정하는데, 홈 자세와
측정 자세는 관절각이 달라 중력 보정값이 어긋난다. 약 200g의
오차가 발생하며, 빈 물체가 무거운 것으로 판정된다.

**증상이 조용하다**: 로그에는 "무게 초과로 정상 처리"로 기록되어
잘못된 것을 알아채기 어렵다.

**이 규칙이 깨지는 경로**

```
비상 정지 후 복구
티치 펜던트 수동 조작
노드 재시작
PC 재부팅
```

**대응: 운용 시작 전 확인 사이클을 수행한다.**

```
빈 캔 하나를 벨트에 올린다
can_bin 으로 가면 정상
review_bin 으로 가면 기준 무게가 어긋난 것
```

**원인이 무엇이든 결과로 잡히므로, 자세를 눈으로 확인하는 것보다
확실하다.**

### 2-3. 기동 순서

**한 번에 띄우는 스크립트는 없다. 터미널을 여러 개 열어 순서대로
실행한다.**

**고정 카메라가 검출 노드보다 먼저 떠야 한다.** 검출이 카메라
토픽을 구독하기 때문이다.

#### ① 로봇 스택

```bash
ros2 launch m0609_rg2_bringup bringup.launch.py \
  mode:=real host:=192.168.1.100 rt_host:=192.168.137.50 camera:=false
```

**로봇 드라이버, 그리퍼 제어, 그리퍼 관절 상태 발행이 함께
기동된다.**

**"Could not enable FIFO RT scheduling policy" 경고는 정상이다.**

#### ② 고정 카메라

```bash
ros2 run v4l2_camera v4l2_camera_node --ros-args \
  -p video_device:="/dev/v4l/by-id/usb-046d_C270_HD_WEBCAM_200901010001-video-index0" \
  -p image_size:="[1280, 720]" \
  -p pixel_format:=YUYV \
  -p output_encoding:=rgb8
```

**장치 번호 대신 `by-id` 경로를 쓰는 이유**: 재부팅할 때마다
`/dev/video` 번호가 바뀐다.

#### ③ 손목 카메라

```bash
ros2 launch realsense2_camera rs_launch.py
```

#### ④ 검출 컨테이너

**현재(GPU, 10일차 오후 전환 완료) 기본 컨테이너는 `rocycle-yolo`
(`--gpus all`로 생성)다.** nvidia 커널모듈이 적재돼 있어야
기동된다(모듈 자체는 상시 존재, 적재만 필요 — 아래 트러블슈팅
참고).

```bash
docker start rocycle-yolo
```

**GPU를 못 쓰는 경우의 대체 경로** — nvidia 커널모듈이 적재
안 됐을 때(재부팅 직후 등) `rocycle-yolo`는 기동 자체가 거부
된다(`--gpus all`이 생성 시점에 박혀 `docker start`로 못
바꿈). 이때는 GPU 요구가 없는 별도 컨테이너를 최초 1회 새로
만들어 우회한다:

```bash
docker run -d --name rocycle-yolo-cpu \
  --network host --ipc private --restart no \
  -e ROS_DOMAIN_ID=30 -e RMW_IMPLEMENTATION=rmw_cyclonedds_cpp \
  -e CYCLONEDDS_URI=file:///config/cyclonedds.xml \
  -v /home/rokey/Rocycle_Project/config/cyclonedds.xml:/config/cyclonedds.xml:ro \
  -v /home/rokey/Rocycle_Project/models/recycle_best.pt:/models/recycle_best.pt:ro \
  -w /ros2_ws rocycle-yolo:jazzy sleep infinity
```
(재기동 시에는 `docker start rocycle-yolo-cpu`.) 모듈이
적재된 걸 확인(`lsmod | grep nvidia`)하면 원래 `rocycle-yolo`
로 돌아갈 것 — 두 컨테이너를 동시에 켜둘 필요는 없다.

**검출 노드 실행** (컨테이너 기본 명령이 대기 상태이므로 별도
실행이 필요하다)

```bash
docker exec -d rocycle-yolo bash -lc \
  'source /opt/ros/jazzy/setup.bash && source /ros2_ws/install/setup.bash && \
   exec ros2 run object_detection recycle_detection --ros-args \
   -p model_path:=/models/recycle_best.pt -p device:=\"0\" > /tmp/det.log 2>&1'
```
(`rocycle-yolo-cpu`로 대체 기동한 경우 컨테이너 이름과
`device:="cpu"`로 바꿔서 실행)

**`device` 값**: GPU 사용 시 `"0"`, CPU 대체 시 `"cpu"`.
**주의**: `-p device:="0"`처럼 따옴표만 쓰면 ROS2가 이를 정수로
해석해 노드가 죽는다 — 위처럼 `-p device:=\"0\"`로 이스케이프해
문자열로 전달할 것.

#### ⑤ 컨베이어

```bash
ros2 run recycle_robot conveyor_node
```

**패키지 이름이 `recycle_robot`이다.** 제어 노드의 `rocycle_robot`과
철자가 다르다.

#### ⑥ 음성 출력

```bash
ros2 run recycle_robot tts_node
```

#### ⑦ 제어 노드

```bash
ros2 run rocycle_robot tracking_pick_node --ros-args \
  --params-file /home/rokey/Rocycle_Project/ros2_ws/src/rocycle_robot/config/tracking.yaml \
  -p vision.dry_run:=false \
  -p voice.initial_state:=RUNNING
```

**[중요] 설정 파일 기본값이 시뮬레이션 모드다.**

**실동작 시 `vision.dry_run:=false`를 반드시 명시해야 한다.**
빠뜨리면 컨베이어만 돌고 로봇이 움직이지 않는다.

#### ⑧ 화면 관련

**관제 PC에서는 띄우지 않는다.** 화면과 데이터베이스는 별도
PC에서 동작한다.

#### ⑨ 음성 입력

**현재 기동하지 않는다.** 상태 표시의 음성 입력 항목이 꺼짐으로
나온다.

**음성 명령을 사용하려면 별도 확인이 필요하다.**

### 2-4. 기동 확인

```bash
ros2 node list
ros2 topic hz /image_raw                         # 약 7.5Hz
ros2 topic hz /recycle_detection/detections      # 약 7.4Hz
ros2 topic echo /ui/state --once                 # 상태 확인
```

**`/ui/state`의 연결 상태 항목에서 어느 장치가 빠졌는지 즉시
확인할 수 있다.**

## 3. 종료 절차

### 3-1. 정상 종료

**순서가 중요하다.**

```
1. 컨베이어 정지
   /conveyor_command 로 정지 명령 발행
   노드를 죽이기 전에 먼저 한다

2. 제어 노드 종료 전 진행 단계 확인
   ros2 topic echo /ui/state --once

   stage 가 detect 또는 track 이면 안전
   pick / place / handoff 이면 사이클 완료까지 대기

3. 검출 노드와 컨테이너 종료
   docker exec rocycle-yolo-cpu pkill -f recycle_detection
   docker stop rocycle-yolo-cpu

4. 음성 출력, 컨베이어, 카메라 2종 종료

5. 로봇 스택 종료
```

**2번을 지키지 않으면 로봇이 물체를 든 채 공중에 정지한다.**

### 3-2. 강제 종료

**`pkill -f` 패턴은 사용하지 않는다.** 자기 셸을 함께 종료시켜
비정상 종료 코드가 남는다.

**대신 프로세스 ID를 추출해 종료한다.**

```bash
ps -ef | grep <패턴> | grep -v grep | awk '{print $2}' | xargs kill
sleep 6
ps -ef | grep <패턴> | grep -v grep | awk '{print $2}' | xargs kill -9
```

```
관제 PC   /home/rokey/Rocycle_Project/ros2_ws/src/rocycle_robot/config/
저장소     config/
```

| 파일 | 담는 내용 |
|---|---|

| `item_routing.yaml` | 품목별 목적지, 무게 검사 조건 |
| `bin_teach_points.py` | 통 좌표 (파이썬 모듈) |
| `belt_plane_teach_points.py` | 벨트 평면 기준점 |
| `motion_timing.yaml` | 이동 속도, 도달 한계 |
| `tracking.yaml` | 추적 파라미터, 실행 인자 |
| `obstacles.yaml` | 구조물 정의 |

**`vision.yaml`은 저장소에만 있고 실행 트리에 없다. 현재 사용되지
않는다.**

### 4-2. [중요] 설정 변경 후 빌드

**런타임은 설치본에서 설정을 읽는다.**

**설치본은 심볼릭 링크가 아니라 복사본이므로, 원본을 고쳐도
그대로는 반영되지 않는다.**

```bash
cd /home/rokey/Rocycle_Project/ros2_ws
colcon build
```

**빌드 후 노드를 다시 띄운다.**

### 4-3. 현재 파지 설정

| 품목 | 파지력 | 대기 | 깊이 | 예측 보정 |
|---|---|---|---|---|
| `can` | 15N | 2.0s | 100mm | 0 |
| `paper` | 10N | 2.0s | 110mm | — |
| `battery` | 기본(40N) | 1.0s | 110mm | +30mm |
| `pet_labeled` | 기본(40N) | 1.0s | 100mm | — |
| `plastic` | 15N | 2.5s | 115mm | +20mm |
| `plastic_bag` | 기본(40N) | 1.0s | 100mm | — |

**[주의] 플라스틱 파지력은 여유가 좁다.**

```
10N   이송 중 낙하 발생
40N   변형 발생
15N   현재 설정
```

**이 값을 임의로 조정하지 않는다.**

### 4-4. 증상별 조정

| 증상 | 조정 |
|---|---|
| 물체가 찌그러진다 | 파지력 하향 |
| 물체가 미끄러진다 | 파지력 상향 |
| 물체 뒤에 착지 | 예측 보정값 증가 |
| 물체 앞에 착지 | 예측 보정값 감소 |
| 물체를 누른다 | 하강 깊이 감소 |
| 헛잡는다 | 하강 깊이 증가 |
| 무게 판정 기준 변경 | 라우팅 설정의 임계값 |

### 4-5. 조정 원칙

```
한 번에 하나만 바꾼다
바꾸기 전 값을 기록한다
바꾼 뒤 여러 번 시험한다
같은 품목 안에 형태가 다양하면 가장 취약한 것을 기준으로 한다
```

### 4-6. 모델 교체 시

```
1. 새 모델의 클래스 목록 확인
2. 파지 설정에 모든 클래스가 있는지 확인
3. 라우팅 설정에 모든 클래스가 있는지 확인
4. 전 품목 검출·분류 재확인
```

**설정에 없는 클래스가 들어오면 파지 도중 예외가 발생한다.**

**클래스명은 항상 모델에 맞춘다.** 모델 재학습 비용이 크기
때문이다.

**모델을 바꾸면 기존 클래스의 동작도 달라진다.** 신뢰도 분포와
오분류 패턴이 변하므로 전 품목을 다시 확인해야 한다.

## 5. 문제 해결

### 5-1. 로봇이 움직이지 않고 벨트만 돈다

**시뮬레이션 모드로 실행되었을 가능성이 높다.**

```
제어 노드 실행 시 vision.dry_run:=false 를 명시했는가
```

### 5-2. 물체를 인식하지 못한다

| 확인 | 조치 |
|---|---|
| 물체가 학습 대상 6종인가 | 대상 외 물체는 의도적으로 무시됨 |
| 물체가 벨트 진행 방향과 나란한가 | 비스듬하면 검출되지 않는 경우가 있음 |
| 물체가 표시된 가로 위치에 있는가 | 화면 위치에 따라 분류가 달라질 수 있음 |
| 물체가 화면 가장자리에 걸쳤는가 | 15px 이내는 폐기됨 |
| 투명한 재질인가 | 깊이 정보가 없어 검출이 어려움 |
| 검출 토픽이 발행되는가 | `ros2 topic hz` 로 확인 |
| 카메라가 검출보다 먼저 떴는가 | 순서가 반대면 구독 실패 |

### 5-3. 파지가 빗나간다

| 증상 | 원인 | 조치 |
|---|---|---|
| 물체 뒤쪽에 착지 | 예측이 짧음 | 예측 보정값 증가 |
| 물체 앞쪽에 착지 | 예측이 과함 | 예측 보정값 감소 |
| 좌우로 빗나감 | 좌표 변환 오차 | 캘리브레이션 확인 |
| 물체를 누름 | 하강 깊이 과함 | 하강 깊이 감소 |
| 헛잡음 | 하강 깊이 부족 | 하강 깊이 증가 |

**예측 조정 전에 확인할 것**: 파지 준비 동작이 예측 계산 이후에
추가되지 않았는지 확인한다. 추가되었다면 그 시간이 예측에
반영되어야 한다.

### 5-4. 무게 판정이 이상하다

| 증상 | 원인 | 조치 |
|---|---|---|
| 빈 물체가 확인 필요 통으로 | 기준 무게 자세 불일치 | 2-2절 확인 사이클 |
| 무거운 물체가 통과 | 같은 원인 | 같음 |
| 값이 크게 흔들림 | 로드셀 주기 진동 | 판정 대상 무게를 크게 조정 |

**로드셀에 주기 약 27초, 진폭 ±45g의 진동이 있다.** 평균이나
중앙값으로 제거되지 않는다.

**판정 대상 물체는 50g 미만 또는 350g 초과여야 한다.**
150~250g 구간은 판정할 수 없다.

### 5-5. 사람에게 건넨 물체를 놓지 않는다

| 확인 | 조치 |
|---|---|
| 충분히 당겼는가 | 수평으로 7mm 이상, 3.0mm/s 이상 |
| 15초가 지났는가 | 자동으로 확인 필요 통으로 이동 |

**천천히 당기면 감지되지 않을 수 있다.** 의도된 안전측 동작이다.

### 5-6. 컨베이어가 멈춘 채 움직이지 않는다

| 확인 | 조치 |
|---|---|
| 화면 알림 확인 | 정지 사유가 표시됨 |
| 도달 한계 물체가 있는가 | 그 물체가 처리되면 재가동 |
| 120초가 지났는가 | 워치독이 강제 재가동 |
| 비상 정지 상태인가 | 물리 버튼 해제 필요 |
| 시리얼 장치 인식 | `lsusb` 로 확인 |

**컨베이어 장치 경로**

```
/dev/ttyACM0
by-id: usb-Arduino__www.arduino.cc__Arduino_14101-if00
```

**포트 번호가 재연결 시 바뀔 수 있으므로 `by-id` 경로를 쓴다.**

### 5-7. 로봇이 물체를 든 채 멈췄다

```
원인   파지 사이클 도중 노드 종료 또는 예외
조치   그리퍼 개방 명령으로 회수
       또는 티치 펜던트로 수동 회수
       회수 후 노드 재시작
```

**재시작 후 2-2절 확인 사이클을 수행한다.**

### 5-8. 검출 컨테이너(GPU)가 시작되지 않는다

```
증상   docker start rocycle-yolo 가 거부됨
원인   --gpus all 컨테이너의 prestart 훅이 NVML로 GPU를 열거하려는데
       nvidia 커널모듈이 적재돼 있지 않음(재부팅 직후 흔함).
       모듈 자체가 없는 게 아니라 "적재"만 안 된 상태일 수 있음 —
       재빌드 전에 먼저 lsmod | grep nvidia 로 확인할 것
조치   1) 모듈 적재 시도(예: sudo modprobe nvidia) 후 재시도
       2) 그래도 안 되면 rocycle-yolo-cpu 대체 컨테이너 사용
          (④ 검출 컨테이너 절 참고) — 시연 급하면 이쪽을 먼저 써도 됨
```

### 5-9. 장치 인식 실패

```
증상   재부팅 후 특정 USB 장치가 인식되지 않음
확인   lsusb 목록 확인
조치   USB 재삽입 또는 포트 변경
```

**접촉 불량으로 인식되지 않은 사례가 있다.**
**케이블을 고정해두면 재발이 줄어든다.**

## 6. 정기 점검

### 6-1. 운용 전 (매회)

```
□ 로봇 시작 자세 확인 사이클 (2-2절)

```

### 6-2. 주기 점검

```
□ 좌표 정확도 재확인 (기준점 파지 시험)

□ 그리퍼 개폐 동작
□ 컨베이어 속도 실측
□ 로그 용량 확인
```

### 6-3. 변경 후 점검

| 변경 | 재검증 대상 |
|---|---|
| 카메라 위치 이동 | 좌표 변환 전체 |

| 모델 교체 | 전 품목 검출·분류 |

| 설정 파일 수정 | 빌드 후 재기동 |

## 7. 백업 및 복구

### 7-1. 백업 대상

```
소스 코드          버전 관리 저장소 main 브랜치
설정 파일          같음
캘리브레이션 결과   같음
학습 모델          별도 보관 (용량이 크므로)
처리 이력          데이터베이스 백업
```

### 7-2. [중요] 실행본과 저장소의 일치

**본 프로젝트에서 실행 중인 코드 일부가 저장소에 없던 사례가
있었다.** 디스크 장애 시 복구가 불가능한 상태였다.

**작업 종료 시 변경분을 반드시 반영한다.**

**정본은 관제 PC 실행 트리다.** 저장소 사본과 차이가 있으면
실행 트리를 기준으로 확인한다.

### 7-3. 모델 파일 주의

**모델 파일이 여러 버전 존재할 수 있다.**

**패키지에 포함된 파일이 구버전이고, 실제 운용 모델은 컨테이너가
별도 경로에서 읽는 경우가 있다.**

**백업 시 실제 운용 중인 버전을 확인한다.** 구버전을 정본으로
착각하면 복구 후 동작이 달라진다.

### 7-4. 복구 절차

```
1. 저장소에서 코드 및 설정 복원
2. 캘리브레이션 결과 확인
3. 모델 파일 배치 및 버전 확인
4. 빌드
5. 기동 후 2-4절 확인
6. 좌표 정확도 재확인
7. 2-2절 확인 사이클
```

## 8. 알려진 함정

**운용 중 반복적으로 문제가 되었던 항목이다.**

| 항목 | 내용 |
|---|---|
| 시뮬레이션 기본값 | 설정 기본값이 시뮬레이션이다. 실동작 시 명시적으로 꺼야 한다 |
| 설정 반영 | 원본을 고쳐도 빌드 전에는 반영되지 않는다 |
| 그리퍼 닫기 비동기 | 명령이 반환되어도 물리 동작이 끝나지 않았다. 대기 시간을 지킨다 |
| 파지력 세션 유지 | 한 번 설정한 파지력이 유지된다. 매 파지 직전 명시적으로 설정한다 |
| 이동 명령 성공 반환 | 성공을 반환해도 실제로 이동하지 않은 경우가 있다. 도달 좌표를 확인한다 |
| 배치 3단계 시퀀스 | 통 상공 진입 후 반드시 수직 하강·상승을 지킨다. 대각선 이동은 통을 밀어 넘어뜨린다 |
| 순응 제어 기준점 | 진입 직후가 아니라 안정된 뒤 기준점을 잡는다 |
| 패키지 이름 혼동 | 컨베이어·음성은 `recycle_robot`, 제어는 `rocycle_robot` |
| 임시 우회 문서화 | 임시 조치를 남길 때는 무엇을 우회했는지, 원래 요구사항이 무엇인지, 언제 재검토할지를 함께 적는다 |

**마지막 항목의 배경**: 카메라 드라이버 문제로 임시 우회한
설정이 정식 절차로 굳어져, 명시된 요구사항과 모순인 채 여러 날
운용된 사례가 있었다.
