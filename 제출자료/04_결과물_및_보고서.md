## 1. 개요

본 문서는 개발 과정에서 얻은 실측 데이터와 주요 시행착오 사례를
정리한다. 특히 원인 규명 과정에서 결론이 뒤집힌 사례를 그대로
기록한다.

## 2. 최종 검증 결과

### 2-1. 전체 시나리오 완주

| 컵 뚜껑 | — | 플라스틱 통 | 정상 분류 |
| 건전지 | — | 건전지 통 | 정상 분류 |
| 검은 비닐 | — | 확인 필요 통 | 재질 판별 불가 |

**7종 전부 의도대로 동작했다.**

### 2-2. 재현성

**같은 날 세 차례 완주(CPU 추론 2회, GPU 추론 1회)에서 무게
판정이 동일하게 재현되었다.**

| 물체 | 1회차(CPU) | 2회차(CPU) | 3회차(GPU) | 결과 |
|---|---|---|---|---|
| 샌드 캔 | +328.9g | +494.2g | — | 전부 확인 필요 통 |
| 빈 캔 | -22.1g | +44.3g | **-97.6g** | 전부 캔 통 |

**빈 캔의 순 무게가 세 회차에 걸쳐 142g 폭(-97.6~+44.3g)으로
흔들렸으나, 판정 임계값 200g 대비 여유가 충분해 전부 캔 통으로
정상 처리됐다.** 이 변동은 규명된 로드셀 진동 범위 안이다.
**-97.6g은 하한값(`net_min_kg=-0.15kg`)을 낮춰둔 효과가 가장
선명하게 드러난 사례다** — 이전 규칙(하한 -30g)이었다면 확인
필요 통으로 잘못 갔을 값이다.

**3회차(GPU)에서 배치 확인 지표(`open_max_rad` 경계값 재설계
이후)도 5건 전부 정답 판정됐다** — 그중 하나(-0.2915)는 재설계
전 규칙이었으면 오탐이었을 값이다.

### 2-3. 실패 경로 검증

**성공 경로뿐 아니라 실패 경로도 설계대로 동작했다.**

```
무게 초과       → 확인 필요 통
사람 미수령      → 15초 후 확인 필요 통
미학습 물체      → 손대지 않고 통과
```

**"안 되는 경우"가 정의된 대로 처리된다는 것을 확인했다.**

### 2-4. 운영 규칙의 실물 검증

**미학습 물체를 펴서 올리는 규칙이 실제로 결과를 갈랐다.**

```
접어서 올림   라벨 페트병으로 오분류되어 파지까지 진행
펴서 올림     검출 자체가 되지 않고 통과
```

**펼친 상태 600프레임 중 3프레임만 검출되었다.**

**프로세스별**

```
검출 노드      CPU 약 44%(7코어) -> GPU 전환 후 약 30%(0.3코어)
카메라 노드    약 8.7%(변화 없음)
GPU 사용률     0% -> 5%
VRAM           - -> 335MiB / 8188MiB
메모리         31GiB 중 2.6%
```

**GPU 전환 완료, CPU 점유 약 23배 감소.** 검출 발행률은
7.42→7.49Hz로 거의 안 바뀌었는데, 카메라 자체 프레임률(7.5Hz)
이 상한이라 추론이 빨라져도 발행 간격은 카메라에 묶여있기
때문이다. 이 덕분에 전환 전 우려했던 "확정 프레임 수 비례조정
필요"가 실제로는 발생하지 않았다 — 발행 간격이 그대로라 프레임
수가 뜻하는 실제 시간도 그대로이기 때문이다. 전환 실패
(아침, 커널모듈 미적재)와 성공(오후, 모듈 적재 확인 후) 경위는
4-8절 참고.

## 4. 시행착오 사례

**아래는 원인 규명 과정에서 결론이 여러 번 뒤집힌 사례다.**
**최종 결론뿐 아니라 뒤집힌 과정을 함께 기록한다.**

### 4-1. 좌표 변환 — 세 번의 실패

**증상**: 계산된 좌표가 실제 물체 위치와 크게 어긋났다.

```
1차 실패   깊이 정보 없이 3차원 좌표를 구하려 함
           → 원리적으로 불가능. 평면 가정 도입

2차 실패   단위테스트를 임의 값으로 통과시킴
           → 실측에서 157mm 오차 발생
           교훈: 검증 데이터가 실제 조건을 재현해야 한다

3차 실패   이론 계산만으로 보정
           → 계통 오차 잔존. 경험적 보정 함수 도입
```

**최종**: RMS 4.5mm 달성

### 4-2. 핸드오버 오탐 개방

**증상**: 사람이 받지 않았는데 약 3초 만에 그리퍼가 열려 물체가
떨어졌다.

```
1차 진단   순응 제어 진입 직후의 처짐을 당김으로 오인
1차 대책   고정 시간 대기 후 기준점 캡처
           → 문제를 그 시간만큼 늦춘 것뿐. 재발

2차 진단   판정 기준 자체가 잘못됨
           누적 변위만 보면 느린 처짐이 결국 임계값을 넘는다
2차 대책   속도 조건 추가 (당김은 빠르고 처짐은 느리다)
           하향 성분 제외 (처짐은 거의 전부 하향)
```

**최종**: 오탐 개방 0건

**주의할 점**: 당김 속도를 20~50mm/s로 추정하고 임계값을
15mm/s로 잡았으나, 실측은 6.2~12.4mm/s였다. 추정 위에 임계값을
세운 것이 오류였다. 실측 후 3.0mm/s로 조정했다.

### 4-3. 무게 측정 분산

**증상**: 같은 빈 캔인데 측정값이 -42g에서 +168g까지 흔들렸다.

```
1차 가설   힘 센서 고유 노이즈
           → 정지 상태 실험으로 ±38g 확인
           그러나 실제 조건을 재현하지 않은 실험이었다

2차 가설   컨베이어 진동
           → 벨트 가동/정지 조건 비교 결과 차이 없음. 기각

3차 진단   측정 두 시점의 로봇 자세가 다름
           중력 보정값이 달라져 계통 오차 발생
```

**대책**: 파지 후 고정된 측정 자세로 이동해 측정

**결과**: 분산 211.4g → 46.8g

**잔여 문제**: 로드셀 자체에 주기 약 27초의 진동이 있음을
추가로 확인했다. 측정창보다 주기가 길어 평균으로 제거되지
않는다. 이는 정밀 계량이 아닌 유무 판별로 설계 방향을 바꾸는
근거가 되었다.

### 4-4. 종이 상자 오분류 — 네 번의 재정정

**본 프로젝트에서 가장 많이 뒤집힌 사례다.**

**증상**: 같은 종이 상자가 때로는 종이로, 때로는 페트병으로
분류되었다.

```
1차 가설   조명 조건
           낮과 밤의 측정 결과가 달랐다
           → 통제 어려움. 대책 없음

2차 가설   손목 카메라의 USB 대역폭 경합
           손목 카메라 가동 여부와 시각이 상관되어 보였다
           → 켜고 끄며 A/B 비교 (각 450프레임 이상)
           → 두 조건 결과 동일. 기각

3차 가설   물체 배치 자세
           박스가 온전히 보이는 자세에서는 종이로 100% 분류
           → 배치 규칙으로 회피 가능하다고 판단, 승인까지 함

4차 진단   화면상 x 위치
           같은 박스·같은 자세로 위치만 바꿔 연속 측정
           → 특정 경계를 기준으로 100%씩 정반대 결과
           → 양쪽 모두 신뢰도 0.92~0.95로 확신에 찬 오분류
```

**최종 결론**: 이 물체는 두 클래스의 결정 경계 위에 있다.
배치 규칙으로 회피할 수 없다.

**조치**: 해당 품목을 운영 대상에서 제외

**이 사례에서 얻은 것**

```
정밀함과 정확함은 다르다
  회귀 잔차가 낮다고 참값에 가까운 것은 아니다

두 변수가 함께 움직일 때 하나만 지목하면 그것이 원인처럼 보인다
  3차 가설이 그 경우였다

승인한 대책을 실험으로 철회할 수 있어야 한다
  3차 대책을 시연에 넣었다면 잘못된 회피책이 남았을 것이다
```

### 4-5. 컨베이어 속도 측정 오류

**증상**: 문서값과 실측값이 크게 달랐다.

```
1차 오류   비전 측정에서 기준점이 코드와 달랐다
2차 오류   측정 구간에 정지 시간이 포함되었다
           → 36% 낮게 산출
정정       이동 구간만으로 회귀 → 약 4.98mm/s
```

**교훈**: 측정 방법이 실제 조건을 재현하는지뿐 아니라, 측정
구간이 측정 대상만 포함하는지도 확인해야 한다.

### 4-6. 검출 결과 누적

**증상**: 파지 사이클 종료 직후 확정이 비정상적으로 빨리
완료되고 예측이 크게 빗나갔다.

```
원인   파지 동작이 콜백을 블로킹하는 동안 검출 결과가 큐에 쌓임
       사이클 종료 시 한꺼번에 처리되어 확정 조건이 0.008초에 충족
       그 짧은 구간의 속도로 장시간을 외삽
```

**대책**: 도착 간격이 비정상적으로 짧으면 누적분으로 간주해 폐기

**결과**: 확정 소요 시간 0.008초 → 1.057초로 복원

**이 문제가 드러난 경위**: 컨베이어를 정지시키는 방식에서는
물체가 움직이지 않아 옛 위치가 여전히 유효했으므로 문제가
보이지 않았다. 무정지 방식으로 바꾸면서 드러났다.

**즉 무정지가 만든 결함이 아니라 원래 있던 결함을 드러낸
것이다.**

**참고**: 이 무정지 실물시험 자체는 실제로 진행됐고 위 버그도
그 과정에서 발견·수정됐지만, 무정지 방식 자체는 별도 문제
(계량 중 진동)로 영구 반영되지 않았다 — 현재는 파지 중 정지
방식을 유지한다(4-8절 참고).

### 4-7. 판정 지표의 표본 확대

**배치 확인 지표를 4건 기준으로 확정했다가 11건으로 재설계했다.**

```
4건 기준   군집 간 여유가 있어 보였으나 표본이 좁았다
11건 기준  경계값 재산정. 과거 11건 재판정 11/11 정답
```

**표본이 늘면서 오히려 결론이 단단해졌다.**

**한 지표는 지표 자체를 폐기했다.** 손목 카메라 기반 파지 자세
검증에서 배경 노출 비율을 지표로 삼았으나, 실패 표본이 나온 뒤
4건 중 1건만 맞았다.

**원인**: 파지 실패 시 물체가 그리퍼 바로 아래 벨트에 남아
있어, 손목 카메라에서 "물린 물체"와 "빈 그리퍼 아래 놓인 물체"가
거의 같은 그림이 된다. 처음 모은 표본은 벨트가 비어 있던
상태여서 이 경우를 대표하지 못했다.

**조치**: 근거 없는 판정이 로그에 남으면 다음 사람이 믿게 되므로
판정 문구를 제거하고 지표만 기록했다.

### 4-8. 문서와 실물의 불일치

**문서에 기록된 값이 실제 설정과 다른 사례가 5건 확인되었다.**

| 항목 | 문서 | 실제 |
|---|---|---|
| 플라스틱 파지력 | 10N | 15N |
| 비닐(plastic_bag) 하강 깊이 | 미확정 | 100mm |
| 사용 설정 파일(vision.yaml) | 목록에 포함 | 실행 트리에 없음, 미사용 |
| 컨베이어 정지 방식 | 무정지로 최종 확정 | 실제로는 파지 중 정지 유지(`stop_during_pick: true`) — 아래 참고 |
| GPU 추론 | 드라이버 파손, 재빌드 필요 | 실제로는 커널모듈 미적재 문제, 재빌드 불필요 — 오후 전환 완료(3-5절) |

**플라스틱 파지력 사례의 경위**: 40N에서 10N으로 내렸다가
이송 중 낙하가 발생해 15N으로 올렸는데, 중간 단계인 10N이
최종값으로 문서에 남았다.

**낙하가 로그에 묻힌 이유**: 배치 자체는 성공으로 기록되어
알아채기 어려웠다.

**컨베이어 정지 방식 사례의 경위**: 무정지 전환은 1단계(정지
유지)→2단계(무정지 실물시험)→3단계로 계획됐고 2단계 실물시험
자체는 진행됐다(4-6절의 검출 결과 누적 버그도 이 시험 중
발견). 그런데 무정지 상태에서 벨트 진동이 계량에 실려 net
오차가 크게 벌어지는 문제가 나와, 무정지를 영구 설정으로
반영하는 작업이 끝나지 않은 채 남았다 — 설정 파일에 항목
자체가 없어 코드 기본값(정지 유지)이 계속 쓰이고 있었다.
촬영 일정상 지금 되돌리지 않고 문서만 정정했다(도달 한계
안전 정지 기능 자체는 별도로 구현·검증 완료 상태다).

**교훈**: 정본은 실행 트리다. 문서와 다르면 실행 트리를 확인한다.
설계·시험이 실물로 진행됐다는 사실과, 그 결과가 영구 설정으로
반영됐다는 사실은 다르다 — 둘을 같은 것으로 여기면 이번
컨베이어 사례처럼 "시험 성공 = 배포 완료"로 잘못 기록하게 된다.

## 5. 설계 원칙의 형성 과정

**아래 원칙들은 개발 과정에서 실패를 통해 확립되었다.**

### 5-1. 분류 결과를 안전 게이트로 쓰지 않는다

**계기**: 내용물이 든 캔이 페트병으로 오분류되면 무게 검사를
건너뛰고 사람에게 전달되는 경로가 확인되었다.

**신뢰도로 걸러낼 수 없다는 것도 확인되었다.**

| 구분 | 신뢰도 범위 |
|---|---|
| 정답 분류 | 0.63 ~ 0.92 |
| 오분류 | 0.51 ~ 0.91 |

**두 분포가 크게 겹쳐 어떤 임계값으로도 구분되지 않는다.**

**대책**: 사람에게 건네기 직전 분류와 무관하게 무게를 확인한다.

**부수 효과**: 두 품목의 무게 임계값을 같게 두면 오분류가
발생해도 결과가 달라지지 않는다.

### 5-2. 판단할 수 없으면 판단하지 않는다

```
비닐          재질 판별 불가 → 확인 필요 통
계측 실패      값을 신뢰할 수 없음 → 확인 필요 통
미학습 물체    인식되지 않음 → 손대지 않음
```

**억지로 분류하는 것보다 사람에게 넘기는 것이 낫다.**

### 5-3. 검증이 실제 실행 경로를 재현해야 한다

**본 프로젝트에서 네 차례 위반되었다.**

```
캘리브레이션   임의 값으로 단위테스트 통과 → 실측 157mm 오차
영상 스트림    실제와 다른 요청으로 확인 → 원인 오판
힘 센서        실제 조건 미재현 → 노이즈로 오진
화면 검증      실제와 다른 해상도로 확인 → 존재하지 않는 문제 수정
```

**기록해두는 것만으로는 재발을 막지 못했다.**
**착수 조건으로 만들어야 한다.**

### 5-4. 임시 우회는 반드시 세 가지를 함께 적는다

```
무엇을 우회했는가
원래 요구사항이 무엇인가
언제 재검토해야 하는가
```

**계기**: 카메라 드라이버 문제로 임시 우회한 설정이 정식 절차로
굳어져, 명시된 요구사항과 모순인 채 여러 날 운용되었다.

### 5-5. 정본은 실행 트리다

**계기**: 저장소 사본과 실행본이 갈라져 있었고, 문서는 저장소
사본을 기준으로 작성되어 실제와 다른 값이 여러 건 남았다.

**대책**: 값을 인용할 때 실행 트리를 확인한다.
