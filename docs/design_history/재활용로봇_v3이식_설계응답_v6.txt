먼저 v3 원문(제안A_설계_상태머신_ROS2아키텍처_일정.txt)을 다시 열어

 요청 1 — 이식 매핑표 완성
====================================================================

### a) 4-2절(그대로 살아남는 것) — 오류 1건

**"지식베이스 스키마"가 살아남는다고 적었는데, v3 자체에 이 절이
없습니다.** [원문] v3에는 v2에 있던 "지식베이스 설계" 섹션이
빠져 있고, `/policy/query_knowledge` 서비스 인터페이스(3-1절
표)만 남아 있습니다 — {reason, action} 페이로드 구조는 3-1절
표에 한 줄로만 언급되고 별도 스키마 절이 없습니다. **이식 매핑을
완성하기 전에 v3 쪽 문서 결손부터 메워야 합니다** — 이번 응답
4절 말미에 이 부분을 복원해서 채워뒀습니다.

이 외에는 4-2절 리스트가 정확합니다.

### b) 4-3절(변경 필요) — 누락 3건

**1. `policy_node`의 (c) 허용부품 검증 역할이 5''에는 대응물이
없습니다.** 이건 개념 매핑표(4-1절) 자체의 오류입니다. 표는
`allowlist(허용 부품 목록)`을 `regional_policy(지역별 분리배출
기준)`에 대응시켰는데, 실제로는 이 둘이 다른 역할입니다:
  - v3의 allowlist: **이진 검증**("이 삽입부품이 허용 목록에
    있는가?") → 오류체결 여부를 가르는 판정 근거
  - 5''의 regional_policy: **목적지 매핑**("이 재질이 어디로
    가는가?") → v3의 `destinations`(6절)에 대응하는 것이지
    allowlist에 대응하는 게 아님

  즉 v3의 (c) 역할(허용 여부 검증)이 5''에서 그냥 사라졌습니다.
  policy_node가 (a)(b) 두 역할만 남고 3역할 스토리가 깨집니다.
  **재구성 제안**: (c)의 새 자리는 "이 지역에서 이것도 재활용
  되나요?"류 **정책 자체에 대한 질문**(예: "이 아파트는 비닐도
  재활용 통에 넣나요?")으로 재배치하면 3역할이 복원됩니다 —
  이건 INFORMATION 트리거의 한 종류로 자연스럽게 들어갑니다.

**2. `/vision/inspect`의 `slot_id` 파라미터가 의미를 잃습니다.**
  단일 투입 위치가 되면 여러 슬롯 중 하나를 특정할 필요가
  없어집니다. `slot_id` → **`cycle_id`**(이번 투입 처리
  사이클의 순번, 로그 식별용으로만 남김)로 이름과 의미를 바꿀
  것을 제안합니다. `MOVE_TO_SLOT_APPROACH(i)`도 `i` 인덱스가
  무의미해지므로 `MOVE_TO_INPUT_APPROACH`(인자 없음)로 변경.

**3. `/policy/decide` 응답에 `needs_confirmation`(v3, 정책
미등록)과 `needs_clarification`(5'' 신설, 비전 판정 애매) 두
필드가 공존하게 되는데, **둘 다 true인 경우 어느 질문을 먼저
하는지가 안 정해져 있습니다.** 예: 아직 지역 정책이 등록 안 된
재질인데 동시에 confidence도 애매한 경우. **우선순위 제안**:
`needs_clarification`(비전 판정) 먼저 → 판정이 끝나야 `final_class`가
정해지고, 그래야 `needs_confirmation`(목적지 미등록) 여부를 판단할
수 있으므로 논리적으로도 이 순서가 맞습니다.

### c) 슬롯 순회 소멸로 깨지는 로직 — "슬롯 반복 실패"의 재해석

원래 규칙의 목적은 "가망 없는 슬롯 하나에 매달려 나머지 슬롯들이
기다리는 것을 막는다"였습니다. 단일 투입 위치에서는 "나머지
슬롯"이 없으므로 **"막을 대상"이 아니라 "포기하고 다음 아이템으로
넘어가는 신호"로 목적이 바뀝니다.** 재해석:

```
"슬롯"의 새 의미 = 이번 투입 사이클(cycle_id)에서의 시도 횟수 카운터
같은 카운터가 2회 이상 SKIP/ABORT
  → 즉시 "확인 필요" 로그 등록 (동일)
  → **(신규) TTS "이 물건은 처리를 포기합니다. 다른 물건을
     놓아주시거나 치워주세요"**
  → WAITING_FOR_ITEM 상태로 복귀, 카운터 리셋
```

굵게 표시한 TTS 알림이 **v3에는 없던 신규 요구사항**입니다. v3는
슬롯 순회 구조라 로봇이 알아서 다음 슬롯으로 이동했지만, 5''는
사람이 물건을 치워주지 않으면 로봇이 무한정 같은 자리를 보며
대기할 수 있어서, "포기했다"는 것을 명시적으로 알리지 않으면
시스템이 그냥 멈춰 있는 것처럼 보입니다. 4절 매핑표에 이 항목을
반드시 추가해야 합니다.

### d) 투입 감지 방식 — 권장안: 자동 폴링(안정화 대기) + 음성 단축

세 방식을 비교했습니다:
  - 순수 폴링(즉시 트리거): 사람 손이 아직 물건 위에 있는 상태를
    잘못 INSPECT할 위험 — 오분류 유발
  - 순수 음성 트리거("확인해줘"): 매번 같은 발화라 V1=0에 가까움
    (버튼과 다를 게 없음) — 애써 만든 V1=3 스토리를 이 지점에서
    스스로 깎아먹음
  - **권장: 자동 폴링 + 안정화 대기.** depth 이미지의 프레임 간
    변화량이 N초간 임계값 이하로 유지되면(= 손이 빠지고 물체가
    정지함) INSPECT 자동 트리거. 음성("확인해줘")은 이 대기시간을
    건너뛰는 **단축 명령**으로만 보조 제공(필수 아님).
    이러면 V1 손실 없이 편의성도 챙깁니다.

이 방식은 v3에 없던 개념(v3는 능동적으로 "이동"했지 "대기하며
감지"하지 않음)이라, **신규 상태 `WAITING_FOR_ITEM`**이 4-1절
정상흐름에 추가돼야 합니다(IDLE과는 다름 — IDLE은 세션 시작 전,
WAITING_FOR_ITEM은 세션 중 다음 아이템 대기).

 요청 2 — 2-1절 종이팩 질문 조건화 방식 결정
====================================================================

**(i) 클래스 분리를 권장합니다.**

먼저 (i)와 (ii)를 다시 보니, 둘 다 원래 v6가 우려한 "V1=0(매번
같은 질문이라 버튼 대체 가능)" 문제를 **똑같이 해결**한다는 걸
발견했습니다. 사람이 "이번엔 질문이 나올지 안 나올지"를 미리 알
수 없다는 점에서 (i)(ii) 모두 동일합니다 — **애초에 사람이
코팅 여부를 미리 안다면 로봇에게 물을 이유 자체가 없으므로**,
질문 발생 여부가 로봇의 판단(클래스든 confidence든)에서 나온다는
사실 자체가 V1을 지킵니다. 그래서 이 두 안의 실제 차이는 V1이
아니라 **재현성**에서 갈립니다. [추론]

  - (ii) confidence 애매구간: 신뢰도가 조명·각도에 따라 흔들리므로,
    시연 당일 하필 질문이 안 뜨는(또는 반대로 명확한 것도 애매하게
    나오는) 리스크가 있습니다 — 이건 "질문이 매번 뜬다"의 반대
    극단이지만 마찬가지로 재현성 문제입니다.
  - (i) 클래스 분리: 어느 실물을 투입하느냐로 질문 발생 여부가
    **팀이 통제 가능한 변수**가 됩니다. 실물 조달도 재활용품이라
    비용이 거의 없습니다(일반 우유팩 1개 + 멸균팩류 1개면 끝 —
    M축 강점을 그대로 유지).

**(iii) 검토했으나 기각**: 질문 내용 자체를 매번 다르게 만드는 안
(예: "어떤 음료였나요?"처럼 자유발화를 받아 매핑)도 생각해봤지만,
5일 안에 넣기엔 파싱 복잡도가 늘어 T축(완주 가능성)을 깎습니다.

 요청 3 — 클래스별 파지 파라미터

### a) grasp_offset 클래스별 맵 — 타당함. 추가 파급 3가지

  1. **접근 자세(orientation)도 클래스별로 필요합니다.** 병/캔은
     원통형이라 yaw 무관하지만 종이팩은 비대칭이라(요청3-b) 접근
     자세 자체가 달라져야 합니다 — `grasp_offset_xyz`뿐 아니라
     방향값도 스키마에 필요.
  2. **`gripper_open_width`(최대 개방폭)는 장비 스펙이라 고정값
     하나로 유지하는 게 맞습니다** — 지금 4-4절 스키마가 이미
     `gripper_close_width`만 클래스별 맵으로 두고 있는데, 이 구분이
     맞습니다(확인 사살).
  3. **`MOVE_TO_INPUT_APPROACH`의 접근 고도는 가장 큰 물체(종이팩
     또는 안 찌그러진 페트병) 기준으로 잡아야** 작은 물체(캔)에도
     충돌 없이 안전합니다 — 클래스별로 다른 접근고도를 쓰는 대신
     "가장 큰 것 기준 단일 고도"로 단순화할 것을 권장(재현성 우선).

### b) 종이팩 yaw — **투입 트레이 방향가이드를 권장**, yaw 추정은 기각

vision 기반 yaw 추정(마스크의 minAreaRect 등)은 기술적으로
가능하지만, vision_node에 방향 출력을 추가하고 그리퍼 접근 자세
계산도 더해야 해서 복잡도가 늘어납니다. 이 프로젝트가 지금까지
반복적으로 택해온 원칙(장보기 봉투 지그, 얕은 선반 등 — **소프트웨어
복잡도보다 물리적 지그를 우선**)과 일치시켜, **투입 트레이에
L자 모양 정렬 가이드**를 두어 사람이 자연스럽게 방향을 맞춰
놓게 하는 방식을 권장합니다. 비용이 사실상 0(재료조달 M축을
안 깎음)이고 재현성도 확실합니다.

### c) 캔 미끄러움 — 힘 상향은 위험할 수 있음, 대안 제시

[원문] `onrobot.py`에 `get_fingertip_offset()`(레지스터 258)이
있는 걸 확인했는데, 이는 **RG2가 교체형 핑거팁을 지원**한다는
뜻입니다. 단순히 `force_val`을 올리면 알루미늄 캔은 얇아서
**찌그러질 위험**이 있습니다(페트병/종이팩보다 훨씬 무릅니다).
권장: (1) 가능하면 **고마찰 핑거팁으로 교체**, (2) `force_val`은
"찌그러지지 않는 한도 내에서" 클래스별 최소값으로 실측(캔은
낮게), (3) 접근 속도를 낮춰 파지 순간의 충격을 줄임(스쿠핑
프로젝트의 "힘 감지 구간 저속 유지" 교훈 재사용).

 요청 4 — 스트레치 인터페이스 선점안
====================================================================

### A — 규칙 충돌 감지

```
내부 함수 (policy_node, ROS 인터페이스 아님):
  validate_before_apply(new_rule: {material_type, destination},
                         current_policy: dict) -> {conflict: bool,
                                                    previous_value: str|null}

stretch.conflict_detection == false:
  정책 갱신 파이프라인이 validate_before_apply를 호출하지 않고
  즉시 덮어씀 (기존 동작 그대로, 오버헤드 0)

stretch.conflict_detection == true:
  발화 파싱 → {material_type, destination} 추출
    → validate_before_apply() 호출
    → conflict=true: TTS "아까 OO을 XX로 지정하셨는데
      변경하시겠습니까?" → 음성 확인 후 적용
    → conflict=false: 기존과 동일하게 즉시 적용
```

### B — 오분류 지적 수용

```
STT/LangChain 발화 분류에 인텐트 필드 추가:
  utterance_intent ∈ {register_policy, query, correction, other}

correction 파싱 결과: {corrected_class: material_type 또는 destination}

내부 함수 (policy_node):
  apply_correction(last_processed_item, corrected_value) -> void
    - last_processed_item: state_machine이 마지막 처리 결과 1건만
      policy_node에 보관(세션 이력 불필요)
    - 갱신 경로는 register_policy와 동일 재사용

stretch.correction_learning == false:
  인텐트 파서 후보 목록에서 correction을 아예 제외
  (LangChain 프롬프트가 오히려 더 짧아짐 — 오버헤드 마이너스)
```

### C — 통 포화 감지

```
신규 서비스: /bin/check_capacity
  Req: bin_id   Resp: is_full(bool)

구현(권장 — 5일 내 확실히 가능): 비전 대신 **카운트 기반**.
  PLACE_TO_BIN 완료마다 통별 카운터 증가, config의
  bin_capacity.max_count 도달 시 포화 판정. 비전 불필요.

stretch.bin_capacity_monitor == false:
  카운터 증가는 비용이 거의 없어 항상 켜둬도 무방하나, 판정+TTS
  알림 로직만 게이팅 (카운터 자체는 로그용으로 계속 축적해도 무해)

포화 시: TTS 알림 → ASSIST_REQUEST(PHYSICAL 계열, 대상이 아이템이
아니라 통) → "비웠어" 음성 확인으로 카운터 리셋
```

### 1~3일차 (우선순위 명시)

**반드시**:
- 실물 4종(PET/캔/종이팩 2그룹/비닐) 확보 — 재활용품이라 즉시 가능
- `/robot/grip` Modbus 래퍼 여부 확인 — **1일차 최우선**(이후
  로봇제어 전체가 이것에 의존)
- 강사 사전 컨펌(3일차 중) — A-4 완화책, 늦으면 4일차 정식승인
  리스크에 그대로 노출됨
- 촬영·라벨링 1차분(YOLO 1차 학습이 돌아갈 최소량)

**가능하면(안 되면 5일차로)**:
- YOLO 1차 학습 완료(촬영만 끝내고 학습 자체는 5일차 아침도 무방)
- 힘 3축 측정(그리퍼+실물 필요 — 단 실물이 재활용품이라 v3의
  "조립체 확보 지연" 리스크보다 훨씬 낮음)
- 카메라 캘리브레이션

**밀려도 됨**:
- 종이팩 2그룹(coating visible/ambiguous)을 대표하는 정확한 실제
  제품 확정 — 1차로 대충 정하고 5~6일차에 보강 촬영하며 다듬기

====================================================================
 요청 6 — 반대 의견
====================================================================

**2절의 세 수정(종이팩 조건화, 방어논리 교체, 프레이밍 수정)에는
반박이 없습니다.** 오히려 종이팩 조건화(요청2)는 더 강한 근거를
찾아 보강했습니다.

**2-2절 방어논리("처리량")에 프레이밍 조건 하나만 덧붙입니다**:
이 논거는 "가정용"보다 **"공동주택 분리수거장"**처럼 배출량이
많은 시나리오로 프레이밍해야 설득력이 생깁니다. 다행히 5절의
소품 계획(부채꼴 통 배치 등)이 이미 이런 공용 배출장 이미지와
잘 맞으니, 발표에서 이 스케일을 명시적으로 설정할 것을 제안합니다.

**스트레치 A/B/C 순위에는 이견이 있습니다 — B를 1순위로 올릴
것을 제안합니다.**

문서의 A(규칙충돌감지) 1순위 논거("말을 알아듣는다→말이 앞뒤가
맞는지 본다")는 타당하지만, **심사위원 각인 효과는 B(오분류
지적 수용)가 더 즉각적**이라고 봅니다. A는 모순되는 두 발화를
순서대로 등록해야 효과가 보이는 2단계 시연이 필요해 다소 연출된
느낌을 줄 수 있는 반면, B는 "틀렸어" 한마디에 로봇이 바로
수정하는 게 한 번에 눈에 들어오고, **원문 배경의 "협동로봇의
변수 대응력 부족"에 더 직접적으로 답합니다.** [추론]

다만 문서가 이미 지적한 B의 리스크(과대 청구 — "학습"이 아니라
"규칙 덮어쓰기")는 그대로 유효하고 오히려 1순위로 올릴수록 더
철저히 관리해야 합니다. **제안: B를 1순위, A를 2순위로.**
