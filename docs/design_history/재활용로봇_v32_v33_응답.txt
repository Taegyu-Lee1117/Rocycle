### 1-2. [변경] obstacles 스키마를 평탄화했습니다

원안은 `bins:` 아래 통 5개를 중첩했는데, 로더 구현을 단순하게
하려고 통도 최상위에 개별 항목으로 뒀습니다:

```yaml
obstacles:
  belt: {xy_bounds: [...], z_floor: ..., note: ...}
  can_bin: null
  plastic_bin: null
  paper_bin: null
  battery_bin: null
  review_bin: null
  camera_mount: null
```

의미 차이는 없고 순수 구현 편의입니다. 원안대로 중첩을 원하시면
로더 쪽만 재귀 처리 추가하면 되니 말씀해 주시면 바꾸겠습니다.

### 1-3. 규칙을 z_min/z_max 둘이 아니라 z_floor 하나로 단순화

원안의 `z_min`(테이블면)/`z_max`(벨트면)는 실제로는 "z_max 아래로
못 내려간다"는 규칙 하나만 씁니다(문서에도 "z 하한 하나면
충분하다"고 쓰여 있었습니다). 그래서 코드에서는 `z_floor` 하나만
받고, `z_min`(테이블면 값)은 note 텍스트에만 남겼습니다 — 나중에
"바닥까지 내려가도 되는" 경우(예: 통 안에 물건을 놓는 PLACE
동작)가 생기면 그때 `z_min`을 별도 필드로 되살리면 됩니다. 지금
스코프(펜 마킹, end-to-end 측정)에는 불필요합니다.

### 1-4. 요청2 — 반대 의견 답변

**(1) obstacles가 실제로 가능한가 — 됩니다, 오늘 사고 좌표로
회귀 테스트까지 통과했습니다.** `test_regression_actual_collision_
case`가 정확히 오늘의 (444.14, -240.56, 294.69)를 넣어서 예외가
나는 것을 확인합니다. 최소 구현으로도 "이번 유형"의 사고는
분명히 막힙니다.

**(2) xy 사각형 근사가 충분한가 — [반론 없음, 의도적으로 보수적인
선택입니다.]** 통이 원형이면 사각형 근사가 통 모서리 바깥
영역까지 과도하게 막을 수 있는 건 맞습니다. 하지만:
- 이 체크는 **경로 계획이 아니라 최종 목표점 하나만** 검사합니다
  — 통 접근/배치는 어차피 티칭된 고정 자세(approach_pose/
  place_pose)로 가는 것이지 임의의 xy로 가는 게 아니라서, 사각형
  근사가 "정상 동작을 막는" 상황 자체가 잘 안 생깁니다.
- 반대로 사각형을 원에 내접시켜(더 타이트하게) 정의하면 실제
  통 모서리를 놓쳐 사고를 못 막는 경우가 생깁니다 — **과소
  추정보다 과대 추정이 안전 방향**이므로 사각형(외접) 근사를
  유지하는 게 맞다고 판단합니다.
- 5일 스코프 원칙(CLAUDE.md 설계원칙5, 원칙7)에도 맞습니다 —
  원형 근사(예: 중심+반지름)로 바꾸는 건 코드 몇 줄 차이지만,
  지금 얻는 이득이 없는데 복잡도만 늘립니다.

**(3) 최소 구현으로 실제 사고를 막을 수 있는가 — 대체로 막되,
한 가지 잔여 위험을 추가로 짚습니다.** 이 체크는 **최종 목표점만**
검사하고 **경로 중간**은 안 봅니다. 저희가 실제로 쓰는 접근
패턴(안전 높이로 이동 → 그 자리에서 수직으로 하강)에서는 중간
경로가 항상 목표점의 바로 위 수직선이라 문제가 없지만, 만약
나중에 **대각선으로 접근하는 코드**를 쓰게 되면 최종점은 안전해도
경로 중간에 구조물을 스칠 수 있습니다. **[제안]** 지금 스코프에선
과설계라 구현하지 않지만, 앞으로 새 이동 스크립트를 짤 때
"수직 접근만 쓴다"는 규칙을 지키는 것 자체가 이 최소 구현의
숨은 전제라는 걸 문서에 명시해 뒀습니다(설계문서 v29 2-5절
CLI 추가).

 2. v33 — end-to-end 측정 절차
====================================================================

### 2-1. 요청1 — 표적 방식 결정: **안 A**

웹 Claude 의견(안 A 우선)을 그대로 채택합니다. 이유를 하나 더
보탭니다: **표적 검출 로직을 새로 만들 필요가 없습니다.**
저희가 오늘 eye-to-hand 재검증에 쓴 체커보드(10x7, 25mm/칸)가
이미 "모눈종이 격자 교차점" 그 자체입니다 — `cv2.
findChessboardCorners` + `cornerSubPix`로 코너 픽셀을 정확히
뽑는 코드가 이미 있고, 오늘 두 개 코너로 실전 검증까지
끝났습니다. 새 표시를 그릴 필요도, 새 검출 로직을 짤 필요도
없이 **같은 체커보드를 벨트의 여러 위치(앞/중간/뒤 × 좌/중앙/
우)로 옮겨가며 그 안의 여러 코너를 표적으로 쓰면** 6~9지점을
채울 수 있습니다.

**팀에 필요한 준비물**: 없음 — 기존 체커보드 그대로 씁니다.

### 2-2. 요청2 — 검출 로직: 기존 코드 재사용

새로 구현할 게 없습니다. `cv2.findChessboardCorners(gray, (10,7))`
+ `cornerSubPix`로 서브픽셀 코너 좌표를 얻는 코드를 오늘 이미
스크래치패드에서 검증했으니, 이걸 정식 측정 스크립트로 정리만
하면 됩니다(로봇이 풀리면 진행).

### 2-3. 요청3 — 반대 의견 답변

**(1) "길게 물린다"가 순이득인가 — [부분 반론] 원리는 맞지만
추가 검증 단계를 제안합니다.** 4-3(a)의 계산(4cm·sin5°≈3.5mm)은
맞고, z 여유 이득도 실재합니다. 다만 **각도 오차의 원천이 로봇의
명령 정밀도가 아니라 "손으로 펜을 끼우는 정렬 오차"** — 이건
오늘 체커보드가 테이프로 헐겁게 고정됐다가 이 정밀도 문제
때문에 캘리브레이션이 통째로 실패했던 것과 **같은 종류의
리스크**입니다. **[제안] 요(yaw) 회전 이중 마킹 검증**: z 오프셋을
구한 뒤, 같은 지점에서 (a) 현재 자세로 한 번 찍고 (b) 그리퍼를
자기 축(rz)으로 90~180도 돌려서 같은 좌표로 다시 한 번 찍습니다.
펜 끝이 TCP z축과 정확히 일치하면 두 점이 겹치고, 안 맞으면
두 점이 어긋난 만큼(과 방향)이 정렬 오차입니다 — 이걸로 (i) 정렬이
충분한지 확인하고 (ii) 필요하면 두 점의 중점을 실제 목표 위치로
써서 1차 오차를 상쇄할 수 있습니다. 5분이면 되는 검증이라
비용 대비 가치가 있다고 판단합니다.

**(2) z 오프셋을 수동 티칭 대신 힘 센서 자동 접촉 감지로 — [반론]
"수동"의 의미를 다르게 제안합니다.** 원안의 "수동"은 티치펜던트
수동모드를 뜻하는데, 저희는 이번 세션에서 **"펜던트 수동모드는
ROS2 서비스를 불응답 상태로 만들고 비효율적"**이라는 걸 반복
경험해서 "펜던트 수동모드를 다시 쓰지 않는다"는 프로세스 규칙을
이미 세웠습니다(이번 3일차 대화 중 확정). 그래서 **ROS2 자동
제어를 유지한 채로 작은 상대이동(예: 1~2mm씩)으로 조심스럽게
하강하며 매 스텝 캡처로 확인하는 방식**을 쓰겠습니다 — 완전
자동(힘 센서 임계값 트리거)보다는 느리지만, 펜던트로 안 넘어가고
안전 확인도 병행되는 절충안입니다. 힘 센서 기반 완전 자동은
이 방식이 검증된 뒤에 도입 여부를 판단하겠습니다(첫 회는
신중하게 하라는 원안 취지와도 맞습니다).

**(3) 6~9지점이 충분한가 — [반론 없음, 동의합니다.]** 상수
오차/위치의존 오차/불규칙 오차 세 갈래를 구분하려면 이 정도
밀도가 필요하고, 남은 시간 대비 과하지 않습니다.

### 2-4. 13절 39번 갱신 완료

설계문서 v29에 아래처럼 갱신했습니다:
```
측정 방식: 안 A(체커보드 코너를 표적으로, 그리퍼에 펜을 물려
           바로 옆에 마킹) — 새 표적/검출 로직 불필요, 기존
           체커보드+코너검출 재사용
z 오프셋: ROS2 자동제어 유지, 소폭 상대이동으로 조심스럽게 하강
           (펜던트 수동모드 미사용)
정렬 검증: 요 회전 이중 마킹으로 펜 끝-TCP z축 정렬 확인(CLI 제안)
측정 지점: 6~9개(앞/중간/뒤 × 좌/중앙/우), 두 축(그리퍼 닫힘 축/
           핑거 길이 축) 구분 기록
순서: obstacles 골격(완료) → 책상에서 z 오프셋+정렬 검증 →
      벨트에서 6~9지점 측정
```
