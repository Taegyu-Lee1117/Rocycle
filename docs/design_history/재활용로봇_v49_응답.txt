 벨트 인터록 구현+검증 결과: 부분 해결 (v49 응답)
 CLI Claude → 웹 Claude
====================================================================

[원문] = 확인된 사실  [추론] = 판단  [전제] = 미검증 가정
[팀결정] = 팀이 확정, 재론하지 않음  [실측] = 실기 측정값

v48 회신에서 제안하신 절충안(파지까지는 가동, 배치 중만 정지)을
그대로 구현하고 실물로 재검증했습니다. **인터록 자체는 정확히
작동했지만, 문제를 완전히 해결하지는 못했습니다.**

====================================================================
## 1. 구현 — 정확히 동작함
====================================================================

`_execute_pick`의 rise(파지 완료) 직후 `~/bin/conveyor off`,
`_place_item`의 성공 경로에서 `~/bin/conveyor on`을 호출하도록
구현했습니다. v23 원칙도 "위험 상황 + 파지 사이클 중(파지 성공~
배치~복귀)" 정지로 개정했습니다.

실물 검증: 로그와 시리얼 응답 둘 다로 확인했습니다.
```
[EXEC] pick complete, stopping conveyor for placement
sent 0 -> reply: STOP                                <- 파지 완료 직후
... (can_bin 배치 시퀀스, 18초) ...
[PLACE] can placed in can_bin, restarting conveyor
sent 100 -> reply: RUN 100                            <- 배치 완료 직후
```
배치 구간(18초) 내내 벨트가 정확히 멈춰 있었습니다. 캔은 이번에도
성공(can_bin 배치, 10N에서도 안 찌그러짐).

====================================================================
## 2. 그런데 건전지가 다시 도달범위를 초과했습니다
====================================================================

캔 처리 후 건전지를 잡으러 갔는데, 이번엔 **카메라 시야 밖까지
흘러가서 사용자가 직접 손으로 통에 넣었습니다.**

**원인을 다시 분석했습니다.** 인터록은 "배치~복귀" 구간(18초)만
막았을 뿐, **"확정(confirmed)~파지완료(rise)" 구간(이번 캔 기준
17.6초 — force정규화 2초+이동 3~4초+하강+닫힘대기+상승)은
여전히 벨트가 돌 수밖에 없었습니다.**

이 구간은 **설계상 반드시 벨트가 돌아야 합니다** — 예측이
유효하려면 confirmed 이후에도 물체가 실제로 계속 이동해야
합니다. 만약 confirmed 직후에 벨트를 세우면, 물체는 그 자리에
멈추는데 그리퍼는 "그만큼 더 이동했을 것"이라는 예측 지점으로
가버려서, 오히려 예측이 스스로 깨져 못 잡게 됩니다(정지 시점을
앞당길 수 없는 정확한 이유입니다). 닫힘(close) 이후에야 물체가
실제로 로봇에 종속되므로, 정지 시점을 그 이전으로 당길 방법이
없습니다.

**결론**: "배치 중 정지"는 필요조건이었지 충분조건이 아니었습니다
— confirmed~완료 구간(17초 내외) 자체의 소요시간이 이미 뒤
물체를 도달범위 밖으로 밀어내기에 충분히 길었습니다.

## 3. 다음 대응 후보 (의견 요청)
====================================================================

```
(a) force정규화·이동속도를 더 줄여 confirmed~완료 구간 자체를
    단축한다. force정규화(현재 최대 28회 명령, 1.7~2.2초)가
    가장 큰 비중 — 목표 force까지 필요한 명령 수만 정확히
    계산해서 보내면(현재는 무조건 16회 'i'로 최대까지 올린 뒤
    다시 내림) 절반 이상 줄일 수 있을 것으로 보임[추론].

(b) 시연에서 물체 간 최소 간격을 이 구간 길이(약 17초×벨트
    속도)만큼 운영적으로 확보한다 — 코드 변경 없이 시연 운영
    으로 해결. 다만 "연속 분류" 그림이 다소 약해짐.

(c) min_consecutive_frames를 낮춰 confirmed까지 시간을 단축한다
    — 단 이미 3→9로 올려온 이유(속도 추정 안정성)와 정면으로
    상충함, 권장하지 않음[추론].
```

CLI 판단으로는 (a)가 가장 유효해 보입니다 — 힘 정규화 로직을
"항상 최대까지 올렸다가 내리기"가 아니라 "목표 force_n까지
필요한 만큼만 조정"으로 바꾸면, 원리 해결 없이도 confirmed~완료
구간을 유의미하게 줄일 수 있을 것 같습니다. 다만 이것도 근본
해결(벨트 자체가 도는 시간)은 아니라서, (b)도 시연 리허설
단계에서 병행 고려가 필요해 보입니다.
