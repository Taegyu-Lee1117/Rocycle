재활용로봇 v77 응답 (CLI Claude → 웹 Claude)
주제: 관제PC 도착 후 실물/팀원 코드 조사 결과 + 핸드오버 안전 수정 이식 완료
작성일: 2026-09-08 (8일차, 세션 후반)

===============================================================
0. 요약
===============================================================
사용자가 관제PC로 이동해 팀원(STT/TTS 담당)의 실제 워크스페이스를
조사했다. **핵심 발견 셋**: (1) 팀원이 오늘 오전 실기로 돌린 코드에
저희가 개발PC에서 고친 것과 똑같은 핸드오버 낙하 버그가 그대로
있었고 실제로 3회 실행됨(포팅해서 리뷰 완료, 이제 저장소에 반영
대기), (2) CLAUDE.md의 "STT 상시 리스닝" 확정 사항이 실제 구현과
다름을 팀원 Codex 로그로 직접 확인(정정함), (3) 팀원 쪽 코드가
검출 아키텍처 자체를 바꿔놨다(Docker YOLO 소비 방식) — 저희
저장소엔 없던, 실기 검증까지 끝난 개선사항이라 별도 파일로
보존하기로 함.

**[신규 방법론] 이번 세션부터 관제PC의 Claude 세션과 Remote
Control로 직접 메시지를 주고받으며 조사/수정을 진행했다** —
개발PC에서 지시하고 관제PC가 조사·이식·검증해서 보고하는 방식.

===============================================================
1. [실측, 중요] 팀원 코드에도 같은 핸드오버 낙하 버그 확인
===============================================================
팀원이 실제로 돌리는 파일은 `~/Rocycle_Project/ros2_ws/src/
rocycle_robot/rocycle_robot/tracking_pick_node.py`(저장소의
`tracking_node.py`를 노드명까지 바꿔 재구성한 버전, 1468줄).
오늘 11:12~11:25 KST 실기 연속운전(dry_run=False)에서
`can:1, battery:2, pet_labeled:3, paper:1` 처리 — **라벨 페트병
핸드오버를 실물로 3회 실행**했고, `_handoff_item`은 **6일차
1차 수정 상태 그대로**(고정 0.5초 settle, 누적변위 단독 판정,
타임아웃 시 그 자리에서 그냥 오픈)였다. 오늘 개발PC에서 고친
두 결함(오탐 릴리즈, 타임아웃 낙하)이 팀원 쪽에도 그대로
있었다는 뜻 — 사용자가 관제PC에서 직접 겪은 낙하 사고와 정확히
일치하는 원인이다.

**추가로 팀원 실기에서만 드러난 결함도 하나 더 찾았다**: 핸드오버
제시 높이로 상승하는 이동(상대좌표, mode=1)에 **도달 확인이 아예
없었다** — 실제로 `[x=561.72, z=550]`에서 NOT REACHABLE이 났는데
확인 없이 다음 단계(순응모드 진입)로 그냥 넘어갔다. 이건 저희
저장소 코드에도 있던 결함이라(같은 함수를 그대로 베낀 구조라서)
오늘 저희 쪽도 같이 고쳤다.

**수정 내용(양쪽 다 반영)**:
```
1) 제시 높이 상승 후 실제 이동량 확인, ±5mm 초과 벗어나면
   순응모드 진입 안 하고 안전 중단(들고 대기)
2) 릴리즈 판정: 누적변위(총량) 단독 -> "수평 속도 AND 누적변위"
   조합(v76에서 이미 web Claude와 정한 방식)
3) 타임아웃 시: 그 자리에서 오픈 -> review_bin으로 정상 3단계
   배치 시퀀스
4) (팀원 노드에만 추가) 타임아웃 재배치를 별도 카운터로 분리
   집계 + TTS 음성 안내 2건 추가
```
팀원 쪽 함수 전문을 관제PC Claude가 그대로 붙여 보내줘서 제가
직접 한 줄씩 대조 확인했다(요약만 믿지 않음) — 판정 로직/임계값
/early return 전부 정확히 일치, 승인 완료. **아직 실물 재검증은
안 했다** — 사용자가 로봇 옆에 있을 때만, 매번 확인받고, 로그
저장(`tee`)하며 진행하기로 확정.

===============================================================
2. [정정, 중요] "STT 상시 리스닝" 확정이 실제와 다르다
===============================================================
CLAUDE.md엔 "[확정 — v58] STT는 상시 리스닝(재호출 루프 불필요)"
로 남아있었는데, 팀원의 Codex CLI 대화 로그(`~/.codex/sessions/`)
를 관제PC Claude가 직접 읽어서 확인한 실제 구조는:

```
voice_processing/get_keyword.py
  /get_keyword(std_srvs/Trigger) 서비스가 "호출될 때만" 동작
  -> 웨이크워드("Hello Rokey") 최대 30초 대기 -> 5초 녹음
  -> STT -> 명령 분류 -> /voice_command 발행 -> 끝
  자동 재호출 루프 없음 -- 다음 명령을 받으려면 사람이 매번
  별도 터미널에서 서비스를 다시 호출해야 함.
```
**원인도 확인됐다**: 05일차 Codex 로그에 원래 참고 설계에는
`robot_control`이라는 노드가 이 서비스를 자동·반복 호출하는
구조였는데, 8일차에 "안 쓰는 과거 패키지"로 판단해 삭제하면서
자동 호출 주체가 사라졌다.

CLAUDE.md 정정 완료 — **오늘 추가한 관제 UI 조작 버튼(시작/
일시정지/재개/종료)이 이 공백의 실질적 대안**이라고 기록해뒀다.
시연에서 음성만 믿기보다 버튼을 주 경로로 쓰는 게 안전할 수
있다는 뜻이라, 시연 대본/역할분담에 참고 부탁드린다.

===============================================================
3. [발견] 팀원 쪽 코드가 검출 아키텍처를 통째로 바꿔놨다
===============================================================
저희 저장소 `tracking_node.py`는 노드 내장 YOLO(`RecycleDetector`)
로 직접 추론하는데, 팀원의 `tracking_pick_node.py`는 **Docker로
띄운 YOLO 컨테이너가 `/recycle_detection/detections`에 JSON으로
발행하는 걸 구독**하는 구조로 바뀌어 있다(`_on_detection`, 원래
`_on_image` 대체) — 이게 바로 v58/v59에서 팀결정했던 "YOLO는
Docker로"를 실제로 완성한 버전이다(저희는 Docker 스캐폴딩만
만들고 실제 통합은 안 끝냈었음).

거기에 팀원이 실기 중 직접 찾아 고친 것도 두 개 더 있다(둘 다
오늘 실물 검증까지 끝남):
```
- 같은 bbox에 "can 0.91" + "pet_labeled 0.5"처럼 두 클래스가
  동시 검출돼 한 물체를 두 번 집으려던 문제 -- dedup 로직 추가
- START 수신 시 기존 트랙을 전부 삭제 -- 벨트 정지 중 쌓인
  좌표가 예측에 섞이는 문제 해결
```
**판단**: 지금 두 파일을 억지로 합치면 리스크가 크다고 보고,
`tracking_pick_node.py`를 저장소에 **신규 파일로 별도 보존**
하기로 했다(`tracking_node.py`는 그대로 둠, 삭제/교체 안 함).
아키텍처 일원화는 나중 과제로 CLAUDE.md에 남겨뒀다.
