## 2. 로봇 연결 중 발견·수정한 버그 5건
====================================================================

### 2-1. Executor 재진입 (첫 실물 시도에서 즉시 발견)
구독 콜백 안에서 같은 노드의 `spin_until_future_complete`를
불러 "Executor is already spinning"으로 즉시 실패(로봇은 전혀
안 움직임, 안전). 로봇 제어 전용 Node+SingleThreadedExecutor를
분리해서 해결.

### 2-2. 그리퍼 미개방 후 파지 → 찌그러짐 사고
`_execute_pick`이 "닫기"만 하고 시작 전 "열기"를 명시하지 않아,
직전 사이클이 닫힌 채로 끝나면 그 상태로 하강해 물체를 눌러
찌그러뜨림(캔 1회 발생). **수정**: (1) 파지 시작 시 항상 먼저
명시적으로 연다, (2) 물체를 들고 있는 동안(`_holding=True`) 새
Pick 자체를 막는 가드 추가(상태머신 완성 전까지 임시 규칙).

### 2-3. 칼만필터가 확정 순간에만 1회 갱신되던 구조적 결함
처음엔 `update_x_detection()`을 pick_ready 순간에 딱 한 번만
불렀음 — 정지 물체는 문제없지만 벨트가 실제로 움직이면 데이터
포인트 하나로는 속도를 추정 못해 예측이 항상 "현재 위치"로만
나오는 결함(v44 최초 실패와 같은 함정을 다른 경로로 재현할
뻔함). **수정**: 같은 객체로 확인되는 한 매 프레임 갱신하고,
`min_consecutive_frames`는 "언제 확정할지"에만 쓰도록 역할 분리.

### 2-4. 힘 정규화 시간(~2초)이 예측에 미반영
그리퍼 열기(0.5s)+파지력 정규화(최대 28회 명령, 실측
1.7~2.2초)를 하는 동안 로봇은 아직 안 움직이는데, 이 시간이
예측 시간(이동+하강+닫힘)에 반영이 안 되고 있었음 — 예측 과소
(under-prediction)의 한 원인. **수정**: 목표 좌표를 힘 정규화가
끝난 직후 "지금" 기준으로 재계산(칼만필터 마지막 갱신 시각부터
그 시점까지 흐른 실제 시간을 예측 시간에 더함).

### 2-5. `MoveLine`이 도달 불가 좌표에서 "성공 응답, 실제 미동작"
안전 검증(`get_current_posx` 비교)이 실패를 정확히 감지하고
중단하도록 이미 되어 있었음 — 이번에 `get_last_alarm`으로
`[ERR] Pose(...) is NOT REACHABLE`이 명시적으로 찍힌 사례를
처음 확인(4절 참고). 그리퍼는 안 열림, 안전.

## 3. 벨트 위 파지 실물 시행 결과 — 정지 1건, 이동 다수
====================================================================

### 3-1. 정지 물체(캔) — 첫 완전 자동 파지, 성공
YOLO 검출→확정→예측→힘정규화→호버 이동→하강→파지→상승까지
사람 개입 없이 전부 성공(사진 확인).

### 3-2. 이동 물체 — 시행착오 경위 (모두 캔/건전지, 요청대로
페트병은 stick-slip 이슈로 배제하고 진행)

```
1차(min_consec=3, 캔): 실패 — 예측 과대(캔 뒤쪽/트레일링 엣지를
  잡아 밀려 떨어짐). 관측 구간(~2초) 너무 짧아 속도 추정 잡음.
2차(min_consec=5, 캔): 실패 — 예측 과소(하단부만 걸림).
  원인은 2-4번 버그(힘정규화 시간 미반영).
2-4번 버그 수정 후 재시도(캔): 성공, 거의 중앙 파지.
상태머신 연결 후 재시도(캔): 성공, can_bin까지 배치 완료.
```

**건전지는 훨씬 어려웠습니다** (허용오차 반지름 7mm로 좁음):
```
1차(min_consec=5): 완전 실패, 못 건드림.
2차(min_consec=7): 부분 개선(하부만 건드림), 여전히 실패.
3차(min_consec=9 + 건전지 전용 prediction_bias_mm=5.0): 성공,
  battery_bin 배치 확인.
```

**[사용자 관찰, 중요]** 벨트 진동이 있고, 속이 비어있는 가벼운
물체(페트병/캔/건전지)가 함께 흔들리는 현상이 육안 관측됨 —
짧은 관측 구간에서 칼만필터 속도 추정이 크게 진동하는 현상의
물리적 원인일 가능성이 높다고 판단[추론].

**[정정 — 과대청구 금지]** 처음엔 "물체가 아직 가속 중이라 속도를
낮게 본다"는 가설을 세웠으나, 실측 `vx` 로그(성공/실패 사례 모두
꾸준한 증가가 아니라 노이즈성 진동)로 기각[사용자 지적, 타당함].
벨트 자체는 스테퍼 구동이라 가속도가 거의 0이라는 사실과도
일치. **정정된 진단**: 짧은 관측 구간 + 검출 픽셀 노이즈(벨트
진동이 원인 후보)로 순간 속도 추정 자체가 불안정한 것.

`prediction_bias_mm`(건전지 전용, +5mm)은 **원인 해결이 아니라
국소 완화책**입니다 — can/paper 등 이미 버그 수정만으로 성공한
품목엔 적용 안 함(전역 적용 시 반대 방향 실패 유발 위험).

## 4. [신규, 중요] 순차 2물체 처리에서 발견한 도달범위 문제
====================================================================

캔→건전지 순서로 벨트에 올려 순차 처리 테스트:
- 캔: 검출→파지→can_bin 배치까지 완전 성공.
- 건전지: 실패. `get_last_alarm`에 `[ERR] Pose(608.69mm,
  -264.00mm, 430.00mm, 179.78°, 176.40°, 89.78°) is NOT
  REACHABLE`이 명시적으로 찍힘.

**근본 원인**: 캔 처리(검출~배치, 약 24초)가 진행되는 동안
**벨트를 멈추지 않아서** 건전지가 그 사이 계속 흘러감 — 첫 검출
시점 이미 x=521.9mm였고, 확정까지 기다리는 동안 x=563.4까지
더 밀렸으며, 예측 시간(8초)까지 더해지자 목표 x=608.69로
4일차에 이미 알려진 "x>590mm는 표준 자세로 도달 불가" 구간에
들어감. 안전장치가 정확히 작동해 로봇은 그리퍼를 열지 않고
안전하게 중단(위험 없음, 건전지를 못 집었을 뿐).

**[팀결정 — 6일차] "연속 파지가 원리적으로 안 된다"는 결론은
아닙니다** — 원인이 도달범위 초과로 특정됐으므로, 다음 중 하나로
해결 가능해 보입니다:
```
(a) 물체 처리 중 벨트 일시정지(하드웨어 인터록)
(b) 확정을 더 서두르거나(상황별 min_consecutive_frames 동적 조정)
(c) 도달 가능 구간(x≤590mm 근처) 안에서만 확정하도록 게이팅 추가
```
오늘은 원인 확인까지만 완료, 대응 구현은 미착수.

## 5. [미해결] can_bin 배치 중 이상 동작 1건 (원인 미확정)
====================================================================

앞선 별도 시행에서, 캔을 파지한 뒤 can_bin으로 이동하는 도중
**그 자리에서 그리퍼를 열고 상승**하는 이상 동작이 1회 관측됨
(사용자 관찰). 당시 `get_last_alarm`에 특이점 관련 정보성 알람
(`Change singularity region status(Inside -> Outside)`, level=1)
이 찍혀 있었음 — can_bin이 ry=166으로 크게 기울어진 자세라
경로 중 특이점 영역을 지났을 가능성이 있으나, **코드 로직상
"그 자리에서 열기"에 해당하는 경로가 없어 정확한 원인은 특정
못함**. 이후 같은 조건(캔→can_bin) 재시행에서는 문제없이
성공(3-2절, 4절 참고) — 재현 안 됨, 1회성 현상으로 잠정 처리하되
원인 불명 상태로 남김.

## 6. 다중 물체 동시 존재 시 처리 순서 문제
====================================================================

페트병(시작점 근처)+건전지(더 진행된 위치)를 동시에 벨트에
올렸을 때, 진행방향상 건전지가 먼저 처리돼야 할 것 같은데도
페트병만 계속 처리됨 — 90초 시행 로그에 건전지 관련 라인이
단 한 줄도 없음(사용자 지적으로 발견).

**원인**: `RecycleDetector.detect()`가 `max_det=1`이라 프레임당
최고-신뢰도 물체 하나만 반환(README의 원래 전제 — "한 번에
물체 하나만 투입"). 페트병 conf(0.94~0.97)가 건전지
(0.87~0.90)보다 매 프레임 높아서 건전지는 시스템에 존재 자체가
안 잡힘. **버그가 아니라 설계 범위 밖 시나리오**입니다 — 다중
물체 동시 처리를 지원하려면 `max_det`를 늘리고 벨트 진행방향(X)
기준 우선순위 로직을 새로 추가해야 함.

## 7. [팀결정, 중요] 페트병은 전부 라벨 있음으로 취급
====================================================================

무라벨 페트병이 `pet_labeled`로 고신뢰도(0.94) 오분류되는 문제가
재현성 있게 계속 확인됨(v47에서 이미 보고, 오늘 벨트 테스트에서
재확인). **[팀결정] `pet_unlabeled`는 코드상으로만 존재하고
실사용에서는 모든 페트병을 `pet_labeled`로 취급합니다** — 라벨
있는 페트병을 새로 촬영·라벨링·재학습할 시간이 없기 때문입니다.

**따라서 페트병은 항상 사람 핸드오버 경로로 갑니다.** 현재
`_place_item()`의 `human_handoff` 처리는 실제 순응제어
핸드오버가 아니라 placeholder(벨트 상공에서 그냥 내려놓기)이며,
**오늘 중 실제 핸드오버(사람이 직접 받는 것)까지 구현이
목표입니다** — 안전 절에 이미 설계된 검증 기준(저강성 500+당김
방향+10회 연속 SAFE_OFF 0회)이 있으나 시간을 보고 결정할 예정.
아직 미착수.

## 9. 요청
====================================================================

### 요청 1 — 반대 의견

```
- 3절 진단 정정(가속 구간 → 검출 노이즈)이 타당한가
- 4절 순차처리 도달범위 문제의 대응 방향(a/b/c) 중 선호가 있는가
- 5절 특이점 의심 사고를 원인 불명인 채로 넘어가도 되는가,
  아니면 재현 시도를 더 해야 하는가
```

### 요청 2 — 설계 문서 반영

```
a) 7절 pet_unlabeled 사실상 폐기 결정을 설계 문서에 반영
b) 4절 순차처리 도달범위 문제를 설계 문서 오차예산/알려진
   한계 절에 추가
c) 6절 다중 물체 동시 처리 미지원을 명시적 제약사항으로 기록
```

### 요청 3 — 다음 순서 확인

지금 계획은:
```
1. 무게측정 + review_bin 라우팅 구현
2. 라벨 페트병 실제 순응제어 핸드오버 구현
3. 위 둘로 "움직이는 물체 파지 테스트 1차" 마무리
```
이 순서로 진행해도 괜찮을지, 혹은 4절(도달범위) 문제를 먼저
막고 가는 게 나을지 의견 요청합니다.
