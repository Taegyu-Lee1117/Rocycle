===============================================================
0. [정정, 중요] snapshot 폴링 실패 — 내 진단이 틀렸다
===============================================================
v77/v78에서 "개발PC 자원 소진(TCP TIME_WAIT 급증) 때문에
`net::ERR_EMPTY_RESPONSE`가 났고, 관제PC(자원 정상)에서는 curl로
확인해보니 재현 안 됐다"고 보고했는데 — **이 결론이 틀렸다.**

관제PC Claude가 실제 원인을 찾았다: `web_ui/index.html`에서
`encodeURIComponent(VIDEO_TOPIC)`을 그대로 썼는데, 이게
`"/image_raw"`를 `"%2Fimage_raw"`로 바꾼다. `web_video_server`가
`%2F`를 디코딩하지 않아 그런 이름의 토픽을 못 찾고, 404도 아니라
**응답 본문 없이 연결을 끊어버린다**(브라우저에는 정확히
`net::ERR_EMPTY_RESPONSE`로 보임) — **자원 상태와 무관한 순수
코드 버그**였다.

**내가 관제PC에서 curl로 "확인"했던 게 왜 통과했는가**: curl
명령을 손으로 칠 때 `topic=/image_raw`(인코딩 안 된 형태)로
쳤기 때문에 우연히 정상 응답을 받았을 뿐이다. 실제 브라우저의
`Image()` 객체는 코드 그대로 `encodeURIComponent`를 거쳐
`%2Fimage_raw`로 요청을 보내고 있었고, 이 차이를 못 잡았다.
**"curl로 재현 안 됨 = 실제로 정상"이 아니라, "내가 실제
코드와 다른 요청을 보내서 확인했다"였다는 뜻 — 검증 방법 자체가
실제 코드 경로를 그대로 재현하지 않으면 결론이 틀릴 수 있다는
교훈으로 남긴다.**

**[완료] 수정 + push**: `encodeURIComponent` 대신, 실제로 쿼리
문자열 구조를 깰 수 있는 문자(`& = # % 공백`)만 이스케이프하고
`/`는 그대로 두는 `encodeTopicForQuery()`로 교체(`621092c`).
ROS 토픽명이 `[A-Za-z0-9_/]`만 쓰는 걸 감안하면 사실 인코딩
자체가 불필요하지만, `video_topic`이 URL 쿼리로 사용자 입력
가능한 값이라 방어적으로 최소한의 이스케이프는 유지했다.
`web_ui/README.md`에도 정정 이력을 남겼다(틀렸던 진단을 지우지
않고 왜 틀렸는지까지 기록 — 문서 규칙 준수).

**재검증 대기 중**: 관제PC에 pull + C270/리얼센스 둘 다(`video_
topic` 쿼리 파라미터로 전환) 헤드리스로 확인 요청해뒀다. 확인되면
web_ui 쪽 미해결 항목이 사실상 다 정리되는 셈이다.
