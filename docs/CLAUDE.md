# ROKEY-Team-Project — 작업 원칙

이 파일은 매 세션 자동으로 다시 로드된다. 대화 내용은 세션 종료
또는 컴팩션 시 사라지므로, 매번 반복 적용되어야 하는 원칙과 현재
유효한 값만 여기 둔다(v46 정리, 936줄→분리). **상세 실측 데이터와
경위, 무효화된 결정의 이력은 `실측기록.md` 참고.** 상세 설계는
설계 문서(저장소 루트의 `재활용로봇_설계문서_v32.txt`, 버전 번호가
더 높은 파일이 최신)를 참고할 것.

## 하드웨어 전제 (현재 구성)

- 로봇: 두산 M0609, eye-in-hand RealSense(TCP에 그리퍼와 함께
  장착). 홈 자세: J3=90°, J5=90°.
- 고정 카메라(eye-to-hand): **Logitech C270**(RGB만, 720p MJPEG
  30fps 필수 — YUYV는 7.5fps로 제한됨). **[실측 — 8일차, 위반
  발견] `v4l2_camera` 0.7.1이 MJPG 디코딩을 못 해 YUYV(7.5fps)로
  우회한 게 `readme2.md`에 정식 절차로 굳어져, 8일차 오전 실기
  전체(핸드오버 3회 포함)가 7.5fps로 돌았다 — "필수" 요구사항
  위반 상태였음. `usb_cam`(mjpeg2rgb)으로 30fps 전환 자체는 실측
  검증 완료(29.84Hz, GPU 15%). **[팀결정 — v83 회신] 그러나 즉시
  전환하지 않는다** — fps를 올리면 확정까지의 관측 시간이 줄어
  속도 추정이 나빠지므로(`_min_consecutive_frames`를 비례 조정
  하지 않으면 오히려 악화) 근거 없이 규정만 맞추는 건 무의미.
  **당분간 7.5fps 유지, 예측 오차를 실측한 뒤 30fps 전환 여부를
  결정한다**(다음 세션 순서 참고) — "몰라서 위반"이 아니라
  "측정해서 결정"으로 남긴다(과대 청구 금지/설명 가능성 원칙).
  캘리브레이션 완료:
  `fx=1427.5, fy=1429.8, cx=674.3, cy=359.2`, 왜곡계수(plumb_bob)
  `[0.0838,-0.0067,-0.0059,0.0080,0]`. depth 없어 평면교차가
  유일한 3D 산출 경로 — `belt_correction.py`로 벨트 평면 경험적
  보정 적용(RMS 4.5mm, 최대 8.6mm).
- 그리퍼: OnRobot RG2, 개폐폭 0~110mm, 파지력 3~40N(0.1N 단위).
  제어: `onrobot_rg_control`의 `OnRobotRGControllerServer` —
  `/onrobot/sendCommand`(`SetCommand`: `'o'`/`'c'`/`'i'`(+2.5N)/
  `'d'`(-2.5N)/숫자문자열(목표폭mm)), `/onrobot/pose`, 상태
  `/onrobot_joint_states`(리맵 필요, 아래 함정 참고).
- **pymodbus는 3.10 미만 필수**(`pip install --break-system-packages
  "pymodbus<3.10"`) — 3.10+는 `slave`→`device_id` 이름 변경으로
  `onrobot_rg_control`/corecode와 비호환.
- 컨베이어: 스테퍼+Microstep Driver(PUL/DIR, ENA는 절대 건드리지
  않음). 시리얼 9600 baud, `"<steps_per_sec>\n"`(직접 정의한
  프로토콜). 100 steps/sec 고정 사용. **[정정 — 9일차 저녁]
  "=2.0cm/s"는 틀렸다 — 발표에서 이 값을 말하지 말 것.**
  현재 확인된 값: **벨트 표면 약 5.0mm/s(스톱워치 실측),
  물체(비전) 약 2.9mm/s(3회 일관)** — 둘의 42% 차이 원인과
  2일차 값이 왜 4배 틀렸는지는 둘 다 미확정, 시연 이후 조사
  (경위는 실측기록.md 9일차 저녁분 참고). 탈조 없음은 여전히
  유효. 수동 제어: `~/bin/conveyor {on|off|rev|<steps_per_sec>}`
  (진단용 헬퍼, `conveyor_node` ROS2 구현체 아님 — 워치독 미구현).
- PC 구성 목표: 관제 PC(**GPU 탑재로 지정** — C270+YOLO12s 추론+
  컨베이어 제어) / 로봇 PC(RealSense+팔+그리퍼+음성+상태머신).
  **[현재 상태] 물리적으로 PC 1대뿐, 이 PC는 GPU 없음**(Intel
  UHD 620 내장그래픽만) — 2대 분리는 미집행, YOLO도 당장은 이
  CPU 전용 PC에서 진행.
- 분리수거 통 5개(로봇 양옆 배치): `paper_bin`/`plastic_bin`/
  `can_bin`/`battery_bin`/`review_bin`. 좌표: `config/
  bin_teach_points.py`. `review_bin`("확인 필요" 물리 라벨)은
  재질별(4통)과 처리상태별(1통) 분류가 섞인 의도된 비대칭 구성—
  재론하지 않음. 벨트 끝 일반쓰레기통은 미검출/미학습 물체 전용.
- **[정정 — 9일차] 클래스 6개(v6 모델 기준)**: `battery`(AA),
  `can`(무게측정 대상), `paper`(초코 종이상자 — "우유팩" 아님),
  `pet_labeled`, `plastic`(신규 — 페트병 형태가 아닌 뚜껑/용기류,
  무게측정 없이 바로 plastic_bin행), `plastic_bag`(묶인 것만,
  무게측정 없이 바로 review_bin행). **`pet_unlabeled`는 9일차에
  의도적으로 삭제됨**(오분류가 너무 많아 라벨/무라벨을 모두
  학습시킬 여유가 없었음, 사용자 확인) — 무라벨 페트병은 이제
  검출 자체가 안 되고 흘려보내짐(시연 물체는 라벨 있는 것만).
  **[팀결정 — v47, 배경] 클래스명은 항상 YOLO 모델 쪽에 문서·
  config를 맞춘다**(모델은 재학습 비용이 크고 쉽게 못 바꾸므로)
  — 이번 `pet_unlabeled`→삭제/`plastic`추가도 같은 원칙의 연장.
  **DB 규격 v2에 `pet_bottle_*`/`pet_unlabeled` 이름이 전달됐다면
  최신 클래스 목록으로 갱신 필요 — 팀 통해 DB 담당자에게 전달
  필요(미완, v47부터 이어지는 미완 항목).**
- 백업 경로: `/media/rokey/UBUNTU 24_0/재활용/backup` — USB
  상시 연결. 설계문서는 최신판(v32)만 로컬에 두고 이전 버전은
  이 경로로 이관(완료). USB는 vfat — 심볼릭 링크/실행권한/특수
  문자 파일명 불가, 유일한 사본으로 두지 말 것(GitHub+클라우드
  병행).

(전체 설정: `config/gripper_profiles.yaml`, `grasp_fail_joint_rad`는
`config/gripper_profiles.yaml` 별도 필드 — 아래 "알려진 함정"
`null`=40N 항목 참고)
`plastic` 추가 실측값: `prediction_bias_mm=+20.0`(**정정 — 9일차
저녁, 원래 40이었으나 깊이(108→115mm) 변경과 동시에 정해져
어느 쪽 효과인지 못 갈랐던 값. 깊이 확정 후 분리 재검증 —
41~43mm 이동량 중 40mm가 보정값이고 실제 예측 기여는 1~3mm뿐
(뚜껑 속도 0.2~0.35mm/s라 8초 앞을 봐도 미미), 40은 뚜껑
지름(~90mm) 대비 중심이 아니라 가장자리를 집는 과한 값이었음
— 20으로 낮춰 재시험, 실물 성공 확인**),
`grasp_fail_joint_rad=null`(찌그러진 뚜껑을 테두리로 물 때와
지름으로 물 때 관절각이 0.78rad 벌어져 판정 불가 — 원리적으로
plastic_bag과 같은 상황, "뚜껑은 여유가 커서 판정이 쉽다"던
이전 CLI 판단은 **온전한 뚜껑에서만 맞고 찌그러지면 틀림**,
정정).

- 이동/하강 속도(채택값): 수평 vel=120/acc=40(HOME↔벨트 3.410s),
  수직 vel=100/acc=40(100mm 하강 2.194s). `config/motion_timing.yaml`.
- 사이클 시간(참고용 하한, 검출/좌표계산 시간 미포함): **20.8초**
  (품목 1개, 벨트→통→벨트 왕복).
- 좌표 정확도: `belt_correction` 적용 후 RMS 4.5mm, 최대 8.6mm
  (x=312.9 지점 재검증 필요 — 국소 이상치 의심, 미해결).
- 관절 가동 범위(물리 한계보다 좁게 설정): J2 ±95°, J3 ±135°,
  J5 ±135°. J1/J4/J6 제한 없음.
- TCP 힘 한계 160N(일반 모드). SAFE_OFF 원인은 확정 못함(원인
  규명 시도 종료) — 검증 기준으로 대체: 저강성(500)+당김 방향+
  핸드오버 자세+라벨 페트병으로 10회 연속 SAFE_OFF 0회.

## 알려진 함정

- **[팀결정 — v83 회신] 임시 우회를 문서에 남길 때는 반드시
  다음 세 가지를 함께 적을 것: (1) 무엇을 우회했는가, (2) 원래
  요구사항이 무엇인가, (3) 언제 재검토해야 하는가.** [실측 —
  8일차] `v4l2_camera`가 MJPG를 못 다뤄 급하게 YUYV(7.5fps)로
  우회한 게 `readme2.md`에 그냥 "터미널1 실행 명령"으로만 적히면서
  정식 절차로 굳었다 — CLAUDE.md의 "C270 30fps 필수"와 대놓고
  모순인 채 8일 동안 아무도 재검토하지 않았다(그 상태로 실기
  운전 전체가 돌았음). 위 세 가지가 없으면 우회가 요구사항을
  조용히 대체해버린다.
- **`pip install -r team_share_yolo12s/requirements.txt`가 `numpy`를
  2.x로 올려 `cv_bridge`를 깨뜨린다**(cv_bridge는 numpy 1.x 기준
  컴파일됨) — `ultralytics`가 최신 `opencv-python`을 끌어오는데
  그게 `numpy>=2`를 요구하는 게 원인. **해결: pip `opencv-python`
  패키지를 제거하고 시스템 `python3-opencv`(4.6.0, apt) +
  `numpy<2`를 쓸 것** — ultralytics 동작엔 지장 없음(실측 확인).
  재설치할 일이 있으면 이 순서를 반복할 것.
- 그리퍼 `'c'`(닫기)는 **비동기** — 반환돼도 물리 동작 안 끝남.
  닫기 후 품목별 `close_wait_sec` 그대로 대기할 것(위 표 참고).
  **[실측 — 9일차 저녁] 이 원칙이 실제로 유용했던 사례**:
  `_call_gripper`의 서비스응답 대기(`timeout_sec`)가 60회 중
  4회 8초를 꽉 채움(원인 미상[불명] — Modbus 폴링 지연/응답
  유실 추정) — 무정지 상태에서 그동안 물체가 약 23mm 끌림
  (인터록 하에서는 벨트가 서 있어 안 드러났던 문제, 백로그
  버그와 같은 유형). **8.0→2.0초로 하향 적용**(관제PC 제안,
  CLI 승인) — `close_wait_sec` sleep이 응답 타이밍과 무관하게
  물리적 완료를 보장하므로 타임아웃 값을 줄여도 파지 완료
  보장에는 영향 없음(위 원칙의 직접 근거), 4회 전부 결국 파지
  성공했다는 것도 "명령은 실행됐고 응답만 지연"을 뒷받침. 근본
  원인(응답 지연 자체) 조사는 시연 이후 과제.
- **파지력은 세션 내내 유지되고 자동 리셋 안 됨.** 매 파지 직전
  `gripper_profiles.yaml` 값을 명시적으로 설정할 것 — 이전 값을
  가정하지 말 것.
- **[실측 — 9일차 저녁] `gripper_profiles.yaml`에서 `force_n: null`
  은 "설정 안 함"이 아니라 "기본값 40N 적용"이다.** v5 시절
  `pet_unlabeled`(뚜껑)의 `force_n`이 null이라 기본 40N이 걸려
  **뚜껑이 실제로 찌그러졌다**(사고로 발견). 새 품목 추가 시
  null을 "안전하게 약하게"로 착각하지 말 것 — 힘이 걱정되면
  명시적으로 낮은 값을 넣을 것.
- **[실측 — 9일차 저녁, 3회 재발] `colcon build`는 워크스페이스
  루트에서 실행할 것, 패키지 디렉터리 안에서 하면 안 됨** —
  `install/`이 심볼릭 링크가 아니라 복사본이라 반영이 안 되고,
  패키지 디렉터리 안에서 빌드하면 조용히 설치본이 안 갱신된
  채로 노드가 뜬다(검증이 실제 실행경로를 재현하는지 확인하라는
  원칙의 또 다른 사례). **기록해도 같은 날 세 번 재발함** —
  관제PC가 "빌드 후 설치본 값을 매번 출력해 확인"을 습관화
  하기로 함(단순 기억이 아니라 매 빌드 뒤 확인 단계를 고정할 것).
- **[실측 — 9일차 저녁] 파지 사이클 진행 여부는 `/ui/state`의
  `stage`로 확인할 것, 로그의 "holding" 문자열로 판단하지 말 것**
  — 그 라인은 파지 중에는 안 찍혀서, 로그만 보고 "안 잡고 있다"고
  오판해 파지 사이클 도중 노드를 내린 사고가 있었다.
- **[실측 — 9일차 저녁] 파지 실패(명시적 `False`) 시 그리퍼를
  열지 말 것.** 판정 자체가 틀릴 수 있는데(교차클래스 오분류로
  엉뚱한 임계값 적용) 열어버리면 실제로 들고 있던 물체를 그
  자리에 떨어뜨린다(종이박스로 실측 재현). 실패 시엔 그냥 들고
  복귀만 하고, 다음 파지 직전의 기존 개방 동작에 맡길 것.
- `MoveLine`은 시작·끝점이 각각 도달 가능해도 그 사이 직선 경로가
  관절 한계에 걸리면 **`success=True`를 반환하면서 안 움직인다.**
  `get_current_posx()`로 실제 이동 여부를 항상 확인할 것. 자세가
  크게 바뀌는 이동은 중간 경유점으로 나눌 것.
- 통 PLACE(낮은 z)에서 상승 없이 바로 다음 지점으로 이동 금지 —
  반드시 "수직 상승 → 수평 이동 → 수직 하강" 3단계 시퀀스.
- 재시도 시 하강량은 항상 **호버 기준 절대값**으로 계산 — 이전
  실패 시도에 상대적으로 값을 더하지 말 것.
- 도달 불가 지점에서 자세 스캔 시 `ry`뿐 아니라 **`rz`도 함께**

  넘는다 — 기준점을 한 번 잡고 "누적 변위(총량)"만 재는 구조인
  한 settle을 아무리 정교히 해도 이 문제가 남는다.

  당기는 동작(빠름, 추정 20~50mm/s)과 중력 처짐/크리프(느림,

  3D 변위가 `release_threshold_mm`=10mm 이상, 미세 흔들림 배제용
  하한선으로 유지) — `_handoff_item` 참고. 이 방식은 적응형
  settle 자체를 불필요하게 만들어 제거했다(속도 게이팅이 스스로
  느린 크리프를 걸러내므로). [전제, 미검증] `pull_speed_mm_per_s`
  =15.0은 실측값과 추정 상한 사이 중간값 — 로봇 실물로 처짐/당김
  두 조건의 속도 분포를 재본 뒤 조정할 것(매 폴링 상세 로그를
  남기도록 함). 다음 순서 참고.
- **예측 시간 관리 원칙(`extra_gap`).** [실측 — 6일차, 무게측정
  baseline 타이밍 버그] `predict_ahead_sec()`로 계산한 예측 시간에

  잡거나 완전히 놓친다(실측 재현: baseline 무게 평균측정을 예측
  계산 이후에 배치했다가 extra_gap=6.5초, total_ahead=13.4초까지

  옮겨 수정). 현재 `extra_gap`에 포함되는 동작: 그리퍼 열기, 힘
  정규화, baseline 무게 측정(weight_check 품목만) — 이후 새 동작을
  추가할 때 이 목록도 함께 갱신할 것.

## 설계 원칙 (위반 시 즉시 지적할 것)

1. **크기로 클래스를 구분하지 않는다.** eye-in-hand top-down에서
   픽셀 크기는 카메라-대상 거리에 의존적이며, RealSense depth
   오차(±1~2mm)로는 보정 불가. 실루엣 1순위, 색상 2순위.
2. **OCR에 의존하지 않는다.** 텍스트 판독이 필요하면 DB 조회로
   우회한다.
3. **외부화 원칙.** 클래스 이름과 물리 수치는 코드에 하드코딩하지
   않고 YAML로 분리한다. 판정 로직에 품목명에 대한 분기를 두지
   않는다 — `clarification_rules[material_type].trigger`처럼
   설정을 조회해서 동작해야 한다.
4. **페이로드 6kg 제약** 내에서 대상을 선정한다.
5. **재현성 우선.** 기능 추가 여부는 "5일 안에 10회 시연해서
   10회 성공 가능한가"로 판단한다.
6. **과대 청구 금지.** 구현한 것 이상으로 표현하지 않는다.
   예: 규칙 덮어쓰기를 "학습"이라 부르지 않는다.
7. **판정을 바꾸는가를 먼저 묻는다.** 새 기능을 검토할 때
   "구현 가능한가"보다 "이 기능이 판정이나 동작을 실제로
   바꾸는가"를 먼저 확인한다. 판정 결과가 같다면 구현
   난이도와 무관하게 제외 대상이다.

## 문서 작성 규칙

- [원문]/[추론]/[전제] 구분 표기를 항상 유지한다.

  캘리브레이션 단위테스트(임의 값으로 통과시켰다가 실측 157mm
  오차)에서도 있었다** — 두 번째 재발. "테스트가 통과한다"와

  항상 확인할 것. **[팀결정 — v103 회신, 세 번째 재발 후 절차화]

  노이즈"로 오진단, 8일차 재검증으로 철회). **기록해두는 것만
  으론 재발을 못 막는다는 뜻 — 실측 계획을 세울 때 "이 측정이
  실제 실행 경로의 어느 조건을 재현하고 어느 조건을 재현하지
  않는가"를 사전에 명시적으로 적을 것**(사후 점검이 아니라
  계획 단계의 필수 항목으로). **[팀결정 — v110 회신, 네 번째
  재발 후 착수 조건으로 격상] 8일차에만 네 번째** — 관제PC
  헤드리스 검증이 1600×900으로 이뤄졌는데 실모니터는 1920×1080
  이었다(위 UI 항목 참고). 이번엔 "재현 안 한 조건으로 오판"을
  넘어 **"존재하지 않는 문제를 고치느라 시간을 썼다"**(손목캠/

  ```
  실측·검증을 시작하기 전에 한 줄로 적을 것:
    이 측정의 조건이 실제 운용 조건과 같은가?
    다르다면 어디가 다른가?
  ```
  사후 점검이 아니라 **착수 조건**으로 두면 네 번째 유형이 다시
  안 나온다는 게 팀 판단.

  이다** — 하나는 "검증이 실제 실행 경로를 재현하는가"(입력 쪽
  오류), 다른 하나는 "이 관측값이 측정/판정 메커니즘 자체가

  준다"를 위험 추세로 오독**(CLI 본인이 이 실수를 함) — 릴리즈
  조건이 "변위≥임계값을 넘는 순간 멈춘다"인 이상 관측값은
  정의상 항상 임계값 바로 위에서 잡히므로, 이 지표로 임계값을
  계속 낮추면 끝없이 내려간다(v96에서 overshoot에 적용했던
  같은 원리를 이번엔 "여유% 추세"에 적용 못 함 — 원리를 안다고
  매번 알아채는 게 아니라는 뜻). **두 규칙을 함께 기억할 것**:
  실측 계획 시작 전 "조건이 같은가"뿐 아니라 "이 관측이 메커니즘
  자체의 산물은 아닌가"도 같이 물을 것.

## 안전

- 힘 임계값은 스쿠핑 프로젝트 값(±20N)을 그대로 쓰지 않는다.
  구조(감지→즉시 해제→HOLD)만 재사용하고 수치는 실측한다.
- 안정화 확인(투입 감지, PICK 직전 재확인)은 보조 수단이며,
  최종 안전망은 힘 하드리밋(HOLD)이다.
- 순응 핸드오버는 힘 기반보다 **위치(TCP 변위) 기반 감지**를
  우선한다 — 관절 엔코더가 힘 센서보다 정밀하고 한계값(관절
  3°≈TCP 약 26mm)이 명시돼 있다.
- **SAFE_OFF 자동 복구는 설계 목표가 아니다** — "발생 자체를
  막는다"가 목표, 발생하면 사람이 복구한다(API 복구는 신뢰 불가
  확인됨, 티치펜던트에서 오류 팝업 닫고 서보 켜기로 복구).
- 관절 가동 범위·TCP 힘 한계는 "현재 확정값" 표 참고.
- 벨트/통 등 물리 구조물은 "면"이 아니라 "입체"로 취급 — 접근
  높이를 애매하게 계산하면 옆에서 눌러버릴 수 있다.
- **[확정 — v139, 9일차 저녁 실물검증 완료] 컨베이어는 무정지로
  동작한다** — 위험 상황(사람 손 검출/힘 하드리밋/음성 정지/
  작업 종료)에서만 정지, 파지 사이클 중에는 더 이상 세우지
  않는다. 대신 **도달한계 안전정지**(가장 앞선 미처리 물체가
  `max_reachable_x` 근접 시 정지, 처리되면 재가동)가 이를
  대체 — v48이 막던 "다음 물체가 처리 중 도달범위를 벗어나는
  문제"(6일차, NOT REACHABLE)를 더 정밀하게 막음. 정지 사유는
  집합으로 관리(인터록/도달한계/계량, `tracking_node` 내부),
  비상정지는 집합 밖 별도 하드상태, 전역 워치독 120초. 인터록은
  `conveyor.stop_during_pick` 설정으로 폴백 가능하게 남겨둠
  (오늘은 `false`). 상세는 "현재 단계" 절·실측기록.md 참고.
- **[구현·실물검증 완료] `weight_check`가 `can`에만 정의돼 있어
  물체가 오분류되면 원칙7(비전으로 못 보는 걸 힘으로 본다)이
  우회되는 구조였다** — 진짜 원인은 `_place_item()`의
  `human_handoff` 분기가 무게초과 판정(`forced_bin`)보다 먼저
  return하는 순서 버그였음(수정, 커밋 4e8be69). 지금은
  `pet_labeled`에 weight_check 추가 + 이 순서버그 수정으로
  안전 게이트 완성(실물 완주시험으로 검증됨). **`can`의
  weight_check는 오늘 밤 비활성화**(baseline 드리프트로 무력,
  단 `can`은 애초에 human_handoff가 아니라 안전 게이트가 아님
  — 상세는 "현재 단계" 절). **분류 결과를 안전 게이트로 쓰지
  말 것** 원칙은 그대로 유효.

### [완료] 무게 게이트(B)
근본원인은 `weight_check`가 `can`에만 있던 게 아니라
`_place_item()`의 `human_handoff` 분기가 `forced_bin`보다 먼저
return하던 순서버그였음 — 수정 완료(커밋 `4e8be69`).
`pet_labeled`에 weight_check 추가(threshold 0.08kg), baseline은
평균 대신 **중앙값**(단일 이상치 방지, 실제 방어선),
`net_weight < -0.03kg`이면 계측불신으로 `forced_bin=review_bin`
강제(보조 방어). **`can`의 weight_check는 오늘 밤 비활성화**
— baseline이 사이클마다 ~95~125g 드리프트(median으로도 안
잡히는 사이클간 문제, 원인 미상)해 신호크기(빈캔16g vs

`can`은 원래 `type: bin`이라 무게와 무관히 늘 can_bin행이므로
안전 게이트가 아님(진짜 안전 게이트는 `pet_labeled` weight_check
+ 위 순서버그 수정) — 비활성화해도 안전에 영향 없음. baseline
드리프트 근본원인 조사는 시연 이후 과제.

완전히 같은 원인·같은 해법**(통 티치 자세 rz=157.11과 파지
자세 rz=89.78이 67.33° 달라 긴 물체가 비스듬히 들어감, 355ml

진행 중.

**[팀결정 — 9일차 저녁] 물병 장면 제외, 캔만 사용.** 무게 판별
시연은 채운 캔 하나로 확정. `pet_labeled`의 weight_check

**[완료 — 9일차 저녁] 검출 안정성 확인 마무리.** 빈 355ml
캔, 샌드 채운 490ml 캔(라벨 정면/반대 방향 포함 여러 각도)
전부 안정적으로 `can`으로 검출됨(신뢰도 0.94 이상 유지, 육안+

샌드 소진으로 추가 소품 준비 어려움 — 이후 필요한 변경은 새
소품 준비보다 기존 캔들(빈 캔/샌드 캔) 안에서 대안을 찾는

**남은 확인**: 새 캔과 기존 학습캔 지름 동일 여부(다르면
pick_depth_mm/pre_close_width_mm/grasp_fail_joint_rad 재조정
필요), 새 캔 길이(~168mm)가 벨트 위에서 진행방향과 나란한지 —
남았으면 빠르게 마무리. **다음: 전체 시나리오 완주 재시험** —
물체 간격 축소 + 벨트 무정지를 **둘 다 반영한 상태로는 아직
전체 사이클을 안 돌려봄**, 모든 품목이 올바른 통에 들어가는지
확인 목적(지금까지는 개별 품목 확인 위주).

**[신규 발견 — 9일차 저녁, 30사이클 완주] baseline 측정이
자세에 고정 안 돼 있다 — 8일차 measure_pose 복원의 사각지대.**
8일차에 post-pick은 고정 자세(measure_pose) 측정으로 고쳤지만
**baseline은 팔이 그 순간 있는 자리에서 그대로 잰다** — 보통
직전 사이클 종료 후 벨트 상공(300,-264,430)이라 measure_pose와
우연히 일치하지만, **완주 시작 전 로봇을 홈으로 보냈더니 첫
사이클 baseline이 홈 자세(367.3,7.0,424.3,90.1)에서 측정돼
관절각 차이로 gravity compensation이 달라져 net이 213.7g
어긋남**(사용자가 "오차가 그렇게 클 리 없다"고 지적해 재조사,
로그로 확정). 30사이클 중 이 자세불일치는 2건뿐(213.7g,
44.2g) — **[정정] 이전에 제안됐던 임계값 0.28kg 상향은 철회**
(그 근거였던 213.7g가 드리프트가 아니라 이 자세문제였음이
밝혀져 무효화, 자세가 맞는 사이클만 보면 빈캔 net -41.1~+126g
로 0.20kg면 충분). **자세가 같은데도 남는 산포(-137.6~+126g)는
여전히 미해결**(진짜 원인불명 드리프트, 시연 이후 과제로 유지).
**결정**: (1) 운영규칙 — 사이클 시작 전 로봇을 홈으로 보내지
않고 벨트 상공에 둔 채 시작(즉시 적용). (2) 코드 가드(시간
되면 적용) — baseline 직전 현재자세 vs measure_pose 비교, x/y
5mm 초과 차이면 계측신뢰불가 처리(기존 net<-30g/파지폭 교차검증
게이트와 같은 구조 재사용) — 시연 중 SAFE_OFF 복구 등으로
로봇이 예상 밖 자세에서 재시작될 가능성이 있어 운영규칙만으론
재발 방지가 불완전하다는 판단.

**[확인 완료 — 9일차 저녁] 파지 후 상승까지 2~3초 대기는
전부 `close_wait_sec`.** 12사이클 실측: "닫기→상승" 소요시간이
설정값과 소수점 둘째자리까지 일치(can 2.01/2.0, plastic 2.51/2.5,
battery 1.02/1.0 등) — 코드도 `_call_gripper("c")`→`sleep(close_
wait_sec)`→즉시 `rise`로 직렬로 붙은 불필요한 대기 없음, 힘
정규화는 하강 전에 끝나있고 파지판정은 상승 후. 사용자가 관찰한
"2~3초"는 하강모션(1.9~2.1초)+close_wait가 합쳐진 것 — 줄이려면
`close_wait_sec` 자체를 줄여야 하는데 그러면 각 값이 정해진
이유(5일차 캔 5N 닫힘느림, 오늘 뚜껑 이송중낙하)가 재발할 수
있어 오늘 밤엔 안 건드림. **부수 확인**: 그리퍼 타임아웃 8→2초
단축 이후 로그에서 8초 행이 한 번도 재발 안 함 — 그 수정이
효과적이었음이 확인됨.

**[확인 완료] 파지실패 즉시복귀 — 회귀 아님, 알려진 범위 그대로.**

```
paper        0.5623   동작 확인
battery      0.6864   동작 확인
pet_labeled  null     종이 오분류 대응으로 비활성화(기존 결정)
plastic      null     판정 원리적 불가(같은 뚜껑 성공파지가
                      +0.7496/-0.0295로 갈림)

```
사용자가 "안 되는 것 같다"고 본 건 뚜껑(plastic) 시험 중이었기

**[중요, 안전 재평가 — 9일차 저녁 완주 재시험] 캔 무게중심 쏠림이
무게 측정을 왜곡시킨다 — 단순 시연 화면 문제가 아님.** 채운
캔을 정중앙이 아니라 한쪽으로 치우쳐 잡으면 반대쪽이 바닥/벨트에
끌리며 무게 일부가 바닥에 실려 로드셀이 실제보다 가볍게 읽음
(실측: 같은 샌드캔 net +448.0g(정상 파지) vs -130.3g(끌림
파지) — **처음엔 "자세는 맞는데도 남는 미제 산포"로 오인했으나
사용자가 원인을 짚어 정정함, 실제로는 이 끌림 현상**). **[위험
재평가]** 이게 만약 `pet_labeled`로 분류된 무거운 물체에서
일어나면, 무게 게이트가 "가볍다"고 오판해 사람에게 갈 수 있다
— 시연 화면 매끄러움 문제를 넘어 **무게 게이트 신뢰성과 직결**.
**대응 방향**: 파지력을 올리는 것보다 예측/그립 위치 보정이
근본적(모멘트 문제라 힘으로는 근본 해결 안 됨, 같은 프로파일을
다른 물체에도 쓰므로 힘 상향은 부작용 위험) — 원인이 (a) 잔여
예측오차인지 (b) 캔 길이 증가(122→168mm)로 그립 중심 계산에
남은 옛 상수 때문인지 관제PC 확인 중.

**[정정 — 9일차 저녁] 종이박스 파지실패는 깊이 부족이 아니었다
— 130mm는 벨트를 손상시킬 위험이 있는 값이라 원복(실물 실행
안 됨, 설정만 바꿨다가 재기동 전에 되돌림).** 처음엔 "하강
깊이 부족"으로 진단해 `paper` `pick_depth_mm`을 120→130mm로
올렸으나, 사용자가 물리 기준(battery 110mm=벨트면을 거의
스치는 기준, 120mm=이미 벨트를 세게 누르는 수준)을 제시해
재계산한 결과 **`paper` 120mm 자체가 이미 벨트 평면보다
10mm 아래**(벨트면 z=316.8~320.2, 120mm 하강 시 TCP z=310)
였음이 확인됨 — 130mm면 battery 기준보다 20mm 더 깊어 파지
실패 시 손가락이 벨트를 누르는 위험한 값. **[미해결, 결정
필요] 현재 배포값 120mm도 사용자 기준으로는 이미 "벨트를 세게
누르는" 값** — 오늘 종이 파지마다 이미 그렇게 눌러왔다는 뜻.
깊이가 실패 원인이 아니었다는 게 밝혀진 이상(아래 참고)
120mm를 유지할 이유가 없어 battery 기준인 110mm로 낮추는
안을 검토 중 — 사용자 확인 대기.

**[재구성 — 9일차 저녁] "깊이 부족"이 무너지면서 나온 대안
가설: X위치(잔여 예측오차)가 캔 끌림과 종이 파지실패의 공통
원인일 수 있다.** 이미 벨트면보다 아래까지 내려가는데 "덜
내려가서 상단만 물린다"는 설명은 성립 안 함 — 같은 깊이(120mm)
에서 초콜릿박스는 성공(+0.0062)했으므로 깊이 자체는 문제가
아니었음. 파지값(+0.6112/+0.6555, 완전허공 +0.7496은 아니고
얇은 것만 물림)은 **그리퍼가 박스 몸통이 아니라 가장자리/모서리에
닿았다**는 설명과 일치 — 무거운 캔은 "끌림"으로, 얇은 종이는
"가장자리만 물림"으로, 같은 X 잔여오차가 물체 형태에 따라
다르게 나타난다는 가설. **코드 확인 결과 좌표 버그는 안 보임**
(하강은 상대이동 Z만, 오프셋 없음) — 다만 **hover 이동엔 도달
검증이 있는데 descend엔 없다는 검증 공백 발견**, 하강 후 실제
z를 로그에 남기는 진단전용 추가(동작 변경 없음) 승인·적용 중.
**C270 스냅샷 자동캡처 스크립트도 준비 중** — 리얼센스가
여전히 프레임을 못 내므로(12초 0프레임 재확인, UI에 보이던
"연결"은 캐시된 정지화면으로 추정) 이 방법으로 다음 파지 시
그립 위치를 직접 확인해 보정 방향·크기를 정할 계획.

### [완료] 벨트 무정지 전환 + 도달한계 안전정지
40cm 간격의 근거("벨트가 계속 돈다")가 인터록 도입으로 이미
무효화됐던 걸 정리 — 벨트를 무정지로 돌리고 도달한계 안전정지
(`max_reachable_x` 근접 시 정지, 처리되면 재가동)로 대체.
확정 파라미터: 정지마진 540mm(한계 590에서 50mm 앞), 워치독
120초(reach_limit이 두 사이클에 걸쳐 유지될 수 있어 90초는
부족), 정지사유 집합은 `tracking_node` 내부(colcon 미구성으로
커스텀 `.srv` 불가), 비상정지는 집합 밖 별도 하드상태,
`hold`/`release` 명명, 타임아웃 초과 트랙은 무시목록+파지후보
제외. 검출 백로그 버그(파지가 executor 블로킹하는 동안 검출이
쌓였다 한꺼번에 드레인 → 칼만이 왜곡된 짧은 구간 속도로 크게
외삽)를 발견·수정(`detection_min_gap_sec` 필터). 칼만 속도
클램프 6.0mm/s 확정(물체 실측속도 2.9mm/s의 2배 — 벨트표면
5.0mm/s와의 42% 차이는 슬립/비전오차 원인 미확정, 시연 이후
조사, **발표에서 "2.0cm/s" 언급 금지**). 완주시험(9회 파지)
결과 무정지 기인 놓침 0건 확인, `stop_during_pick: false`로
최종 채택. 벨트속도 조사 경위 전체는 실측기록.md 9일차 저녁분
참고.

### [팀결정] 시연 물체 제약

위험 — 종이상자는 실제로 pet_labeled로도 잡히는 게 확인된

권장.
can↔pet_labeled 오분류는 벨트가 움직이는 조건에서 실물 재현
확인됨 — (B) 게이트가 승패와 무관하게 막아주므로 안전엔 영향
없음(빈 캔이 pet_labeled로 잘못 잡히면 그리퍼 힘 과다로 찌그러질
잔여리스크만 있음, 조치 없음). 찌그러진 빈 캔이 `plastic`으로
오검출(안전문제 아님, 찌그러진 캔 사용 자제로 대응).

**[중대 정정 — 9일차 밤, 판단 요청 중 v153] "종이박스는 물체
교체로 해결된다"는 대책이 무효화됨.** 같은 초콜릿박스가 낮
15시경엔 paper 53:pet_labeled 1(안전)이었는데 밤 17시경 같은
박스로 재측정하니 pet_labeled 10:paper 2로 **정반대**가 나옴
— 조명(창밖 밝기) 또는 박스 자세 변화로 추정, 어느 쪽이든
시연 당일에도 바뀔 수 있는 조건이라 "이 물체는 안전하다"는
결론 자체가 불안정함이 확인됨. 실제로 이 박스가 `pet_labeled`
로 확정돼 파지(빈 손, `pet_labeled` 100mm 프로파일을 탐 —
`paper` 110mm이 아님)됨. **[확인됨] review_bin행 경로**: 15초
타임아웃 폴백이 아니라 `net=-113.8g<-30g`로 계측신뢰불가
게이트가 먼저 걸려 사람에게 제시되기도 전에 차단됨(오늘 오전
만든 두 장치 — 신뢰불가 게이트 + forced_bin 우선순위 수정 —
가 연달아 작동, 설계대로). **다만 이번엔 우연히 막힌 것** —
같은 날 반대 사례(`full_1652` #5, net+105.6g로 임계값 안쪽이라
실제로 사람에게 제시→15초 대기→무응답→review_bin 폴백)가
이미 있었음, 막히느냐 사람 앞까지 가느냐가 그 순간 드리프트
부호에 좌우됨. **[신규, 실물 확인] 그립력 위험도 근접사고로
확인됨** — 이 사이클에서 종이박스를 `pet_labeled`로 분류해
**40N으로 잡으려 시도**(빈 손이라 무해했으나, 실제로 물렸으면
눌렸을 가능성 높음, "오분류 시 그립력이 무게판정보다 먼저
정해진다"는 우려의 실물 확인).

**[결정 완료 — v155] 오늘 밤 완주시험은 종이 제외, 시연 포함
여부는 당일 결정.** 오분류 빈도 자체가 물체의 고정된 성질이
아님이 확인됨(낮 2% → 밤 83%, 두 시간 만에 역전) — "빈도가
낮으니 안전"이라는 판단 틀이 성립 안 함. **오늘 밤은 변수축소
목적으로 종이를 빼고 나머지 6품목만 진행**(종이 오분류가
"라우팅 문제"와 "다른 품목 문제"를 구분 못 하게 오염시킴).
**시연 포함 여부는 촬영 당일 그 시각·조명에서 5~10회 재확인
후 그 자리에서 결정** — 조건에 따라 뒤집히므로 조건이 확정되는
시점에 정하는 게 맞다는 판단. 시나리오는 종이 포함본/제외본
두 버전 준비 권장. **`pet_labeled` 파지력(40N)과
`grasp_fail_joint_rad`(null)는 오늘 밤 둘 다 건드리지 않음** —
파지력 조정은 오늘 검증된 핸드오버 7/7 성공을 무효화하고 새
실패모드(당김판정 전 물체 이탈) 위험, 판정값 재활성화는 v143
에서 막았던 "오분류 시 성공을 실패로 오판" 문제 재발 위험.
**빈손 파지가 통 카운트를 오염시킬 수 있음 인지만 하고 조치
없음** — `pet_labeled` 빈손이 review_bin에 "배치"로 기록되는
경우가 있어 종료보고 숫자가 실제와 다를 수 있음, 촬영 후 로그와
실제 통 내용물 대조 확인 필요.
