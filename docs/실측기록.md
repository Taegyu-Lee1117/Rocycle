# ROKEY-Team-Project — 실측 기록 (시간순 로그)

이 파일은 `CLAUDE.md`(원칙·현재값)에서 분리된 상세 실측 로그다
(v46 정리). 실측 수치와 그 조건, 사고 경위와 원인 규명 과정, 설계
변경의 근거, 철회·정정 이력을 시간순으로 보존한다 — 최종 산출물
(요구사항 명세서·기능 명세서·보고서)의 원재료이므로 지우지 않고
옮긴 것이다. **현재 유효한 값/원칙은 `CLAUDE.md`를 참고할 것** —
이 파일은 "어떻게 그 결론에 이르렀는가"를 보여주는 경위 기록이며,
무효화된 결정도 왜 바뀌었는지 알 수 있도록 그대로 남겨둔다.

[원문] = 확인된 사실 [추론] = 판단 [전제] = 미검증 가정
[팀결정] = 팀이 확정, 재론하지 않음 [실측] = 실기 측정값

**[일러두기 — v47 반영]** 항목은 원래 CLAUDE.md의 순서(주제별
그룹, 예: 카메라 관련이 한데 모임)를 그대로 유지했다 — 유실
위험 때문에 재정렬하지 않았다. 그 결과 날짜가 문서 순서상
앞뒤로 오갈 수 있다(예: 2일차 항목 뒤에 6일차 항목이 나온 뒤
다시 1일차 항목이 나옴). 아래 목차와 주요 구간 소제목은 "이
구간은 대체로 어느 날 기록인가"를 보여주는 용도이며, 개별
항목의 정확한 날짜는 각 항목 자신의 `[... — N일차]` 태그를
따른다.

### 1일차 — 그리퍼 제어

- 그리퍼 제어: **[실측 — 1일차] ROS2 래퍼 제공됨.**
  `onrobot_rg_control` 패키지의 `OnRobotRGControllerServer` 노드가
  ws_dsr 워크스페이스에 이미 빌드되어 있음.
  서비스: `/onrobot/sendCommand`(`onrobot_rg_msgs/srv/SetCommand`,
  열기/닫기/파지력 증감/목표폭), `/onrobot/pose`
  (`onrobot_rg_msgs/srv/GripperPose`, 관절각→개방폭 조회).
  상태: `/onrobot_joint_states`(실제 하드웨어 값)
- **pymodbus는 3.10 미만이어야 함**(실사용 3.9.2). 3.10+부터
  `read_holding_registers()`의 `slave` 파라미터가 `device_id`로
  이름이 바뀌어 `onrobot_rg_control` 패키지 및 corecode의
  `onrobot.py`/`modbus.py`(둘 다 구버전 API 기준)와 호환 안 됨.
  설치: `pip install --break-system-packages "pymodbus<3.10"`
  ([실측] corecode `onrobot.py`의 `RG.__init__`도 `ModbusTcpClient`에
  `stopbits`/`bytesize`/`parity`/`baudrate` 인자를 넘기는데 현재
  pymodbus에서 `TypeError` 발생 — 같은 구버전 API 문제의 또 다른
  증상. corecode를 직접 쓸 땐 `ModbusTcpClient(ip, port=..., timeout=1)`
  형태로 직접 연결하는 우회가 필요)
- **개방폭 읽기(`get_width` 계열)는 레지스터 3개로 나뉜다**
  ([원문] `onrobot_rg_control`의 `User_Manual.pdf`): 267=Actual
  width(핑거팁 오프셋 미반영, 알루미늄 핑거 안쪽 기준), 275=Actual
  width with offset(오프셋 반영), 258=Fingertip offset(자동 감지
  아님 — 레지스터 1031로 **사용자가 직접 설정·저장**하는 값,
  캘리브레이션 이력 없으면 0일 가능성 높음). 현재 `/onrobot/pose`
  경로는 267 기반이라 오프셋 미반영 — 중간 폭 대역 오차(8.3mm)의
  원인 후보지만 258 실측 전까지 확정 아님.

### 2일차 — 컨베이어 프로토콜, PC 구성

- **[실측] 컨베이어는 단순 DC모터가 아니라 스테퍼 모터 +
  범용 "Microstep Driver"(PUL/DIR/ENA 방식, 9~42VDC)다.** 기존
  소스코드/문서 전혀 없었음 — 아두이노 Uno에 진단용 스케치를
  직접 작성해 확인함([팀 승인] 하에 진행, "구현 코드 금지" 원칙의
  예외 — 최종 `conveyor_node`가 아닌 1회성 진단 목적임을 항상
  명시할 것). 배선: PUL+→D3, DIR+→D4, PUL-/DIR- 공통→GND.
  **ENA+는 D5에 물려있지만 펌웨어에서 절대 건드리면 안 됨**
  (HIGH/LOW 어느 쪽으로 구동해도 안 움직였고, 핀을 아예 안 건드려
  플로팅 상태로 둬야 정상 동작함). 드라이버 DIP 스위치(SW1/SW2/SW3)
  는 **정확히 1개만 ON**이어야 동작(2개 이상 겹치면 무반응) —
  현재 SW1만 ON. 방향은 드라이버 실크스크린 화살표 표시의
  **반대**가 실제 정방향. 시리얼 프로토콜은 9600 baud,
  `"<steps_per_sec>\n"`(0=정지)로 직접 정의함(기존 규약 없었음).
  아두이노 개발에는 `arduino-cli`(snap)를 씀 — snap 샌드박스가
  `/tmp` 경로에 접근 못해 스케치는 반드시 `$HOME` 하위에 둘 것,
  USB 접근에 `sudo snap connect arduino-cli:raw-usb` 필요
  (serial-port 인터페이스는 이 환경에 슬롯이 없어 연결 불가 —
  raw-usb만으로 업로드는 됨).
- **[팀결정, 2일차 근거 갱신] PC 2대 구성**: 관제 PC(**C270**
  고정 카메라 + 추적 + **컨베이어 제어**) / 로봇 PC(RealSense
  손목카메라·팔·그리퍼·음성·상태머신). **[정정 — v28] 컨베이어를
  관제 PC가 맡는 이유였던 "추적 신뢰도 저하 시 즉시 정지"는
  더 이상 유효하지 않다** — 그 근거였던 `BELT_PAUSE_CORRECT`가
  v23에서 폐기됐다. **현재 유효한 근거는 손 검출 안전정지**
  (고정 카메라가 검출하고 관제 PC 로컬에서 즉시 `conveyor_node`
  를 정지시킴, 네트워크 왕복 없음) — 반대로 음성 정지·종료
  명령은 로봇 PC에서 네트워크를 건너 컨베이어에 도달하는
  비대칭 구조다(수백 ms 지연은 무해). USB 대역폭 분리 근거도
  약화됐다(C270이 720p MJPEG이라 부담이 작음). **[실측 — 2일차]
  arduino-cli는 현재 로봇 스택과 함께 떠 있는 공유 개발 PC 한
  대에 설치돼 있음** — 2일차 시점엔 물리적으로 PC가 아직
  하나뿐이고(케이블을 번갈아 꽂아 테스트 중), 실제 2대 분리는
  아직 집행 전이다. **[실측 — 6일차] 이 PC(로봇+카메라 전부
  붙여 써온 개발 PC)에는 NVIDIA GPU가 없다**(`nvidia-smi` 없음,
  내장그래픽 Intel UHD 620만 확인) — "관제 PC=GPU PC" 결정은
  아직 실행 전, 물리적으로 여전히 PC 1대뿐이라 YOLO 통합도
  이 CPU 전용 PC에서 우선 진행.
- **[팀결정 — v26, 최종 확정, v22/v23/v25 무효화] 분리수거 통은
  5개**(플라스틱/캔/종이/**건전지**/**확인 필요**), 로봇 양옆
  배치. **`battery`는 전용 통으로 로봇이 직접 파지해 넣는다**
  (v22의 "사람 전달" 결정 폐기). `styrofoam`은 품목에서 **제외**
  (파지력 하한 시연은 `can`으로 대체). **`vinyl_bin`(비닐 전용)이
  `review_bin`(확인 필요)으로 바뀌었다** — 재질별 분류(4통)와
  처리상태별 분류(1통)가 섞인 비대칭 구성은 결함이 아니라 "로봇이
  자기 한계를 아는 시스템"이라는 설계 의도를 물리적으로 드러내는
  장치([팀결정], 재론 안 함). `review_bin`에는 "확인 필요" 물리
  라벨을 부착한다. `plastic_bag`은 **묶인 것만 소품으로 준비**
  (낱장 `plastic_bag_loose`는 폐기 — 소품 자체를 준비하지 않음)
  하고 **무게 측정 없이 바로 `review_bin`으로 이동**한다(비전·
  무게 둘 다로 내용물 판별 불가한 유일한 품목이라는 게 근거).
  **클래스 수는 6개로 축소**(styrofoam 제외 + plastic_bag_loose
  폐기, 이름은 `plastic_bag_bundled`→`plastic_bag`으로 환원).
  **`PLACE_BACK_ON_BELT`/`place_back_pose`/로봇 옆 `general_bin`
  대안은 모두 폐기** — review_bin 도입으로 파지 후 되놓기 경로
  자체가 사라짐(무게측정 결과 무거운 opaque_container도 review_bin
  으로 직접 파지). 벨트 끝 일반쓰레기통은 **미검출/미학습 물체
  전용**으로 남는다(6클래스 밖 물체는 학습시키지 않고 그대로
  통과 — 판정이 바뀌지 않으므로, 원칙7).
- **[확정 — v25] 건전지는 AA로 진행, D형 폴백 불필요.** 조정된
  카메라 구도(30~40도 각도, 배경 차폐)에서 실측 폭 약 30px/길이
  약 110px로 20px 검출 기준을 상회함. 은박지류와 색·광택이
  유사해 혼동 가능성이 있어 건전지 촬영량은 다른 품목보다 다소
  늘릴 것.
  **[재검토 필요 — v38, 팀결정 대기 → 4일차 해소]** 위 결정은
  검출 기준(20px)만 본 것이고, `belt_correction.py` 최대 잔차
  (8.6mm)가 AA 반지름(7mm)을 넘어 파지 좌표 여유 부족 우려가
  있었으나, 4일차 실측에서 8.6mm 잔차 우려가 실제로는 발생하지
  않음을 확인(아래 4일차 항목 참고).
- **[실측 — 2일차] `can` 파지력 하한: 정적 매달림(로봇 미이동,
  중력만) 조건에서 5N→2.5N→0N(그리퍼 소프트웨어 명령 최저값)까지
  내려도 미끄러지지 않았다** — 이 캔+고무 재질 핑거팁 조합에서는
  중력만으로 하한을 특정할 수 없었다. 단 0N 명령 상태에서도
  사람이 손으로 당기자 캔이 찌그러지려 했다 — **그리퍼의 "0N"
  명령이 실제 물리적 0N을 의미하지 않는 것으로 추정**[추론].
  상한(찌그러짐)과 하한 사이 여유가 기대보다 좁을 가능성이
  있어, **상한 실측(캔 여분 확보 후) 우선순위가 높아졌다.**

### 4일차 — 파지력 재질별 차이

- **[실측 — 4일차] 기본 그리퍼 파지력(명령 조정 없는 기본값)으로
  종이/포일 재질 소품(초콜릿 상자)을 집었더니 모서리가 찌그러짐.**

### 2일차 — 컨베이어 탈조 검증, 그리퍼 복구 절차

- **[팀결정 — 실측 기반] 컨베이어 속도는 100 steps/sec로 고정**
  (50=무동작, 100=적당함 확인, 200=과속으로 사용자 판단). 속도
  조절 기능은 지금 만들지 않는다. 수동 on/off는
  `~/bin/conveyor {on|off|rev|<steps_per_sec>}` 스크립트로 가능
  (직접 작성한 진단용 헬퍼, `conveyor_node` ROS2 구현체가 아님).
- **[실측 — 2일차, 완전 종료]** 컨베이어 탈조 검증 완료 — 100
  steps/sec는 탈조 없음 확정. DIP표 실측(사진, SW1만 ON): 400
  pulses/rev, microstep 2/B. 풀리 지름 실측: 2.5cm(둘레 π×2.5=
  7.85cm). 이론 속도 vs 실측: 100 steps/sec는 1.96cm/s(이론) vs
  2.0cm/s(실측, 차이 2%, 오차범위 내) — 탈조 없음. 200 steps/sec는
  3.93cm/s(이론) vs 2.5cm/s(실측, 차이 36%) — 탈조 확정(200은
  시연에 안 쓰여 무관). 칼만 필터 상수는 실측값 2.0cm/s를 그대로
  쓴다.
- **[실측]** 그리퍼가 "Connected successfully" 로그 후에도
  `ModbusIOException: No response received after 3 retries`로
  죽는 경우가 있다 — TCP 연결은 되는데 장치가 응답을 안 하는
  상태. **그리퍼 Compute Box 전원을 껐다 켜면 해결됨.**
- **[실측 — 2일차]** `/onrobot/restartPower` 서비스
  (`std_srvs/Trigger`) 호출하지 말 것 — 즉시 노드를 죽인다.
  `restartPowerCycle()`이 `self.client.write_register(address=0,
  values=message, slave=restart_address)`를 호출하는데, 현재
  pymodbus 버전은 `values` 키워드 인자를 받지 않아(`TypeError`)
  그 자리에서 크래시한다(`comModbusTcp.py` 88행,
  `OnRobotRGControllerServer.py` 207행).
- **[실측 — 2일차, 문서 정정]** 그리퍼가 응답 없어 보여도 하드웨어
  문제가 아닐 수 있다 — 토픽 리맵 누락이 원인이었던 사례 확인.
  `OnRobotRGControllerServer`는 조인트 상태를 항상 `/joint_states`
  로 퍼블리시한다(소스에 하드코딩, `remap`으로만 이름을 바꿀 수
  있음). `-r /joint_states:=/onrobot_joint_states` 리맵이 빠지면,
  노드는 정상 출력하고 그리퍼 제어도 되지만 `/onrobot_joint_states`
  토픽엔 아무 것도 안 뜨고 에러도 없이 조용히 비어있다.
- **[운영]** 로봇 제어 스택이 꺼져 있으면 아래로 재기동:
  ```
  ros2 launch m0609_rg2_bringup bringup.launch.py mode:=real host:=192.168.1.100 model:=m0609
  ```
  **[정정 — 2일차]** `bringup.launch.py`(149~167행)에는 그리퍼
  노드가 `mode:=real` 조건으로 이미 포함돼 있다 — 과거 "그리퍼
  노드를 포함하지 않는다"는 기록은 더 이상 정확하지 않다. **[확인
  — 2일차]** 스택을 처음부터 재기동하면 위 명령 하나로 그리퍼까지
  자동으로 뜨는 것을 실측 확인함 — 별도 그리퍼 실행 불필요.
  스택 재기동 없이 그리퍼만 따로 다시 띄워야 하는 경우에만
  아래처럼 **반드시 리맵을 붙여서** 수동 실행:
  ```
  ros2 run onrobot_rg_control OnRobotRGControllerServer --ros-args \
    -p /onrobot/gripper:=rg2 -p /onrobot/control:=modbus \
    -p /onrobot/ip:=192.168.1.1 -p /onrobot/port:=502 \
    -r /joint_states:=/onrobot_joint_states
  ```

### 4일차 — 그리퍼 비동기·좌표 함정

- **[실측 — 4일차, 다중 물체 테스트]** `onrobot/sendCommand`의
  'c'(닫기) 명령은 즉시 반환되고 실제 그리퍼 물리 동작 완료를
  기다리지 않는다. 닫기 명령 직후 바로 로봇 이동(상승) 명령을
  보내면 그리퍼가 완전히 닫히기 전에 팔이 움직여 물체를 놓치는
  사고가 반복 재현됨. **대응: 닫기 후 최소 1초, 파지력을 낮춘
  상태(5N)라면 2초 대기 후 다음 동작 진행할 것.** 실시간 완료
  신호(`/onrobot_joint_states`의 `effort` 필드, 219행)를 폴링
  하는 게 더 정확할 수 있으나 시간 관계상 구현 못함 — 다음
  기회에 폴링 기반으로 교체 권장.
- **[실측, 중요 — 4일차]** 그리퍼 파지력 상태는 세션 내내 수동으로
  추적해야 한다 — 자동으로 리셋되지 않는다. 캔 파지 목적으로
  낮춰둔 5N 상태가 이후 배터리 등 다른 작업에도 그대로 유지되고,
  반대로 기본값(약 40N)으로 복원한 뒤 이를 잊고 캔을 다시 잡으면
  찌그러진다 — 실제로 이 세션에서 두 방향 다 실수로 재현됨.
  **[팀결정 — v40]** 파지력·대기시간을 품목별 쌍으로 외부화해
  코드로 강제한다 — 매 파지 직전 `config/gripper_profiles.yaml`
  에서 해당 품목 값을 조회해 명시적으로 설정할 것. **[과대 청구
  금지]** 이건 "안전한 값을 찾았다"이지 "찌그러짐 정확한 상한을
  특정했다"가 아니다 — 40N(찌그러짐)과 5N(정상) 사이 어딘가에
  실제 임계값이 있다는 것만 안다.
- **[실측, 중요 — 4일차]** 벨트 끝부분(로봇 베이스에서 먼 지점,
  예: x=650~660mm 부근)의 물체는 일반적인 수직 자세(ry≈180 근처)
  로는 도달 불가능한 경우가 있다 — CAN 통과 달리 이번엔 ry만
  바꿔서 기울이는 시도(160~80 전 범위 스캔)가 전혀 통하지 않았다.
  **실제로 도달 가능했던 자세는 rz까지 크게 바꾼 값**(예: 실측
  `x=599.76, y=-262.97, z=316.68, rx=2.45, ry=161.14, rz=-84.84`
  — 일반 벨트 자세의 rz~89.78과 약 175° 차이)이었다. **교훈:
  도달 불가능 지점에서 자세를 조정할 때 한 축(ry)만 스캔하지
  말고, 특히 rz도 함께 바꿔볼 것.**
- **[실측 — 4일차]** `MoveLine` 직선 경로가 관절한계에 걸려 조용히
  실패하는 문제는 벨트 위 물체 파지에서도 동일하게 재현됨 — 특히
  자세가 크게 다른 시작점(예: 홈 자세)에서 벨트 먼 지점으로 한
  번에 이동하려 하면 실패. 중간 경유점(예: x를 100~150mm 단위로
  나눠 순차 이동)으로 우회 가능.

### 3일차 — 캘리브레이션 원인 규명, 펜 마킹, 충돌 모델

- **[완료 — 3일차 심야] end-to-end 정확도 근본원인 규명 + 수정.**
  펜 마킹 실측(8.7~23cm 오차)의 원인은 두 가지였다: (1) corecode
  `eye2hand_calibration.py`의 AX=XB 솔버 자체가 버그(가상 정답
  데이터로 검증, `cv2.calibrateHandEye()`로 교체 완료), (2) 그래도
  남은 오차는 **eye-to-hand 캘리브레이션 샘플의 깊이(카메라로부터
  거리) 다양성 부족** — 회전은 다양했지만(42°) 깊이 범위가
  66mm로 좁아 깊이축 정확도가 안 잡혔고, 벨트처럼 먼 곳에서
  증폭됨(체커보드-그리퍼 오프셋 역산 표준편차: X,Y는 1~2mm인데
  Z만 7.7mm). **진단 방법**: 코너 쌍 사이 거리를 검산해 "예측
  거리/실제 거리(24mm×칸수)" 비율이 위치와 무관하게 0.60~0.62로
  일정함을 확인(강체변환은 거리를 보존하므로 이건 캘리브레이션
  문제가 아니라는 게 결정적 단서였음 — 웹 클로드 v36 지적).
  깊이 다양성을 넓힌 재캘리브레이션은 **체커보드 테이프 마운팅의
  재현성 한계**로 오히려 악화돼 실패 — 대신 실측 5점(펜 마킹)에
  유사변환을 피팅한 경험적 보정(`rocycle_robot/geometry/
  belt_correction.py`)을 `pixel_to_base_point`의 belt_plane 결과에
  후처리로 적용, RMS 4.5mm/최대 8.6mm로 검증 완료(추가 랜덤
  검증 5회 재현, 0~4mm). **[전제]** 이 보정은 belt_plane 전용 —
  다른 평면에 쓰려면 재보정 필요.
- **[해소 — 3일차 심야]** 벨트 물리 위치 이동 후 원위치 복원 +
  재검증 완료. 3일차 후반 반복된 로봇 접근 시행 중 벨트가
  밀렸었으나, 원위치 복원 후 랜덤 코너 재검증에서 오차 약 2.2mm

  체크리스트에도 포함해야 함.**

  입체 구조물"로 취급할 것 — 접근 높이를 벨트면과 테이블면 사이

  (3일차 실측으로 확인, 안전 후퇴로 대응함).

### 6일차(계속) — YOLO12s 통합~순차 처리 인덱싱, 무게측정
버그체인, 인프라 사고 2건, 핸드오버 안전수정 (CLAUDE.md v53
정리로 이관, 원문 그대로 보존)


- 주제: **컨베이어 기반 재활용 분류 협동로봇**(벨트 이송 + 동적
  추적 + 예측 파지, 확정).
- 평가 기준: 참신성·사업성 미평가, **기술력만 평가**(완성도 +
  기법 융합 + 설명 가능성) — 각 기술 선택마다 "왜 이 방법이어야
  했는가"를 설명할 수 있어야 함.
- **[팀결정] 강사 승인 완료, 구현 단계.** 구현 코드 작성 제약
  없음(설계·인터페이스까지만이라는 과거 제약은 무효, 단 실측

- **좌표·파지 검증 단계 완료**: 벨트→통 파이프라인 5개 품목
  전부 실물 성공, 5개 통 좌표 티칭 완료.
- **[팀결정 — v45, 최우선] 벨트 위 수동-검출 기반 예측 파지는
  구조적으로 성립하지 않음이 확인돼 중단.** 카메라 캡처→(사람/AI
  가 이미지를 보고) 좌표 판단까지 실측 50초 이상 걸려, 벨트
  2cm/s 기준 예측 출발점 자체가 과거 데이터가 됨(상세:
  실측기록.md "Task C 종료" 항목). **다음 작업 순서:**
  1. YOLO12s 실시간 검출 연동(팀원 전달 모델, `team_share_yolo12s/`)
     — 좌표변환·파지 시퀀스·안전 처리는 보존, 검출 결과 생성
     부분만 교체. 클래스명은 이미 모델 쪽(`pet_labeled`/
     `pet_unlabeled`)으로 통일 완료(v47).
  2. [완료 — 6일차, dry-run] anchor_pixel 위치·미학습 물체 오검출·
     추론 지연시간 확인. **결과: (a) anchor_pixel은 매번 bbox
     하단중앙(벨트 접점)에 정확히 찍힘 — 정상. (b) 미학습 물체
     (휴지심)를 올리자 `pet_labeled`로 오검출(conf 0.28~0.30,
     10프레임 중 8회) — 단 신뢰도가 낮아 conf 임계값 0.6~0.7로
     올리면 걸러짐(계획된 대응이 유효함을 실측 확인). (c) 라벨
     없는 실제 페트병이 `pet_labeled`로 오분류(conf 0.94, 10
     프레임 전부) — 이건 신뢰도 자체가 높아서 **conf 임계값으로는
     못 거른다**, README/평가치(14/16)가 경고한 모델 자체의
     한계가 실물로 재현된 것. (d) 추론 지연시간 CPU 평균 ~1.0fps
     (웜업 프레임 제외 600ms~2s/frame) — 계획했던 "CPU 3~10fps"
     미달.** `pip install torch`가 이 PC에 불필요한 전체 CUDA
     스택을 받으면서 `numpy`를 2.x로 올려 `cv_bridge`가 깨지는
     충돌 발견·해결(`opencv-python` pip 패키지 제거, 시스템
     `python3-opencv`(4.6.0)+`numpy<2`로 복귀 — 상세: 실측기록.md
     6일차).
  2b. **[팀결정 — v47 회신] 세 가지 확정.**
     - **conf=0.6로 확정.** 오검출(0.28~0.30)과 정상 검출(0.94+)
       사이 여유가 커서 0.6이면 충분(0.7도 안전).
     - **pet_labeled/pet_unlabeled 고신뢰도 오분류는 (a) 알려진
       한계로 받아들이고 진행 + 시연 구성에서 무라벨 페트병
       제외**(라벨 있는 페트병만 사용, 사람전달 시연은 그걸로
       진행). 보조 후처리 규칙(옵션 c)은 원칙6(과대청구금지)에
       걸림 — "모델이 못하는 걸 후처리로 덮었다"가 되고, 라벨
       유무 판별 규칙 자체도 만들기 까다로움. 재학습(옵션 b)은
       시간이 없음(재촬영·재라벨링·재학습에 하루 소요). **이
       한계는 v25부터 예견했던 것과 같은 맥락**(C270은 depth
       없어 무라벨 투명체 검출이 원리적으로 제한됨) — 발표에서
       "예측이 실측으로 확인된 것"으로 설명 가능.
     - **GPU PC 분리는 지금 안 한다.** 새 DDS 통신 문제가 생기면
       복구에 몇 시간 걸릴 수 있어 리스크가 큼. **CPU ~1fps로도
       충분할 가능성이 높다** — 벨트 속도(2cm/s)는 이미 알고
       있는 값이라 칼만 필터가 굳이 매 프레임 속도를 다시
       추정할 필요가 적고, 위치 갱신 위주로 예측 시간(검출지연
       +이동+하강+닫힘)에 넣어 보정하면 됨. 통합 후 실측으로
       재확인할 것.
  2c. **[완료 — 6일차] YOLO12s 통합 완료(dry-run).** 신규:
     `rocycle_robot/vision/{detector.py, config_loader.py}`,
     `rocycle_robot/models/yolo12s_best.pt`(sha256 검증됨),
     `config/vision.yaml`(conf=0.6 등 외부화). `tracking_node.py`에
     `/image_raw` 구독 + 연속 프레임 확인(`min_consecutive_frames`
     =3) + 객체 잠금(`object_lost_frames`=5) 게이팅 추가 —
     `pixel_to_base`/`belt_correction`/칼만필터/파지시퀀스는 전혀
     안 건드림(통합 프롬프트 7번 준수). **로봇 명령 코드는 이
     노드에 없음 — 현재 100% dry-run.** 백업: 통합 전
     `tracking_node.py`를 USB(`backup/tracking_node.py.pre_yolo_
     backup`)에 보관. 단위테스트 33개 전부 통과(모델 로딩 포함).
     **라이브 검증**: 실제 카메라로 미학습 물체(휴지심) 테스트 —
     conf=0.6에서는 무검출(정상), conf=0.1로 낮추면 0.30~0.33으로
     검출되다가 3프레임째 `pick_ready=True`가 정확히 1회만 발행되고
     이후 잠김(재트리거 안 됨) — 게이팅 로직 정상 확인. 실제
     로봇 연결(Pick 명령 발행)은 아직 안 함 — 이 노드엔 그 코드
     자체가 없고, 상태머신 노드가 아직 미착수 상태.
  2d. **[완료 — 6일차, 이정표] YOLO12s 검출로 트리거된 첫 완전
     자동 파지 성공.** `tracking_node.py`에 실제 로봇 실행
     연결(`_execute_pick`: 파지력 정규화 → 호버 이동 → 하강 →
     닫기 → 상승, `config/motion_timing.yaml`의 벨트 호버 포즈/
     속도 값과 `gripper_profiles.yaml`의 `pick_depth_mm`(신규
     필드) 사용). 정지한 캔으로 실물 검증 — YOLO가 검출→3프레임
     확인→예측→실제 로봇 이동·파지까지 **사람 개입 없이** 전부
     성공(사진으로 확인). 안전장치로 `belt_pixel_y_min`(vision.yaml)
     추가 — 지금 카메라 구도엔 통(bin)들도 같이 잡히므로, 통
     영역(anchor_pixel의 v가 470 미만)에서 검출되면 로봇을 실행
     하지 않음(README의 "벨트 ROI 불필요" 전제는 통이 카메라
     시야 밖인 최종 배치 기준 — 지금은 아직 아님).
     **[버그 발견·수정]** 처음 시도에서 `rclpy.spin_until_future_
     complete(self, future)`를 구독 콜백(`_on_image`) 안에서
     호출하다 "Executor is already spinning"으로 실패(재진입
     스핀 금지, 아무 로봇 명령도 안 나간 채 안전하게 중단됨 —
     `get_current_posx`로 무이동 확인). **해결**: 로봇 제어 전용
     `Node`+`SingleThreadedExecutor`를 별도로 만들어 완전히 분리
     — 이제 정상 동작. 상태머신 노드를 나중에 따로 만들 때도
     이 분리 패턴(구독 콜백과 블로킹 서비스 호출을 같은
     executor에서 섞지 말 것)을 유지할 것.
  2e. **[버그 발견·수정 — 6일차, 벨트 이동 1차 시도]** 위 2d 성공
     직후 `update_x_detection()`을 pick_ready 순간에 딱 한 번만
     부르는 구조였다는 걸 발견 — 정지 물체는 문제없지만(속도=0→
     예측=현재), **벨트가 실제로 움직이면 데이터 포인트 하나로는
     속도를 추정 못해 예측이 항상 "현재 위치"로만 나오는 구조적
     결함**이었다(v44 최초 실패와 같은 함정을 다른 경로로 재현할
     뻔함). **수정: 같은 객체로 확인되는 한 매 프레임
     `update_x_detection()`을 호출**해 칼만필터가 여러 프레임에
     걸쳐 속도를 계속 추정하게 바꿈 — `min_consecutive_frames`는
     "Pick을 언제 확정할지"에만 쓰도록 역할 분리. 새 클래스가
     시작되면 칼만필터를 리셋해 이전 객체 상태와 안 섞이게 함.
  2f. **[실측, 실패 — 6일차, 벨트 이동 1차 실물 시도]** 캔을 벨트
     시작점에 놓고 벨트 가동, 위 2e 수정 버전으로 시도 — **실패,
     캔 뒤쪽(진행방향 기준 뒤쪽)을 잡아 파지가 밀려 떨어짐.**
     칼만필터가 3프레임(~2초, CPU ~1fps 기준) 만에 확정되어
     vx=0.00→3.92→2.00mm/s로 추정치가 크게 흔들린 상태에서
     7.6초(이동+하강+닫힘) 앞을 예측 — **짧은 관측 구간(baseline)
     에서 나온 잡음 섞인 속도로 긴 시간을 외삽하니 오차가
     증폭돼 예측 과대(캔이 예측보다 덜 이동, 그리퍼가 앞서서
     닫힘)로 이어졌다**[추론]. **대응: `min_consecutive_frames`를
     3→5로 상향**(관측 구간 ~2초→~4~5초로 확장, `vision.yaml`).
     로봇 상태 정상(SAFE 트립 없음), 캔은 사용자가 벨트에 재배치,
     재시도 대기 중.
  2g. **[사고, 수정 — 6일차] `_execute_pick`이 파지 전 그리퍼를
     명시적으로 열지 않는 버그로 캔이 찌그러짐.** 2f 수정 직후
     재시도(min_consecutive_frames=5) — 첫 번째 캔 파지는 성공
     (거의 중앙, 사용자 확인), 그 직후 화면에 잡힌 **두 번째
     물체(pet_labeled로 오검출된 것으로 추정)를 향해 그리퍼가
     닫힌 채로 그대로 내려가 눌러서 캔이 찌그러짐** — `_execute_
     pick`이 "닫기"만 하고 그 전에 "열기"를 한 적이 없어서, 첫
     파지 후 닫힌 상태가 그대로 유지된 채 두 번째 파지 시도의
     하강이 시작된 것. **긴급 조치**: 수동으로 그리퍼 열어 확인,
     로봇 SAFE 트립 없음 확인. **수정 2가지**: (1) `_execute_pick`
     맨 앞에 `'o'`(열기) 명시 추가(파지 시작 시 항상 먼저 연다),
     (2) 물체를 들고 있는 동안(`_holding=True`) 배치/상태머신이
     없어 놓을 수 없으므로 **새 Pick 자체를 막는 가드 추가** —
     상태머신이 생기기 전까지 한 번에 하나만 파지하고 사람이
     확인 후 재시작하는 것을 임시 규칙으로 둠. **[팀 확인]**
     테스트 시작 전 그리퍼가 열려있는지 항상 먼저 확인할 것
     (사용자 지적, 표준 절차로 채택).
  2h. **[실측, 부분성공/부분실패 — 6일차, 벨트 이동 재시도]** 위
     2g 수정 후 다시 시도 — **성공, 거의 중앙 파지**(사용자 확인).
     이어서 사용자가 아까 찌그러졌던 캔을 손으로 펴서(약간 찌그러진
     채) 다시 테스트 — **YOLO가 여전히 `can`으로 conf 0.94 검출**
     (찌그러짐이 검출에 영향 없음 확인). 이 캔으로 재시도 —
     **실패, 캔 하단부 끝만 겨우 잡음(더 우측/진행방향으로 갔어야
     함) — 이번엔 예측 과소(부족)** 방향.
     **[버그 발견·수정] 원인: 그리퍼 열기(0.5s)+파지력 정규화
     (최대 28회 명령, 실측 약 1.7~2.2초)를 하는 동안 로봇이
     실제로는 아직 안 움직이는데, 이 시간이 `predict_ahead_sec()`
     (이동+하강+닫힘)에 전혀 반영이 안 되고 있었다** — 즉 예측
     시점("지금")과 실제 이동 시작 시점 사이에 매번 2초 넘는
     누락된 지연이 있었던 것(2f의 "예측 과대"와 정반대 방향 오차
     — 서로 다른 원인이 같은 세션에서 양방향으로 다 나타남).
     **수정: 목표 좌표를 힘 정규화가 다 끝난 직후 "지금" 기준으로
     다시 계산**하도록 `_execute_pick`을 재구성(칼만필터 마지막
     갱신 시각부터 그 시점까지 흐른 실제 시간을 예측 시간에 더함).
  2i. **[실측, 성공 — 6일차, 벨트 이동 재검증]** 위 2h 수정 버전으로
     재시도 — **성공, 거의 중앙 파지**(사용자 확인). 재예측 로그로
     확인된 실측값: `extra_gap=2.207s`(그리퍼 열기+파지력 정규화에
     실제로 걸린 시간), 이걸 반영해 목표 x가 508.65→521.99mm로
     약 13.3mm 앞쪽으로 보정됨 — 이 보정이 없었다면 2h와 동일하게
     하단부만 걸렸을 것[추론, 이번 시행과 2h 실패 시행의 유일한
     코드 차이가 이 보정이므로 근거는 타당하나 다른 요인(속도
     추정치 자체의 차이 등) 기여도까지 정밀 분리하지는 않음].
     **현재까지 벨트 이동 파지 성공 2회(2i, 그리고 2g 수정 직후
     1회 — 둘 다 "거의 중앙"), 실패 2회(2f 예측 과대, 2h 예측

     consecutive_frames를 낮춰 confirmed까지 시간을 단축(단

    *이전*(force 정규화 직후)으로 이동 — 이러면 이 시간이 자동으로

    늘려(길수록 칼만필터 속도오차 증폭) 파지 정확도에 악영향을
    주므로, **baseline은 빠른 설정(n=3, interval=0.08s)으로 축소**
    (post-pick 측정은 벨트 이미 정지 상태·그리퍼-크리티컬 경로
    아니므로 기본값 n=5 유지). 수정 후 재검증: extra_gap 정상 범위
    복귀, 파지 위치 "중앙에서 아주 약간 하부"로 크게 개선(사용자
    확인), net=-57.5g로 can_bin 정상 배치.
  - **[사고] `reset_workpiece_weight` 서비스 호출 후 ROS2 서비스
    레이어 전체가 멈춘 사고 발생** — `get_workpiece_weight`뿐
    아니라 무관한 `get_robot_state`까지 타임아웃. 펜던트 확인 결과
    로봇 자체는 정상(ROS2 stale, CLAUDE.md 기존 원칙과 일치) —
    **로봇 스택 재기동**(`bringup.launch.py`)으로 복구, 이후 정상.
    **`reset_workpiece_weight`는 이 세션에서 더 쓰지 않기로 함**
    (인과관계 미확정이나 리스크 대비 실익 낮음). 재기동 후 무게
    절대값의 기준점 자체가 바뀜(빈 그리퍼 ~1.3kg → ~0.1~0.2kg) —
    상대측정 설계이므로 로직 영향은 없음.
  - **[미해결, 열린 이슈]** 위 수정들 이후로도 편향이 완전히 0이
    되진 않았다(예: net=47.6g로 review_bin行 사례 재발) — 힘센서
    노이즈의 근본 원인(수 초~수십 초 단위 완만한 드리프트, 별도
    실측으로 확인됨: rise 후 0.7초=1.367kg→7초=1.405kg→18초=1.330kg,
    진폭 약 ±38g) 자체는 미해결(원인 추정: 관절 토크 센서 온도
    드리프트 또는 중력보상 모델 오차[추론] — 우리가 고칠 수 있는
    대상이 아니라고 판단, 파고들지 않기로 함).
  - **[팀결정 — v52 회신] threshold 30g→80g 상향 + 시연용 내용물
    무게를 현재(86.9g)의 약 2배(~175g)로 늘리는 것으로 잠정 결정**
    (`config/item_routing.yaml`에 반영 완료). 근거: 신호(내용물
    무게)를 드리프트보다 크게 키워 압도하는 방향 — 빈 캔 최대
    (16.3g+38g=54g)와 든 캔 최소(175g-38g=137g) 사이에 80g을 둠.
    **[전제, 미검증] 이 계산은 구 속도 기준값(16.3g/86.9g)과 정지
    상태 고립 드리프트(±38g)를 근거로 한 것인데, 이 세션 후반
    실제 파지 사이클에서 관측된 net 값은 -87.9g~+153.8g로 이
    계산이 가정한 것보다 훨씬 넓게 흔들린 사례가 있다** — 정지
    상태 드리프트 실험은 "가만히 있을 때" 노이즈만 포착했을 뿐,
    실제 파지 사이클(baseline은 수평 이동 후, post-pick은 수직
    하강+파지+상승 후 — 서로 다른 동작 뒤에 측정)에서 생기는
    추가 요인은 못 잡았을 가능성이 있다[추론]. **80g/175g은
    최종값이 아니라 시작값** — 내용물 교체 후 빈 캔 5회·든 캔
    5회를 재고 두 분포가 80g을 사이에 두고 명확히 갈리는지 반드시
    재검증할 것(다음 세션 최우선).
  - **[과대 청구 금지, 문서 작성 시 준수]** "무게를 정밀하게
    측정한다"고 쓰지 말 것 — 정확한 표현은 "내용물 유무를 판별할
    만큼의 여유를 확보했다"이다. 힘센서 자체가 수 초~수십 초 단위로
    ±38g 드리프트하는 걸 알고 threshold를 그보다 크게 잡은 것이지,
    센서 드리프트 자체를 해결한 게 아니다.

  **4) 카메라(usb_cam) 노드 중단·복구.** 세션 중 원인 불명으로
  `usb_cam_node_exe` 프로세스가 죽어 `/image_raw`에 아무것도 안
  들어오는 상태가 됨(`tracking_node`는 정상 기동했지만 검출 자체가
  0건, "로봇 안움직임"으로 발견). `ros2 node list`로 카메라 노드
  부재 확인 → 과거 로그(`~/.ros/log/usb_cam_node_exe_*.log`)에서
  정확한 실행 파라미터(device=/dev/video2, 1280x720, mjpeg2rgb,
  30fps — CLAUDE.md 하드웨어 전제와 일치) 확인 → 동일 설정으로
  재실행해 복구(`ros2 topic hz /image_raw`로 30fps 확인).

  **5) 핸드오버 오탐 릴리즈 버그 발견·수정 — `_handoff_item`.**
  라벨 페트병(실제로는 캔이 `pet_labeled`로 오검출된 사례, 아래
  참고) 핸드오버 중 순응모드 진입 2.9초 만에 아무도 안 당겼는데
  "당김 감지"(disp=10.7mm)로 그리퍼가 열려 물체가 떨어짐(사진으로
  확인). **원인**: `start_pos`(변위 비교 기준점)를 순응모드 진입
  *이전*에 캡처하고 있었는데, 저강성(500) 진입 자체가 물체 무게로
  인한 자연스러운 처짐(중력)을 만들어 그게 "당김"으로 오인됨.
  **수정**: `start_pos` 캡처를 순응모드 진입+settle 대기 *이후*로
  이동 — 중력 처짐은 이미 기준점에 포함되고 그 이후의 "추가" 변위만
  당김으로 잡힌다. **실물 재검증 성공**: 진입 2초 후 실제 당김
  (disp=10.8mm) 정상 감지, 사용자가 실제로 페트병 수령 확인.

  **6) [팀 확인, 원인 특정] 캔→`pet_labeled` 오검출 1건 재현.**
  사진으로 명백한 캔(라벨 반사 있는 특정 캔)이 `pet_labeled`
  0.95~0.96 고신뢰도로 오검출됨. **[팀 확인] 사용자가 팀원과 원인
  확인** — 학습 데이터에 없는(미학습) 캔이었고, 성분표가 보이는
  면을 위로 놓으니 `can`으로 정상 검출됨(라벨 인쇄면 방향 이슈로
  잠정 결론, 모델 재학습 없이 코드로 고칠 사안 아님 — 원칙6). 오늘
  범위에서는 이 캔을 테스트에서 배제하는 것으로 넘어감.
  **[팀결정 — v52 회신] 시연 물체 목록에 "학습된 캔만 사용" 명시**
  — 리허설에서 미학습 캔이 섞이면 같은 오검출이 재발한다.
