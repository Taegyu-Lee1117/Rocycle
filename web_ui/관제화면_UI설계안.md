# 관제 화면 UI 설계안 (v67 확정본 기준, 8일차 갱신)

[원문] = 확인된 사실  [추론] = 판단  [전제] = 미검증 가정

이 문서는 `web_ui/index.html`(실제 구현)과 항상 일치해야 하는
**단일 유효본**이다. v64~v74 문서에 흩어져 있던 논의(초기 5분할
그리드 원안 → v67 축소 → v69/v72/v74 조정)를 여기 하나로
정리한다 — 과거 문서를 참고할 땐 반드시 이 파일이 최신인지
먼저 확인할 것(v72에서 겪은 "원안과 확정본을 혼동한" 혼선 재발
방지).

## 1. 메인 화면

시연 중 기본으로 떠 있는 화면. 카메라 영상과 비상정지가 항상
보여야 한다는 게 원칙.

```
전체 배경        videoCanvas (snapshot 폴링, 10fps, object-fit:contain)
좌상단           상태 텍스트(큰 글씨, 색 구분) + 경과시간 + "상세" 버튼
우상단           비상정지 버튼 + 캡션("위급 시 물리 버튼")
                 + 조작 버튼 4개(시작/일시정지/재개/종료)
                 + 알림 패널(활성 알림 있을 때만 보임)
```

**[팀결정 — v67] 좌상단은 상태 정보만.** 처리 집계·마지막 처리
결과·연결 상태 점·진행 단계는 전부 상세 페이지로 뺐다(v64 원안
5분할 그리드 대비 축소). **그리드 레이아웃이 아니라 각 요소가
독립적으로 `position: fixed`/`absolute`로 배치된 구조**다 —
그리드 컨테이너 자체가 없다(v72에서 "그리드 미적용"으로
오진단됐던 부분, 애초에 그리드를 쓴 적이 없다는 게 정확한 설명).

**[팀결정 — v74] 조작 버튼 4개 추가.** 음성이 안 먹힐 때 대비용
안전망 — 새 인터페이스 없이 `/voice_command`(std_msgs/String,
"START"/"PAUSE"/"RESUME"/"STOP")에 그대로 발행한다. 벨트/그리퍼/
홈복귀 개별 버튼은 넣지 않는다(START/STOP이 컨베이어까지
같이 제어하고, 그리퍼는 비상정지 후 노드 재시작으로 정리하기로
확정됐으므로 불필요 — v74 2-4절).

**상태별 색**: IDLE=회색, RUNNING=초록, PAUSED=노랑, STOPPING=주황.

## 2. 상세 페이지

메인을 완전히 덮는 화면 전환(모달 아님). "상세" 버튼 또는
30초 무조작 시 자동으로 메인 복귀(조작 시 타이머 리셋). 자체
비상정지 버튼도 우상단에 작게 둔다 — "어느 화면에서든 비상정지에
닿아야 한다"는 원칙(v67).

```
상단   [← 메인] 작업 현황 [상태 배지] [비상정지] 총 N건 · 실시간
       (자동복귀까지 남은 시간 카운트다운 함께 표시)
중앙   막대그래프 6개, 색 3종, 두 개의 분리선
하단   좌: 진행 단계 칩 + 마지막 처리 결과
       우: 연결 상태 점 5개(카메라/로봇/컨베이어/STT/TTS)
```

### 막대그래프 (v69/v72 확정)

```
정상 분류(초록)   플라스틱 통 / 캔 / 종이 / 건전지
사람 전달(파랑)   사람 전달        (pet_labeled 경로, human_handoff)
확인 필요(노랑)   확인 필요        (review_bin)
```
"일반쓰레기"(미검출 통과) 막대는 뺐다 — 클래스 무관 감지 수단이
없어 셀 방법 자체가 없다(v69 2절 확정, `passed` 필드도 뺌).
"플라스틱 통"으로 라벨을 구체화(단순 "플라스틱"이 아님) — 라벨
있는 페트병(시연 주력)은 이 막대가 아니라 "사람 전달"로 간다는
걸 헷갈리지 않게 하기 위함.

**막대 최댓값**: 고정 3, 6개 항목(정상4+사람전달1+확인필요1)
전체 기준 최댓값이 3을 넘으면 그 값까지 자동 확장. 숫자를
막대보다 크고 명확하게 표시.

**총 N건**의 의미 = `counts`(통 이름 기준 집계, 6개 항목 합) 전체
합 = 로봇이 실제로 처리한 개수(미검출 통과분 제외).

## 3. 데이터 (서버 -> 클라이언트)

`tracking_node.py`가 발행, 코드가 유일한 원본(source of truth) —
이 문서는 설명일 뿐이다.

```
/ui/state        (std_msgs/String, JSON, 0.5초 주기)
  ts, state, stage, counts(통 이름 키), total, last, reach_limit_px,
  health{camera,robot,conveyor,stt,tts}
/ui/alert        (std_msgs/String, JSON, 이벤트 발생 시)
  ts, level(warn|error), msg
/ui/detections   (std_msgs/String, JSON, 매 프레임)
  ts, w, h, items[{cls,conf,bbox,anchor,pending,required,locked}]
```

**[중요, 아키텍처 한계]** `_execute_pick`/`_place_item`/
`_handoff_item`이 `_on_image` 콜백 안에서 블로킹 실행되고
`tracking_node`는 단일 스레드 executor라, 파지~배치 구간
(17~24초)에는 위 세 토픽 전부 발행이 멈춘다. `ts`가 오래되면
클라이언트가 "처리 중" 등으로 알아서 표시해야 한다(구현
완료 — `web_ui/index.html`의 경과시간 로직 참고).

## 4. 영상 (web_video_server, rosbridge와 별개의 HTTP)

**[완료 — 8일차] snapshot 폴링 + canvas.** `<img>`(MJPEG multipart
미지원, 확인됨) → `<iframe>`(렌더링 불안정, 원인 미규명) → 현재
방식 순으로 시행착오를 거쳤다. `/snapshot?topic=...&type=jpeg
&t=<캐시무력화>`를 자기재귀 `setTimeout`으로 순차 폴링(동시에
최대 1개 요청, 이전 요청 완료 후 다음 예약)해 canvas에 그린다.
bbox 오버레이(아직 미구현)도 같은 canvas 위에 그릴 예정.

## 5. 비상정지

```
컨베이어 정지    /conveyor/stop 직접 호출 -- 확실히 즉시 정지
                (conveyor_node가 별도 프로세스, 확인됨)
로봇 정지 시도   dsr_msgs2/srv/MoveStop 직접 호출 -- 서비스 존재는
                확인됐으나 실제 인터럽트 여부는 [확인 필요](로봇
                실물 테스트 전)
```
**과대 청구 금지**: "웹 UI에도 정지 버튼이 있다"는 맞지만 "웹
UI로 즉시 멈출 수 있다"는 로봇 쪽은 아직 검증 전. 물리 비상정지가
최종 수단이라는 문구를 화면(캡션)과 문서 양쪽에 유지한다.

## 6. [전제, 미검증] 환경 의존 항목 — 개발 PC 결과를 그대로
   믿지 말 것

아래는 이번 세션 개발 PC(GPU 없음, 자원 소진 이력 있음)에서
얻은 결과라 관제 PC에서 재확인 필요:
```
snapshot 폴링이 실제로 안정적으로 뜨는지
canvas 갱신 성능(10fps 유지되는지)
YOLO 추론 속도에 따른 예측 타이밍(GPU 추론 fps 확정 후 재조정)
화면 해상도별 레이아웃(16:9 기준으로 만듦 -- 관제 PC 모니터
  비율 확인 필요)
```
아래는 환경과 무관하게 유효(코드/프로토콜 자체의 사실):
```
<img>의 multipart/x-mixed-replace 미지원 (fetch/naturalWidth로 확인)
/image_raw 구독 QoS depth=10 문제 및 qos_profile_sensor_data 수정
겹친 snapshot 요청 방지(자기재귀 설계)
그리드 미사용(설계상 애초에 없음)
```
