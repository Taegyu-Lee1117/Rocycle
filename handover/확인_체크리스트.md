## 1. 컨베이어 단독 (로봇·카메라 불필요)

```bash
python3 -m rocycle_robot.conveyor_node
# 다른 터미널에서
ros2 service call /conveyor/set_speed std_srvs/srv/Trigger "{}"
```
```
[ ] 서비스 응답 success=true
[ ] 벨트가 실제로 도는가(육안 확인)
[ ] ros2 service call /conveyor/stop std_srvs/srv/Trigger "{}" → 벨트 정지
[ ] ros2 topic echo /conveyor/status → state=RUN/STOP이 명령에 맞게 바뀌는가
```
**여기서 막히면**: 시리얼 포트 권한(`dialout` 그룹, 4-5절), 포트
경로(`/dev/ttyACM*` 등)부터 확인하세요.

## 2. 카메라 + YOLO (dry-run, 로봇 불필요)

```bash
# 카메라 노드
ros2 run usb_cam usb_cam_node_exe --ros-args \
  -p video_device:=/dev/video2 -p image_width:=1280 \
  -p image_height:=720 -p pixel_format:=mjpeg2rgb -p framerate:=30.0

# 다른 터미널 — 확인용
ros2 topic hz /image_raw   # 30 근처로 나오는가(YUYV로 잡히면 7.5 근처로 뚝 떨어짐)
```
```
[ ] /image_raw가 약 30Hz로 발행되는가(7~8Hz면 MJPEG가 아니라
    YUYV로 잡힌 것 — pixel_format 파라미터 확인)
[ ] tracking_node를 vision.dry_run=True로 띄운 뒤 로그에
    "class=... conf=... anchor=..." 가 물체를 비출 때 찍히는가
[ ] 추론 지연이 몇 ms/frame인지 로그로 확인(GPU면 CPU 대비
    훨씬 빨라야 함 — 이 값이 바뀌면 인수인계 문서 5-3절/
    motion_timing.yaml의 예측 타이밍 재조정 필요, 아래 5번 참고)
```

## 3. 음성 → 컨베이어 (로봇 불필요)

```
[ ] voice_bridge_node + tracking_node(dry_run 무관) 실행
[ ] 팀원 STT/TTS에서 "분리수거 시작해줘" → /voice_command에
    START 발행 확인(ros2 topic echo /voice_command)
[ ] tracking_node 로그에 "[VOICE] state=IDLE cmd='start'" →
    "conveyor on" 시도 로그가 찍히는가
[ ] 벨트가 실제로 도는가
[ ] "그만하자" → STOP → 벨트 정지 + 종료보고 로그(또는 /voice/tts/say
    발행)가 나오는가
```

## 4. [가장 중요] 좌표 검증 — 로봇 연결 후 가장 먼저

**여기서 크게 어긋나면 캘리브레이션이 제대로 안 옮겨진 것입니다.
그 이상 진행하지 마세요.**

```
[ ] 벨트를 세운 상태에서 물체(예: 캔)를 벨트 위 임의 지점에 놓는다
[ ] tracking_node 로그에서 anchor_pixel과 base 좌표(x,y,z) 확인
[ ] 로봇을 그 좌표 근처(호버 높이)로 수동 이동시켜 실제 물체와
    비교 -- 몇 mm 어긋나는가
[ ] 기대치: RMS 4.5mm, 최대 8.6mm 근방(캘리브레이션_안내.md 4절)
[ ] 이보다 크게(수 cm 이상) 어긋나면:
      - config/tracking.yaml의 camera.* 값이 원본과 같은지 재확인
      - calib_capture/T_cam2base.npy가 원본과 바이트 단위로
        같은지 확인(sha256sum으로 비교)
      - 카메라가 원래 마운트에서 움직이지 않았는지 확인
```

## 5. 캘리브레이션 값이 실제로 로드됐는지 로그로 확인

파일이 없거나 잘못 읽혀도 노드는 뜰 수 있습니다(디폴트값으로
조용히 넘어갈 위험) — 아래로 직접 확인하세요.

```bash
python3 -c "
import sys; sys.path.insert(0, '<rocycle_robot 경로>')
from rocycle_robot.tracking_node import TrackingNode
import rclpy
rclpy.init()
node = TrackingNode()
print('calibrated:', node._is_calibrated())
print('cam_to_base shape:', None if node._cam_to_base is None else node._cam_to_base.shape)
print('belt_plane:', node._belt_plane)
node.destroy_node(); rclpy.shutdown()
"
```
```
[ ] calibrated: True
[ ] cam_to_base shape: (4, 4)
[ ] belt_plane이 (0,0,0,0)이 아닌 실제 값
```
`tracking_node up. calibration ready=True ...` 시작 로그로도
같은 걸 확인할 수 있습니다(`False`면 파라미터가 안 먹은 것).

## 6. 정지 상태 파지 → 이동 벨트 파지 (실물 로봇 필요)

```
[ ] 벨트를 세우고 물체를 놓은 뒤 dry_run=False로 파지 시도 → 성공
[ ] 벨트를 돌리며 같은 물체로 파지 시도 → 성공
[ ] 실패 시 CLAUDE.md "알려진 함정"/"현재 확정값" 절부터 검색
    (특히 MoveLine success=True인데 실제로 안 움직이는 함정,
    그리퍼 파지력 세션 유지 함정)
```

## 7. GPU 추론 속도 반영 (관제 PC 고유 확인사항)

```
[ ] 2번 단계에서 측정한 추론 지연(ms/frame)을 기록
[ ] motion_timing.yaml의 travel_time_sec/descent_time_sec은
    로봇 이동 속도값이라 GPU와 무관 -- 그대로 둘 것
[ ] 단, 검출 지연(확정까지 걸리는 시간)이 크게 줄면
    vision.yaml의 min_consecutive_frames(현재 9)를 다시 튜닝할
    여지가 있음(CPU ~1fps 전제로 잡은 값) -- 로봇 팔 제어 담당과
    상의해서 재조정할 것, 임의로 줄이지 말 것(예측 정확도와
    트레이드오프가 있었던 값)
```
