# 8일차 인수인계 — 관제 화면 UI + 핸드오버 안전 수정

[원문] = 확인된 사실  [추론] = 판단  [전제] = 미검증 가정

이 문서는 사용자가 개발 PC에서 관제 PC로 이동하기 직전에
작성됐다. **관제 PC의 Claude는 이 문서부터 읽고 시작할 것** —
`CLAUDE.md`(`docs/CLAUDE.md`)의 "현재 단계"/"다음 세션 최우선
순서"와 내용이 겹치니, 자세한 배경은 그쪽을 참고하되 여기서는
"지금 뭘 해야 하는가"만 압축해서 정리한다.

## 지금 해야 할 일 (사용자 계획)

```
1. 관제 PC로 이동
2. DB 스키마 + UI 연동을 시각적으로 확인
3. 나머지 실물 테스트 진행(핸드오버 재검증 포함)
```

## 1. 관제 화면 UI (오늘 신규)

`ros2/rocycle_robot/web_ui/` 폴더 신규 — `index.html` 하나짜리
정적 페이지. **먼저 `web_ui/README.md`(기동 절차 + 확인
체크리스트)와 `web_ui/관제화면_UI설계안.md`(설계 전체, 이게
유일한 최신 설계 기준 문서)를 읽을 것.**

핵심만 요약:
```
포트 3개 필요: rosbridge(9090), web_video_server(8080),
              web_ui 정적 서버(8000, python3 -m http.server)
메인 화면: 영상(canvas, snapshot 폴링) + 상태 + 경과시간 +
          비상정지 + 조작버튼 4개(시작/일시정지/재개/종료,
          /voice_command로 발행) + 알림 패널
상세 화면: 막대그래프 6개(정상분류4/사람전달1/확인필요1) +
          진행단계 + 마지막처리 + 연결상태 5개, 30초 자동복귀
```

**[전제, 미검증] 이 개발 PC엔 실카메라/실로봇이 없어서 검증이
제한적이었다** — 특히 영상(snapshot 폴링)이 실제로 안정적으로
뜨는지는 개발 PC 자체가 세션 후반 자원 소진 상태(TCP TIME_WAIT
급증, 메모리 부족)였어서 결과를 신뢰하기 어려웠다. **관제 PC에서
처음부터 다시, 자원이 정상인 상태에서 확인할 것.**

`web_ui/README.md`의 "환경 의존/환경 무관" 절을 반드시 참고 —
개발 PC에서 얻은 결론 중 어느 게 재확인 대상인지 구분해뒀다.

## 2. [안전, 최우선] 핸드오버(`pet_labeled`) 릴리즈 판정 재작성

**오늘 관제 PC 실물 테스트 중 실제로 사고가 있었다** — 사람이
받지 않았는데 약 3초 만에 그리퍼가 열려 라벨 페트병이 낙하했다
(로그 미확보, 재현 상황으로 원인 추정). CLAUDE.md에 이미 기록된
6일차 사고("순응모드 진입 자체의 중력 처짐을 당김으로 오인")와
같은 유형의 재발로 강하게 추정한다.

**수정 이력(오늘 하루에만 두 번 더 고쳤다)**:
```
1차 수정(6일차, 기존)  진입 + 고정 0.5초 대기 후 기준점 캡처
2차 수정(8일차 오전)   위치가 실제로 멈출 때까지(적응형) 대기
                       → 이것도 "변화율 조건"일 뿐이라 느린
                         크리프가 누적되면 여전히 오탐 가능
                         (실물 재현 전에 이론적으로 지적받음)
3차 수정(8일차, 현재)  **판별 기준을 "누적 변위(총량)"에서
                       "수평 이동 속도"로 전환** — 사람이
                       당기는 건 빠르고(추정 20~50mm/s), 중력
                       처짐은 느리다(6일차 실측 평균 약 3.7mm/s)
```

`_handoff_item()`(`rocycle_robot/tracking_node.py`) 현재 로직:
릴리즈 = (수평 속도가 연속 2회 이상 `pull_speed_mm_per_s`=15.0
mm/s 이상) **AND** (시작점 대비 누적 3D 변위가
`release_threshold_mm`=10mm 이상). 값은 전부
`config/item_routing.yaml`의 `handoff:` 절.

**[전제, 미검증] `pull_speed_mm_per_s`=15.0은 추정치다** — 실측
3.7mm/s(처짐)와 추정 상한(당김) 사이 중간값으로 잡았을 뿐,
로봇 실물로 두 조건(처짐만/실제 당김)의 속도 분포를 재본 적이
없다. **매 폴링마다 상세 로그**(경과시간/좌표/누적변위/수평
스텝거리/dt/수평속도/연속카운트)를 남기도록 해뒀으니, 다음
테스트에서 **반드시 터미널 로그를 저장**할 것:
```bash
ros2 launch ... 2>&1 | tee handoff_test_$(date +%H%M).log
```
로그 없이 사고가 나면 이번처럼 원인을 추정으로만 답하게 된다.

**[팀결정] 타임아웃(15초 안에 안 받아감) 시 동작도 바뀌었다** —
이전엔 제시 높이 허공에서 그냥 열어 물체가 떨어졌는데, 지금은
정상 배치와 같은 3단계 시퀀스(상승→이동→하강)로 `review_bin`
(확인 필요 통)에 넣는다.

**[중요] 핸드오버 10회 연속 무사고 검증은 사실상 처음부터 다시
센다.** 이전 "3회 성공" 기록은 오늘 고친 것과 같은 결함을 안은
채 우연히 통과했을 가능성이 있어 신뢰할 수 없다.

## 3. DB 스키마 연동 (미확인 — 관제 PC에서 확인 필요)

DB 담당자가 스키마를 git에 커밋했다고 하는데, **`rocycle`
(이 저장소)에도 `origin`(ROKEY-Team-Project 모노레포, 완전히
다른 서브프로젝트)에도 fetch해서 찾아봤지만 안 보였다** — 아직
어느 저장소/브랜치에 올라갔는지 이 개발 PC에서는 확인 못 했다.
관제 PC에서 DB 담당자에게 정확한 위치를 다시 확인할 것.

확인되면 CLAUDE.md의 "**[팀결정 — v47]**" 항목(`pet_bottle_*` ->
`pet_labeled`/`pet_unlabeled` 클래스명 변경이 DB 규격 v2에 아직
반영 안 됐을 수 있다는 미해결 사항)과 이름이 일치하는지부터
대조할 것.
