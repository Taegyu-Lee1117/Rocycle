# 로봇 제어 시스템 인수인계 — 관제 PC 이관용

> 로봇 팔 제어 담당 → STT/TTS 담당(관제 PC 소유자)
> 컨베이어 기반 재활용 분류 협동로봇

---

## 0. 이 문서에 대해

**그쪽 랩탑을 관제 PC로 쓰기로 했습니다.** GPU가 있어서 YOLO 추론에
유리하고, STT/TTS도 이미 그쪽에 있기 때문입니다.

**저희가 지금까지 만든 것을 그쪽으로 옮기려고 합니다.**
이 문서는 무엇을 옮기고 어떻게 세팅하는지 설명합니다.

**5절(반드시 알아야 할 것)이 가장 중요합니다.** 8일간 실기로
부딪히며 알아낸 것들이라, 모르면 원인을 못 찾고 오래 헤맵니다.

표기: **[실측]** 실기로 확인한 값 / **[추론]** 판단이나 미검증 /
**[협의]** 함께 정해야 할 것

## 1. 시스템 개요

컨베이어로 흘러오는 재활용 쓰레기를 로봇팔이 집어 종류별 통에
넣습니다.

```
음성 "분리수거 시작해줘"
  → 컨베이어 가동
  → 고정 카메라(C270)가 물체 검출 (YOLO12s)
  → 칼만 필터로 추적하며 도착 위치 예측
  → 로봇이 예측 지점에서 파지
  → 무게 측정 (캔만)
  → 종류에 맞는 통에 배치
  → 음성 "그만하자" → 결과 보고
```

**분류 통 5개**
```
plastic_bin / can_bin / paper_bin / battery_bin / review_bin
```
`review_bin`은 "확인 필요" 통입니다. 로봇이 판단은 했으나 처리할
수 없는 것들이 모입니다.

**대상 품목 6종**
```
can              캔
pet_labeled      페트병 (라벨 있음)  → 사람에게 전달
pet_unlabeled    페트병 (라벨 없음)
paper            종이 상자
battery          건전지 (AA)
plastic_bag      묶인 비닐          → review_bin
```

**학습하지 않은 물체는 검출되지 않고 벨트 끝 일반쓰레기통으로
그냥 떨어집니다.** 의도된 동작입니다.

## 2. PC 역할 분담

### 2-1. 목표 구성

```
[관제 PC — 그쪽 랩탑]
  C270 고정 카메라
  YOLO12s 추론
  물체 추적 + 예측
  컨베이어 제어 (시리얼)
  STT / TTS

[로봇 PC — 현재 저희 PC]
  두산 M0609 로봇팔
  OnRobot RG2 그리퍼
  RealSense 손목 카메라
```

### 2-2. [협의] 로봇 명령이 네트워크를 건넙니다

**현재 코드는 한 노드(`tracking_node`)에 검출부터 로봇 제어까지
전부 들어 있습니다.**

이걸 관제 PC로 옮기면 **로봇 명령이 ROS2 서비스로 네트워크를
타게 됩니다.**

```
관제 PC의 tracking_node → (네트워크) → 로봇 PC의 DSR 서비스
```

**저희 판단**
```
지연은 문제없을 것 [추론]
  LAN 왕복 수 ms, 파지 사이클이 17~24초
위험한 것
  사이클 도중 네트워크가 끊기면 로봇이 물체를 든 채 멈춤
```

**일단 통째로 옮겨서 동작을 확인하고, 문제가 생기면 노드를
쪼개는 방향을 제안합니다.**

노드를 쪼갠다면 이렇게 됩니다.
```
관제 PC   검출 + 추적 + 예측 → 좌표 발행
로봇 PC   좌표 수신 → 로봇 실행
```

**설계 문서에는 원래 이 구조로 되어 있습니다.** 다만 구현이 한
노드로 되어 있어, 지금 쪼개면 검증된 코드를 크게 건드리게 됩니다.

### 2-3. [협의] 음성 노드 위치

**STT/TTS가 관제 PC에 있으므로 `/voice_command`도 거기서
발행됩니다.**

`tracking_node`가 이 토픽을 구독해 상태를 전이합니다
(IDLE → RUNNING 등). **같은 PC에 있으면 네트워크를 안 탑니다.**

**2-2절에서 노드를 쪼갠다면 상태 머신을 어디에 둘지 다시
정해야 합니다.**

## 4. 환경 구축

### 4-1. 기본 환경

```
Ubuntu 24.04
ROS2 Jazzy
ROS_DOMAIN_ID=30
RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
```

**그쪽 환경과 이미 일치합니다.**

### 4-2. [중요] pymodbus 버전 제약

```bash
pip install --break-system-packages "pymodbus<3.10"
```

**3.10 이상이면 그리퍼가 동작하지 않습니다.**
`read_holding_registers()`의 파라미터 이름이 바뀌어 호환되지
않습니다. 실사용 3.9.2입니다.

**다만 그리퍼는 로봇 PC에 붙으므로, 관제 PC에는 불필요할 수
있습니다.** 2-2절 구조에 따라 달라집니다.

### 4-3. PyTorch

**GPU가 있으니 CUDA 버전을 쓰시면 됩니다.**

저희 PC에는 GPU가 없어 CPU 전용으로 설치했고, **추론이 약 1fps**
였습니다. GPU에서는 훨씬 빠를 것으로 기대합니다.

**[중요] 추론 속도가 빨라지면 예측 타이밍을 다시 맞춰야 합니다.**
5-3절 참고.

### 4-4. 카메라

```
C270 웹캠
/dev/video* 번호는 재부팅 시 바뀔 수 있음
→ /dev/v4l/by-id/ 경로로 고정 권장

MJPEG로 잡아야 1280x720 30fps가 나옴
YUYV는 대역폭 때문에 프레임이 떨어짐
```

### 4-5. 컨베이어

```
아두이노 스테퍼 드라이버, USB 시리얼
/dev/ttyUSB* 또는 /dev/ttyACM*
접근에 dialout 그룹 필요:
  sudo usermod -aG dialout $USER   (후 재로그인)
```

**[실측] 100 steps/sec = 2.0 cm/s** 입니다. 이 값으로 고정해
운영합니다.

## 5. 반드시 알아야 할 것

**저희가 시간을 많이 쓴 것들입니다. 모르면 같은 데서 막힙니다.**

### 5-1. 캘리브레이션 데이터를 새로 만들지 마세요

**가장 중요합니다.**

```
좌표 정확도    RMS 4.5mm (실측 검증 완료)
벨트 평면      5점 티칭, 잔차 0.334mm
```

**세 번 실패한 끝에 얻은 값입니다.**
```
1차  솔버 버그로 157mm 오차
2차  깊이 다양성 부족으로 8~23cm 오차
3차  마운팅 재현성 한계로 악화
최종 실측 기반 경험적 보정으로 4.5mm 확보
```

**AI가 "값이 없으니 추정하겠다"고 하면 막아주세요.**
그럴듯한 숫자를 채워 넣으면 로봇이 엉뚱한 곳으로 갑니다.

### 5-2. 그리퍼 관련 함정 셋

**닫기 명령이 비동기입니다.**
```
"c" 명령은 물리적으로 다 닫히기 전에 반환됩니다
직후 상승하면 물체를 놓칩니다
파지력에 따라 1~2초 대기가 필요합니다
```

**파지력이 세션 내내 유지됩니다.**
```
한 번 설정하면 자동으로 리셋되지 않습니다
매 파지 직전에 그 품목의 값을 명시적으로 설정해야 합니다
```

**파지력을 낮추면 닫히는 속도도 느려집니다.**
```
기본값(약 40N)  1초 대기
낮춘 값(10N)    2초 대기
두 값은 연동됩니다
```

### 5-3. 예측 타이밍 관리 원칙

**칼만 필터가 "언제 잡을지"를 예측해 그 시점의 위치로 갑니다.**

```
예측 시간 = 검출 지연 + 로봇 이동 + 하강 + 그리퍼 닫힘 + 기타
```

**예측 계산 이후 파지 전에 실행되는 모든 동작은 이 시간에
포함되어야 합니다.**

포함하지 않으면 예측이 그만큼 뒤처져, 물체의 뒷부분만 잡거나
아예 놓칩니다. **저희가 실제로 겪은 문제입니다.**

**현재 포함 항목**
```
그리퍼 열기
파지력 정규화
baseline 무게 측정
```

**새 동작을 추가할 때 반드시 확인하세요.**

**그리고 GPU로 추론이 빨라지면 검출 지연이 줄어듭니다.**
이 값도 다시 재서 반영해야 합니다.

### 5-4. `MoveLine`이 성공을 반환하면서 안 움직입니다

```
시작점과 끝점이 각각 도달 가능해도
그 사이 직선 경로가 관절 한계를 넘으면
success=True를 반환하면서 로봇이 전혀 안 움직입니다
```

**매 이동 후 `get_current_posx()`로 실제 이동을 확인해야 합니다.**

### 5-5. 통에 넣은 뒤 바로 옆으로 움직이면 통을 밉니다

```
반드시: 수직 상승 → 수평 이동 → 수직 하강
```

**실제로 통을 밀어 넘어뜨린 적이 있습니다.**

### 5-6. 벨트는 입체 구조물입니다

```
"얇은 평면"이 아니라 테이블면부터 벨트면까지 차지합니다
로봇이 벨트를 눌러 손상시킬 뻔한 사고가 있었습니다
obstacles.yaml에 정의되어 있습니다
```

**목표 좌표가 구조물 안이면 명령을 거부합니다.**
이 검사는 최종 목표점만 봅니다. 경로 중간은 안 봅니다.

### 5-7. 벨트가 물리적으로 움직이면 좌표가 전부 어긋납니다

```
벨트가 밀린 적이 있어 재작업이 필요했습니다
작업 전에 벨트가 고정되어 있는지 확인하세요
```

### 5-8. 안전 정지 복구

**순응 제어(핸드오버) 중 외력을 가하면 로봇 서보가 꺼질 수
있습니다.**

```
1. ROS2 API로 리셋 시도
   ※ success=True를 반환해도 실제로 안 풀릴 수 있습니다
2. 안 풀리면 티치펜던트에서 오류 팝업 닫고 "서보 켜기"
3. 그래도 ROS2가 계속 SAFE_OFF를 보고하면
   로봇 스택 재기동
```

**`reset_workpiece_weight` 서비스는 호출하지 마세요.**
호출 후 무관한 서비스까지 전부 타임아웃된 사고가 있었습니다.

## 6. 검증 순서

**한 번에 다 연결하지 마세요.** 문제가 생기면 원인을 못 찾습니다.

### 6-1. 컨베이어 단독

```
conveyor_node 실행
ros2 service call /conveyor/set_speed ...
→ 벨트가 도는가
```

**로봇·카메라 불필요.**

### 6-2. 카메라 + YOLO (dry-run)

```
로봇에 명령을 보내지 않는 모드로 실행
화면에 클래스, 신뢰도, bbox가 표시되는가
추론 지연이 몇 ms인가  ← 5-3절에 반영 필요
```

**로봇 불필요.**

### 6-3. 음성 → 컨베이어

```
"분리수거 시작해줘" → 벨트가 도는가
"그만하자" → 벨트가 멈추고 보고가 나오는가
```

**로봇 불필요.**

### 6-4. 좌표 검증

**로봇 연결 후 가장 먼저 할 것입니다.**

```
벨트를 세운 상태에서 물체를 놓고
카메라가 산출한 좌표로 로봇을 보낸다
실제 물체와 몇 mm 어긋나는가
```

**여기서 크게 어긋나면 캘리브레이션 데이터가 제대로 이관되지
않은 것입니다.** 그 이상 진행하지 마세요.

### 6-5. 정지 상태 파지 → 이동 벨트 파지

```
벨트를 세우고 파지 → 성공하면
벨트를 돌리며 파지
```
