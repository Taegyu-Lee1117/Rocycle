## 1. 작업1 — 환경 확인 결과
====================================================================

- **[실측] 이 PC에 GPU 없음** — `nvidia-smi` 없음, 내장그래픽
  Intel UHD 620만 확인(CLAUDE.md에 이미 기록).
- **[실측] `pip install -r requirements.txt`가 부수적으로 환경을
  깨뜨림 — 발견·해결함.** `ultralytics`가 최신 `opencv-python`을
  받는데 이게 `numpy>=2`를 요구해서, 이 PC의 `cv_bridge`(numpy 1.x
  기준 컴파일)가 깨졌다. **해결: pip `opencv-python` 제거, 시스템
  `python3-opencv`(4.6.0, apt)+`numpy<2`로 복귀** — ultralytics
  동작엔 지장 없음(실측 확인). 재설치할 일이 있으면 이 순서를
  반복해야 함.
- `ultralytics`/`torch`(CPU)/`opencv` 설치 자체는 완료.

## 2. 작업2 — C270 dry-run 결과 (4-3절 확인 3항목 전부 완료)
====================================================================

### 2-1. anchor_pixel 위치 — 정상

can/pet_labeled/pet_unlabeled 전부 bbox 하단중앙(벨트 접점)에
정확히 찍힘. 설계 의도대로 동작.

### 2-2. 미학습 물체 오검출 — 발생하지만 저신뢰도

휴지심(원통형 흰색 물체)을 벨트에 단독으로 올렸더니 10프레임 중
8회 `pet_labeled`로 오검출됐다. **단 신뢰도가 0.28~0.30으로 낮다**
— conf 임계값을 0.6~0.7로 올리면 이 오검출은 걸러진다(직접 확인).
**계획했던 대응(작업3의 conf 상향)이 이 문제엔 실제로 유효함을
실측으로 확인했다.**

### 2-3. [중요, 신규 발견] pet_labeled/pet_unlabeled 고신뢰도 오분류

라벨이 전혀 없는 실제 페트병(투명, 어떤 인쇄물도 없음)을 벨트에
올렸더니 10프레임 전부 `pet_labeled`로 오분류됐다 — **신뢰도
0.941~0.942로 상당히 높다.** 같은 세션에서 진짜 라벨 있는 병은
0.964~0.965로 나와 두 값의 차이가 크지 않다.

**이건 2-2와 다른 종류의 문제다** — conf 임계값을 아무리 올려도
0.94는 걸러지지 않는다. README/`model_info.json`이 이미 경고한
"pet_unlabeled 일부가 pet_labeled로 판단될 수 있다"(신규 이미지
평가 14/16=87.5%)는 것이 실물 실측에서도 재현됐다.

**[추론] 실패 방향은 상대적으로 안전한 쪽이다** — 이 오분류는
"자동 재활용 대상을 사람 전달로 잘못 보냄"이지 그 반대(라벨
있는 걸 자동재활용으로 보냄)가 아니다. 자동재활용 성공률은
낮아지지만 위험한 방향의 오류는 아니다.

### 2-4. 추론 지연시간 — 목표 미달

CPU 추론 평균 **~1.0fps**(웜업 프레임 제외 600ms~2s/frame, 10~15
프레임 반복 측정 2회 기준). v45가 기대한 "CPU 3~10fps"에 못
미친다. 이전 방식(사람이 이미지 보고 판단, 50초+)보다는 압도적
으로 빠르지만, "칼만 필터가 제대로 돈다"는 원래 목표(초당 여러
프레임 갱신)에는 아직 부족하다.

## 3. 결정 필요 사항 3건
====================================================================

### 3-1. conf 임계값 0.6~0.7 확정?

2-2 결과로 계획대로 진행해도 될 근거는 확보됨. **이견 없으면
0.6으로 확정하고 `config/`에 외부화하겠음.**

### 3-2. pet_labeled/pet_unlabeled 고신뢰도 오분류를 어떻게 할까?

옵션이 여러 개 있어 보임:
```
(a) 알려진 한계로 문서화만 하고 그대로 진행
    — 실패 방향이 안전한 쪽이라는 3-1c의 판단에 기댐
(b) 학습 담당 팀원에게 이 두 클래스 데이터 보강 요청
    — 시간이 얼마나 남았는지에 달림
(c) 보조 판정 추가(예: 라벨 영역 픽셀 비율/색상 분산 등 간단한
    후처리 규칙으로 모델 출력을 보정) — 설계 원칙3(외부화)·
    원칙6(과대청구금지)과 어떻게 맞을지 검토 필요
```
**어느 쪽으로 갈지, 혹은 다른 안이 있는지 의견 요청.**

### 3-3. CPU ~1fps로 통합 진행 vs GPU PC 분리를 지금 실행

두 갈래:
```
(a) 일단 이 속도로 통합·검증 진행 — 벨트 저속(2cm/s) 기준으로는
    50초보다 압도적으로 나으므로 "우선 되게 만들고" 나중에
    GPU PC로 옮기며 속도 개선
(b) 지금 GPU PC 분리를 실행 — 관제 PC를 실제로 GPU 있는 별도
    PC로 옮긴 뒤 작업 계속. 팀에 GPU PC가 실제로 준비돼 있는지
    확인 필요(CLI 쪽에서는 확인 불가)
```
**시간 예산(오늘 10시간 중 남은 시간)과 실제 GPU PC 가용 여부에
따라 다를 것 같아 방향 요청.** CLI 판단으로는 (a)로 가되 사이클
시간에 검출 지연이 그대로 들어가므로(현재 20.8초 사이클에 초당
1프레임씩 최대 1초 지연 추가되는 정도) 큰 문제는 아닐 것으로
봄[추론] — 단 실제 예측 정확도는 통합 후 재검증 필요.
