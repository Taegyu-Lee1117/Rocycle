1. 요청1 — 막대 6개/색 3종 반영
===============================================================
**[완료]** 구현대로 정리:
```
정상 분류 (초록, --ok)
  플라스틱 통   plastic_bin
  캔           can_bin
  종이         paper_bin
  건전지        battery_bin
────────────────────────────
사람 전달 (파랑, --handoff #378add)
  사람 전달     human_handoff
────────────────────────────
확인 필요 (노랑, --review)
  확인 필요     review_bin
```
최댓값(`barMax`)은 6개 항목 전체(정상4+사람전달1+확인필요1)
기준으로 동일하게 계산해서 그룹 간 막대 길이가 서로 비교 가능
하게 뒀다 -- 그룹별로 다른 스케일을 쓰면 "사람전달 막대가 확인
필요 막대보다 길어 보이는데 실제 개수는 더 적다" 같은 왜곡이
생길 수 있어서다.

**라벨 정리 (1-5절 반영)**: "플라스틱" -> **"플라스틱 통"**으로
변경. 캔/종이/건전지는 다른 목적지와 헷갈릴 여지가 없어 그대로
뒀다. "사람 전달"은 원안 그대로 채택(통 이름이 아니라 실제 동작을
설명하는 편이 더 명확하다고 판단).

**1-4절(0으로 남는 것 유지)도 그대로 반영** — 코드에서 `plastic_bin`
막대를 숨기는 조건분기는 넣지 않았다. `counts`에 값이 없으면
`0`으로 렌더링되고 라벨은 항상 보인다.

3. 요청4(3절) — executor 종류, 로봇 없이 확인한 결과
===============================================================
**[실측]**
```bash
ps -T -p 71033 | wc -l   # ros2_control_node PID (어제부터 떠있음)
```
결과: **총 27개 스레드.** 이름을 분류하면:
```
Cyclone DDS 내부 스레드(~10개): gc, dq.builtins, dq.user, tev,
  recv, recvMC, recvUC, ust* 등 -- executor 종류와 무관하게 항상
  존재하는 것들
"ros2_control_no"(이름 잘림, ros2_control_node) 이름 스레드:
  ~17개 -- 이게 executor/노드 자체가 만든 스레드
```
**[추론] 17개는 SingleThreadedExecutor(스레드 1개)로는 설명이
안 되는 숫자다** — 최소한 여러 스레드가 동시에 존재하는 건
확실하고, 이는 `MultiThreadedExecutor` 또는 그에 준하는 스레드
풀 구조를 쓰고 있다는 정황 증거다. **다만 v69 3-2절이 이미
지적했듯 이건 결정적 증거는 아니다** — `ros2_control`의
실시간 제어 루프, 하드웨어 인터페이스 스레드 등 executor와 무관한
이유로도 스레드가 늘어날 수 있다. `apt-get source`용
`deb-src`가 이 시스템에 설정돼 있지 않아(`ros2_control_node.cpp`
소스 파일도 로컬에 없음 확인) 소스 대조는 못 했다 -- 3-4절
지적대로 우선순위가 낮아 여기서 멈추고 실동작 테스트로 넘긴다.

**결론: "가능성이 높다"는 심증은 하나 더 늘었지만("스레드가
여럿" 자체는 확인됨), "그래서 move_stop이 move_line을 실제로
인터럽트한다"는 여전히 실측 전까지 확정 아님.**

4. 요청3 — 알림 패널 연결 여부 확인
===============================================================
**[정정, 솔직한 답] 확인해보니 "하드코딩된 예시"조차 아니었다
— v68 시점 코드에는 알림 패널 자체가 없었다.** `/ui/alert`
구독 콜백은 `console.warn`만 찍고 화면에는 아무것도 안 그리고
있었다(v68 4절에서 이미 "다음 단계"로 남겨뒀던 부분 맞음, 다만
"패널이 이미 있다"는 전제 자체가 틀렸었다).

**[완료]** 이번에 실제로 만들어 연결했다 — `/ui/alert`를 구독해
우상단(비상정지 버튼 아래)에 최근 4개까지 스택으로 쌓고, 10초 뒤
서서히 사라지게 했다. `error`는 빨간 테두리, `warn`은 노란
테두리로 구분. 새 토스트 컴포넌트가 아니라 요청하신 대로 "기존
패널에 연결"하는 형태로 만들었다(패널 자체를 이번에 처음
만든 것뿐, 별도 팝업/모달 방식은 아님).

===============================================================
5. 요청4 — 나머지 반대 의견 답변
===============================================================

**"색을 셋으로 늘리는 게 적절한가 -- 사람전달을 초록에 넣어도
되는가"**
동의한다, 셋이 맞다. 초록에 합치면 "로봇이 통에 넣어 완결"과
"사람이 받아가서 완결"이 시각적으로 구분이 안 되는데, 이 둘은
실제로 **누가 마지막 동작을 했는지**가 다르다(하나는 순전히
로봇 자율 동작, 하나는 사람 개입이 필요한 핸드오버) -- 시연에서
"로봇이 어디까지 스스로 하는지"를 보여주는 게 중요하다면 이
구분이 그대로 정보값이 있다고 본다.

**"플라스틱 0 막대를 남기는 게 적절한가"**
동의(위 1절 참고). 추가로: 만약 시연 중 실수로 무라벨 페트병이
잡혀 plastic_bin으로 갔다면, 그건 CLAUDE.md의 "무라벨은 고신뢰도
오분류 확인됨" 항목과 관련된 흥미로운 신호일 수 있어서(예상과
다른 경로로 갔다는 것 자체가 로그성 정보) 막대를 없애기보다는
남겨서 "0이 아니게 됐다"를 보이게 하는 게 오히려 유용하다고
생각한다.

**"executor 확인이 지금 할 가치가 있는가"**
스레드 수 확인 정도(1분 안팎, 로봇/코드 변경 무관)는 위험이
전혀 없어 바로 했다. 그 이상(소스 대조, apt-get source)은
3-4절 판단대로 보류하는 게 맞다고 본다 -- 실동작 테스트가 어차피
최종 확인이고, 지금 단계에서 시간을 더 쓸 가치가 낮다.
