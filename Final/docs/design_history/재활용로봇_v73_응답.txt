1. 요청1 — 2-2절 CDP 확인 결과 (실측)
===============================================================
Chromium 헤드리스 + CDP로 정확히 요청하신 항목들을 확인했다
(로봇/카메라 불필요, 말씀대로 진행 가능했음).

```
grid_elements: ""                     <- 빈 문자열!
```
**[실측, 결정적] 페이지 전체에서 `display: grid`인 요소가
단 하나도 없다.** `index.html`에 "grid"라는 단어 자체가 아예
없다(grep 확인) — **CSS Grid를 애초에 쓴 적이 없다.**
v67에서 메인 화면을 "상태/경과시간/상세버튼 세 가지뿐"으로
줄인 이후, 실제 구현은 그리드가 아니라 **`position: fixed`/
`position: absolute` 오버레이 방식**으로 배치했다(각 요소가
독립적으로 화면 특정 위치에 떠 있는 구조, 그리드 컨테이너 자체가
없음). "그리드가 형성 안 됐다"가 아니라 **"애초에 그리드를 쓰는
설계가 아니다"**가 정확한 진단이다.

```
mainScreen_display: "block"
mainScreen_position: "absolute"
mainScreen_rect: {x:0,y:0,width:1280,height:657}   <- 정상, 전체 뷰포트
```
mainScreen 자체는 정확히 코드대로(`position:absolute; inset:0`)
전체 화면을 차지하고 있다 — 레이아웃이 깨진 게 아니라 **설계된
그대로 렌더링되고 있다.**

```
alertPanel_rect: {x:960,y:100,width:300,height:0}
alertPanel_children: 0
```
**알림 패널이 "안 보이는" 건 버그가 아니라 정상 동작이다.**
CSS가 `display:flex`인 빈 컨테이너라 자식이 0개면 height도 0이
돼 화면에 아무것도 안 그려진다 — 활성 알림이 있을 때만 내용이
채워지는 설계(v70에서 구현)가 그대로 동작하는 것뿐이다.

```
panel_class_count: 0
```
이건 **셀렉터 불일치**다 — 내 코드는 `class="panel"`을 쓴 적이
없고 전부 고유 id(`alertPanel`, `chartArea`, `bottomArea`,
`stageBox`, `healthBox` 등)로 참조한다. "패널이 없다"가 아니라
"panel이라는 클래스명 자체가 이 코드에 없다"가 정확하다.

```
app_innerHTML_head (일부):
  <div id="mainScreen">
    <canvas id="videoCanvas" width="1280" height="657"></canvas>
    <div id="videoPlaceholder" style="display: none;"></div>
    <div id="statusBar">
      <div id="stateText">대기 중</div>
      ...
```
코드가 의도한 그대로 DOM이 구성돼 있다.

**결론: "조작 버튼이 안 보인다"는 진단도 오해다** — v67에서
확정한 메인 화면 스펙(1-2절: "상태/경과시간/상세버튼, 세 가지
뿐이다")에 애초에 조작 버튼(START/PAUSE/RESUME/STOP류) 자체가
없다. 원래 v64 설계안(초기 5분할 그리드 + 조작 버튼)과 v67이
확정한 축소안이 다른데, Firefox 확인 시 **v64 원안 기준으로
비교하신 것 같다** — v67로 합의된 이후 메인 화면은 의도적으로
저렇게 단순해진 게 맞다. 조작 버튼이 필요하다면 그건 "누락된
버그"가 아니라 "v67에서 뺀 걸 다시 넣을지"의 **새로운 설계
결정**이 필요한 사안이다 — 아래 요청 드린다(요청1 참고).

2. [중요, 방향 전환] 이 개발 PC 자체가 소진 상태였다 —
   지금까지의 렌더링 문제 상당수가 여기서 비롯됐을 가능성
===============================================================
snapshot 폴링을 구현하고 검증하던 중, 예상 못 한 일이 있었다:

**2-1. 첫 구현(`setInterval`로 100ms마다 새 Image() 생성)에서
전부 `net::ERR_EMPTY_RESPONSE` 실패**
CDP Network 도메인으로 직접 확인 — 100% 실패. curl로 순차 15회/
동시 10회 요청은 전부 200 정상이라 **처음엔 "겹친 요청이 문제"**
라고 진단하고, 이전 요청이 끝난 뒤에만 다음 요청을 예약하는
자기재귀 `setTimeout` 방식으로 고쳤다(코드는 유지 — 이 자체는
분명한 개선이라 되돌리지 않았다, 3절 참고).

**2-2. 그런데 고친 뒤에도 여전히 100% 실패했다**
이때 시스템 상태를 다시 확인해보니:
```
[실측] TCP: 598 (established 21, TIME_WAIT 564)
[실측] 여유 메모리 463MB, swap 2.7GB 사용 중
[실측] load average 9~13 (8코어 기준 매우 높음)
```
**TIME_WAIT 소켓 564개**는 비정상적으로 많다 — 오늘 세션 내내
반복한 자동화 헤드리스 테스트(수십 번의 Chromium 재시작, 초당
여러 번씩 반복한 스크린샷/네트워크 요청)가 누적되며 이 PC의
연결 상태 자체를 소진시킨 것으로 보인다[추론, 확정 아님].

**[정정 요청, v71 2절 재검토]** v71에서 "iframe이 실제 창에서도
렌더링이 불안정했다"고 보고했는데, 돌이켜보면 **그 테스트들도
전부 이 소진된 상태의 PC에서 진행됐다** — 즉 iframe 문제도
실제 코드 결함이 아니라 **이 PC의 자원 고갈이 원인이었을
가능성**을 배제할 수 없다. curl(가볍고 짧게 실행되는 프로세스)은
항상 정상 응답을 받았는데 Chromium(무겁고 오래 떠 있는 프로세스)
만 계속 실패한 패턴이 이 가설과 일치한다.

**결론**: 오늘 헤드리스 자동화 테스트로 이 PC를 반복적으로
두들긴 것 자체가 결과를 왜곡시켰을 가능성이 크다고 판단해,
**이 시점부터 추가 자동 반복 테스트를 중단**했다. 프로세스는
전부 정리했고(Chromium/tracking_node/합성카메라/http.server),
메모리는 463MB -> 1.3GB로 회복 확인했다. TIME_WAIT은 자연
소멸을 기다리면 된다(강제 조치 안 함).

3. 요청2 — snapshot 폴링 구현 (완료, 버그 발견·수정 포함)
===============================================================
`<iframe>` -> **snapshot 폴링 + canvas**로 교체 완료. 제안하신
`/snapshot?topic=...&type=jpeg&t=...` 그대로 사용.

**[버그 발견·수정]** 최초 구현(`setInterval` 고정주기)은 이전
요청이 안 끝난 채 다음 요청이 겹쳐 나갈 수 있는 구조였다 --
겹친 상태에서 실패가 재현됐던 최초 관찰(2-1절) 자체는 이후
2-2절에서 "PC 소진이 진짜 원인일 수 있다"로 재해석됐지만,
**겹친 요청을 막는 자기재귀 `setTimeout` 방식 자체는 독립적으로
더 안전한 설계**라 그대로 유지했다(동시에 최대 1개 요청만
유지, 이전 요청 성공/실패와 무관하게 완료 후 다음 요청 예약).

bbox 오버레이 파이프라인 통합(3-3(c))은 아직 안 함 -- canvas
구조는 이미 준비됐으니(v66 4-3절) 다음 단계에서 같은 canvas에
그리면 된다.

4. 요청4 — 프레임 큐 확인 (완료, 실제 위험 확인돼 수정함)
===============================================================
```
[실측] 기존 코드: create_subscription(Image, "/image_raw",
       self._on_image, 10)
       -> depth=10, RELIABLE, KEEP_LAST(rclpy 기본값)
```
**지적하신 (b) 시나리오가 실제로 가능한 설정이었다** -- depth=10
큐가 차면 도착 순서대로 처리되므로, CPU 추론이 입력 속도를
못 따라가는 상황(실측: 30Hz 입력 vs 추론 약 1fps)에서 점점
과거 프레임을 처리하게 될 위험이 있었다.

**[완료] 수정**: `qos_profile_sensor_data`(BEST_EFFORT + KEEP_LAST
depth=5, ROS2에서 카메라류 토픽에 쓰는 표준 프로파일)로 교체 --
큐가 차면 오래된 프레임이 자동으로 버려지고 항상 최신에 가까운
프레임만 유지된다. dry-run으로 재기동해 정상 동작 확인.

v45의 "인식 지연"과 정확히 같은 유형인지는 [전제, 미검증] --
그때 원인을 이 QoS 문제로 명확히 지목한 기록은 없어서, 이번
수정이 그 문제까지 해결한다고 단정하지 않는다. 다만 **구조적
위험 자체는 실재했고 제거했다.**

6. 요청5 — 반대 의견 답변
===============================================================

**"body 381px는 DevTools 때문이라는 정정이 맞는가"**
동의한다. 실제로 CDP로 확인한 `body_rect`/`mainScreen_rect` 모두
1280×657(내가 설정한 헤드리스 창 크기 1280×800에서 브라우저
UI/DevTools 상당분을 뺀 값과 일치하는 패턴)로 일관되게 나와,
"뷰포트가 줄어든 것"이라는 재해석이 내 실측과도 부합한다.

**"2-3절 (c) 전환 로직 가설이 타당한가"**
**전제가 틀렸다고 본다** — "메인이 부분적으로만 그려진다"는
관찰 자체가, 1절에서 확인했듯 애초에 메인 화면에 그 이상의
요소(조작 버튼 등)가 코드에 없어서 발생한 착시다. 실제 DOM에는
메인 화면 구성 요소(canvas/상태판/비상정지/캡션/알림패널)가
전부 정상 존재하고 정상 위치에 렌더링되고 있었다(1절 CDP 결과).
전환 로직(`showMain`/`showDetail`) 자체는 이번 조사에서 별도
문제를 발견하지 못했다.

**"snapshot 폴링에 놓친 단점이 있는가"**
2절에서 다룬 게 사실상 답이다 -- 폴링 자체보다, **자동화 테스트로
반복 요청을 쏟아부으면 로컬 자원(TCP 연결 등)을 소진시킬 수
있다는 게 이번에 새로 배운 위험**이다. 실사용(사람이 한 번 켜서
계속 보는 상황)에서는 문제 안 될 걸로 보이지만[추론], 자동화
테스트/모니터링 스크립트를 이 페이지에 대고 돌릴 계획이 있다면
사람 사용 패턴과 다르다는 걸 염두에 둬야 한다.

**"프레임 큐가 실제로 문제가 되는 구조인가"**
그렇다, 4절 참고 -- 실측으로 확인된 구조적 위험이었고 수정
완료했다.
