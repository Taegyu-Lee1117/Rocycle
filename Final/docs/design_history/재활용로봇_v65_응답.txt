1. 요청1 — 1단계(영상 스트리밍) 결과 보고
===============================================================
[실측] rosbridge_server, web_video_server 둘 다 이 개발 PC에
이미 apt로 설치돼 있었다(`ros-jazzy-rosbridge-suite`,
`ros-jazzy-web-video-server`) — 별도 설치 불필요, v64 "7-1절"
사전 확인 게이트 즉시 통과.

[실측] 실행 확인:
  - `ros2 launch rosbridge_server rosbridge_websocket_launch.xml`
    → 로그에 "Rosbridge WebSocket server started on port 9090" 확인.
  - `ros2 run web_video_server web_video_server`
    → 6개 스트리머/스냅샷 플러그인 전부 로드, 8080 포트 대기 확인.

[실측] 실제 카메라(C270)가 오늘 연결 안 돼 있어, 파이프라인
자체(ROS2 이미지 토픽 → web_video_server → HTTP 응답)만 검증
하기 위해 합성 이미지 퍼블리셔(`fake_camera.py`, 640x480 BGR8,
움직이는 도형+타임스탬프 텍스트, 30Hz)를 만들어 `/image_raw`에
발행했다.
  - `ros2 topic hz /image_raw` → 29.841Hz (정상).
  - 단일 스냅샷: `curl .../snapshot?topic=/image_raw&type=jpeg`
    → 유효한 JPEG(640x480, 21310 bytes), 실제로 열어서 합성
    이미지가 정확히 보이는 것까지 육안 확인.
  - 연속 스트림: `curl .../stream?topic=/image_raw&type=mjpeg`를
    3초간 받음 → **89프레임 수신(≈29.6fps)**, 발행 속도(30Hz)와
    거의 일치 — 지연이 누적되며 프레임이 밀리는 현상 없음.

**결론: 파이프라인 자체는 정상 동작한다.** 단, 아래는 오늘
검증 범위 밖(GPU 없는 개발 PC + 합성 카메라의 구조적 한계)이며
과대 청구 금지 원칙에 따라 명확히 미검증으로 남긴다:
  - [전제, 미검증] YOLO 추론과 동시 구동 시 CPU 경합으로 인한
    지연 증가 (지금 CPU ~1fps인 것과 web_video_server가 같은
    코어를 나눠 쓰면 스트리밍 fps가 떨어질 가능성이 있음[추론]).
  - [전제, 미검증] 실제 C270(MJPEG 720p) 연결 시 지연/대역폭.
  - [전제, 미검증] 실제 브라우저(roslibjs)에서의 수신 — 오늘은
    curl로만 확인, 브라우저 렌더링/JS 콘솔 확인은 못 함.
  → 이 세 가지는 통제 PC에서 실카메라+YOLO 가동 상태로 재확인
    필요(다음 세션 우선순위).

2. 요청2 — /ui/state, /ui/alert 스키마 확정
===============================================================
[완료] `tracking_node.py`에 실제 구현 완료(코드 작업이라 카메라/
로봇 없이도 가능했음). 아래는 원안(v64) 대비 실제 코드와 대조해
수정한 부분 — **원안 그대로가 아니라 이 버전으로 확정 요청**.

2-1. `stage` 값 — **7개 → 8개로 수정(handoff 추가)**
  원안: idle/detect/track/predict/pick/measure/place
  실제: 위 7개 + **handoff**(사람전달, `pet_labeled` 경로) —
  코드에 `_handoff_item()`이 `_place_item()`과 별개 함수로 이미
  존재하고(순응제어 핸드오버), place와 동작이 달라 구분 필요.
  실제 코드의 전이:
    idle(voice_state≠RUNNING) → detect(트랙 없음, 이번 프레임
    신규 검출) → track(pending_count 누적 중) → predict(Pick
    대상 확정, 예측 계산 시작) → pick(_execute_pick 실행 중) →
    measure(무게 측정 중) → place 또는 handoff(품목별 라우팅에
    따라 둘 중 하나) → 완료 후 idle/track으로 복귀.

2-2. **[중요, 반드시 확인할 것] `stage`가 블로킹 구간 동안
  UI에 실시간으로 보이지 않는다 — 아키텍처 한계.**
  `_execute_pick`/`_place_item`/`_handoff_item`은 전부 `_on_image`
  콜백 안에서 **동기(블로킹) 호출**되고, `tracking_node`는
  단일 스레드 executor(`rclpy.spin`)를 쓴다. 즉 이 콜백이 실행
  중인 동안(파지~배치 완료까지, CLAUDE.md 실측 기준 17~24초)
  **`/ui/state`를 0.5초마다 발행하는 타이머 콜백 자체가 실행될
  기회가 없다.** 실제로 벌어지는 일: "predict"까지는 실시간으로
  보이다가, "pick"으로 바뀌는 순간부터 화면이 멈추고, 17~24초
  후 배치가 끝나야 "idle"(또는 다음 물체의 "track")로 한 번에
  점프한다. `ts` 필드가 그 사이 갱신되지 않는 것으로 이 상황을
  클라이언트가 스스로 판단할 수 있게 해뒀다(오래된 ts=블로킹
  중이라는 뜻으로 UI에서 "처리 중..." 같은 표시로 대체 권장).
  **근본 해결은 파지 실행 로직을 별도 스레드/executor로 분리하는
  아키텍처 변경인데, 이는 오늘 범위 밖이고 데모 임박 시점에
  건드리기엔 리스크가 크다고 판단해 보류한다** — 요청3 답변에서
  더 자세히 다룸(비상정지 질문과 원인이 완전히 같음).

2-3. `passed` 필드 정의 — **[전제, 확인 필요] 임의로 정함**
  원안에 정의가 없어서, "review_bin으로 강제 라우팅되지 않고
  정상 처리된 개수"(= total − review_bin 개수)로 정의했다.
  다른 의미(예: "육안 confirm까지 간 개수" 등)를 의도했다면
  알려달라 — 코드 한 줄만 바꾸면 됨.

2-4. `health` 체크 방식 — 원안 대비 2곳 수정
  - `robot`: dry_run 중엔 판단 불가라 **true/false 대신 null**
    (JSON null)로 발행한다 — 로봇 없이 true/false로 단정하면
    과대 청구 원칙 위반이라 판단. dry_run=False일 때는 로봇
    서비스들이 `__init__`에서 이미 `wait_for_service`로 확인된
    뒤에만 노드가 뜨므로 true 고정 — "최근 성공한 호출" 방식
    (원안 제안)보다 단순하지만, 서비스가 죽어도 노드 재시작
    전까진 계속 true로 보일 수 있다는 약점은 있음[전제].
  - `conveyor`: "최근 성공한 호출" 대신 **`service_is_ready()`**
    (연결 여부만 확인)로 대체 — 상태 확인 목적으로 실제 컨베이어
    서비스를 호출하면 부작용(원치 않는 속도 변경 등)이 생길 수
    있어 부적절하다고 판단.
  - `stt`/`tts`는 원안 그대로(`count_publishers`/`count_subscribers`).

2-5. `last.reason` 값 — 지금 코드에서 나올 수 있는 값은
  `"over_weight"` 하나뿐(무게 초과 review_bin 라우팅). 도달
  불가/이동 실패 등 다른 실패는 `last`가 아니라 `/ui/alert`로만
  나간다(아래 3절) — "last"는 "마지막으로 완료된 처리 결과"만
  의미하도록 설계했다(실패한 시도까지 last에 넣으면 의미가
  섞인다고 판단[전제, 다른 설계도 가능]).

[실측] 코드 완성 후 dry-run으로 6초간 실행해 크래시 없음 확인,
`ros2 topic echo /ui/state --once`로 실제 JSON 수신 확인:
  `{"ts": ..., "state": "IDLE", "stage": "idle", "counts": {},
    "passed": 0, "total": 0, "last": null, "health": {...}}`
— 필드 이름·타입 전부 위 스키마와 일치. 카메라/로봇 없이도
노드 기동 자체(캘리브레이션 없음 상태, calibration ready=False)
는 문제없이 동작.

  - warn: "예측 좌표 도달 범위 초과 — 건너뜀 (predicted_x=...)"

  - error: "{통이름} 상공 이동 실패 — 배치 중단, 사람 확인 필요"
  - error: "{품목} 라우팅 설정 없음 — 들고 대기"
  - warn: "{품목} 무게 초과 — {통이름}으로 라우팅"

할 수 있었지만 시간상 2단계 코드 완성을 우선함) — 다음 세션.

===============================================================
4. 요청3 — 4가지 질문 답변
===============================================================

4-1. (질문 내용 요약 불명확 — 순서 관련이라면) 0-1-2절 순서
그대로 진행했고 문제없었다. 인프라(1단계) 검증 후 코드(2단계)로
넘어가는 순서가 합리적이었다 — 1단계에서 실제 하드웨어 문제가
나왔다면 2단계 스키마 설계가 무의미해질 수 있었는데, 다행히
1단계가 깨끗해서 순서 변경 필요 없었다.

4-2. JSON-vs-토픽분리: 지금처럼 상태 전체를 JSON 문자열 하나로
묶어 `/ui/state`에 발행하는 방식을 유지 추천. 이유: 이미 코드에
캡슐화된 값들(voice_state, pick_counts, stage 등)이 서로 다른
시점에 갱신되는데, 필드별로 토픽을 쪼개면 클라이언트가 여러
토픽을 조합해 "현재 스냅샷"을 재구성해야 해서 오히려 복잡해짐
(현재 값이 하나의 딕셔너리로 이미 존재하므로 직렬화만 하면 됨).

4-3. 오버레이 서버측 합성 vs 클라이언트측: **클라이언트측(웹
프론트)에서 캔버스에 겹쳐 그리는 방식 추천.** 서버측(파이썬)
에서 OpenCV로 bbox를 프레임에 그려 넣으면 그 프레임을 다시
web_video_server가 인코딩해야 하는데, 이미 CPU가 YOLO 추론으로
빠듯한 상황(CPU ~1fps)에서 매 프레임 추가 연산을 얹는 건 부담
[추론]. 클라이언트측은 `/ui/state`의 `last`/추적 좌표를 따로
발행하면(현재는 없음 — 필요하면 별도 필드 추가 가능) 그걸로
브라우저 canvas에 그리면 되고, 서버 부하가 늘지 않는다.

4-4. **[가장 중요한 질문] 블로킹 파지 사이클 도중 비상정지가
기술적으로 가능한가?**

**결론: 지금 아키텍처(단일 스레드 executor)로는 소프트웨어
차원의 비상정지가 원리적으로 불가능하다.** 이유는 2-2절에서
설명한 것과 완전히 같다 — `/ui/estop` 같은 토픽을 구독해도,
그 구독 콜백 자체가 `_execute_pick`이 끝나야만(블로킹이 풀려야만)
실행될 기회를 얻는다. 즉 "비상정지 명령을 보냈는데 로봇이
하강/파지/이동 중이면 그 명령은 로봇 큐에 들어가지도 못하고
대기하다가, 동작이 다 끝난 뒤에야 뒤늦게 처리된다" — 이름만
"비상"이지 실제로는 전혀 즉시성이 없다. **CLAUDE.md에 이미
있는 원칙과도 일치한다**: "음성은 인식 지연이 있어 비상정지에
부적합, 물리 비상정지 버튼이 즉시 정지를 담당" — 지금 보니
이 원칙이 음성뿐 아니라 **웹 UI 버튼에도 그대로 적용된다**는
뜻이 된다. 즉 웹 UI의 "정지" 버튼도 음성 STOP과 똑같은 한계
(현재 사이클 완료까지 지연)를 가질 수밖에 없다.

**진짜 즉시 정지가 필요하다면 두 가지 층이 분리돼야 한다:**
  (a) **물리 비상정지**(하드웨어 스위치, 로봇 컨트롤러 자체의
      안전 회로) — 이건 소프트웨어 아키텍처와 무관하게 이미
      독립적으로 존재할 것(로봇 자체 안전 기능, [확인 필요] —
      두산 M0609 펜던트/컨트롤러의 물리 비상정지 버튼 유무·
      동작은 이미 있을 가능성이 높으나 이 세션에서 직접 확인한
      적은 없음). **웹 UI는 이 물리 비상정지를 대체할 수 없고,
      대체한다고 문서에 쓰면 안 된다**(과대 청구 금지 원칙 —
      "웹 UI에도 정지 버튼이 있다"와 "웹 UI로 즉시 멈출 수
      있다"는 다른 주장).
  (b) **소프트웨어 차원의 실제 인터럽트**를 원한다면, 파지
      실행 로직(`_execute_pick`/`_place_item`/`_handoff_item`)을
      메인 콜백(`_on_image`)에서 분리해 **별도 스레드에서
      실행**하고(이미 `conveyor_node`/robot client에 쓴 "별도
      Node+SingleThreadedExecutor" 패턴과 유사하지만, 이번엔
      "별도 노드"가 아니라 "같은 노드의 로직을 별도 파이썬
      스레드에서 실행"이 필요 — 조금 더 큰 리팩터링), 그 스레드가
      각 `_call_move_line` 호출 사이사이 체크포인트마다 "정지
      플래그"를 확인해서 다음 스텝을 시작하기 전에 멈추는 방식
      (예: 하강은 이미 시작했으면 끝까지 가되, 하강 후 닫기
      전에 플래그를 보고 중단). **이것도 "모션 도중 즉시 정지"는
      아니고 "스텝과 스텝 사이에서 정지"** — MoveLine 자체가
      이미 시작된 뒤 중간에 멈추려면 로봇 드라이버 쪽에 별도의
      "모션 중단" 서비스가 있어야 하는데, `dsr_msgs2`에 그런
      서비스가 있는지는 **[확인 필요, 이 세션에서 조사 안 함]**.

**팀 결정 요청**: (b)는 데모 임박 시점에 시도하기엔 리스크가
있는 리팩터링이라 판단한다. 대안으로 **웹 UI의 "정지" 버튼은
음성 STOP과 동일한 의미("현재 사이클 마무리 후 정지")로 명확히
라벨링하고, 진짜 즉시 정지는 "물리 비상정지 버튼을 누르세요"
라는 안내를 UI 자체에 표시하는 쪽으로 범위를 좁히는 것을
제안한다** — 구현 난이도 대비 실제로 판정/동작을 바꾸는 정도
(원칙7)를 고려했을 때, 지금은 이 쪽이 합리적이라고 본다. 이견
있으면 알려달라.
