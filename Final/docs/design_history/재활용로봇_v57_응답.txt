## 3. START 게이팅 — tracking_node.py에 상태머신 추가
====================================================================

**어디에 둘지 결정**: `voice_bridge_node`가 아니라 `tracking_node`가
`/voice_command`를 직접 구독하도록 했습니다 — 컨베이어 제어와 파지
로직이 이미 거기 있어서, 실제 상태 전이(컨베이어 on/off, Pick
게이팅, 카운터 집계)를 다른 노드에 맡기면 서비스 호출 등 조정
비용이 더 듭니다. `voice_bridge_node`는 정적 TTS 응답(예:
speed_inquiry)만 계속 담당 — 같은 토픽을 두 노드가 각자 구독하는
건 ROS2 토픽 특성상 문제없습니다(다중 구독자 허용).

```
상태: IDLE(대기, 검출은 하되 Pick 안 함) / RUNNING(가동) /
      PAUSED(일시정지) / STOPPING(종료 시퀀스 중)

START  : IDLE -> RUNNING, 컨베이어 ON, TTS "분리수거를 시작합니다"
PAUSE  : RUNNING -> PAUSED, 컨베이어 OFF, TTS "현재 작업을
         마무리한 뒤 정지합니다"
RESUME : PAUSED -> RUNNING, 컨베이어 ON, TTS "작업을 재개합니다"
STOP   : STOPPING -> (종료보고) -> 컨베이어 OFF -> IDLE
STATUS : 누적 카운터 기반 동적 응답
```

**4-2절(파지 사이클 중 PAUSE) 확인 결과**: 맞습니다 — `_execute_pick`
/`_place_item`이 블로킹이라 이 콜백은 사이클 도중엔 아예 안 불립니다.
그래서 PAUSE/STOP은 구조적으로 "현재 사이클 완료 후"에만 반영되고,
물체를 든 채로 멈추는 경우는 있을 수 없습니다(별도 안전장치 없이
아키텍처 자체가 보장). 다만 핸드오버(`_handoff_item`)도 마찬가지로
블로킹(최대 15초 타임아웃까지)이라 그 도중의 PAUSE/STOP도 같은
방식으로 자연히 지연 반영됩니다 — v56에 명시는 안 됐지만 같은
원리로 커버되는 걸 확인했습니다.

**요청3(TTS 없을 때 폴백)**: `_say()` 헬퍼로 처리 — `/voice/tts/say`
발행과 동시에 항상 `get_logger().info()`로도 남깁니다. TTS가 아직
안 붙어도 로그만으로 STATUS·종료보고 확인 가능합니다.

**테스트 편의 이슈 발견 및 처리**: 기본 상태를 IDLE로 하면, 이번
세션 내내 써온 "voice 노드 없이 TrackingNode만 띄워 바로 파지"
방식의 단독 테스트 스크립트가 전부 깨집니다(아무도 START를 안
보내니 영원히 Pick 안 나감). `voice.initial_state` 파라미터를
추가해 테스트 시 `RUNNING`으로 오버라이드할 수 있게 했습니다
(기본값은 실제 배포 의도대로 `IDLE` 유지).

## 4. 무하드웨어 로직 테스트 — 전부 통과
====================================================================

```
IDLE -> START -> RUNNING -> PAUSE -> PAUSED -> RESUME -> RUNNING
STATUS(카운트 0) -> "아직 처리한 물체가 없습니다"
카운터에 can=2, battery=1 주입 -> STATUS -> "총 3개... can 2개,
  battery 1개"
STOP -> 종료보고(총 3개...) -> IDLE
GIBBERISH -> "unknown command" 로그만, 크래시 없음
```

컨베이어가 실제로 연결 해제된 상태에서 `_call_conveyor()`가 매번
에러를 로그로 남기고 계속 진행하는 것도 확인(크래시 없음, 기존
에러 처리 그대로 유효).
