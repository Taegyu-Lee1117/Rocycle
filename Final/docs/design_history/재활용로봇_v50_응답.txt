## 2. 라벨 페트병 실제 순응제어 핸드오버 — 실물 성공
====================================================================

`task_compliance_ctrl`(저강성 500,500,500,100,100,100)로 순응 모드
진입 -> `get_current_posx` 0.3초 폴링으로 변위(release_threshold_mm
=10mm, v25 예비 시행값 재사용)를 감지하면 그리퍼 오픈 ->
`release_compliance_ctrl`로 복귀. 좌표는 새로 만들지 않고
`_execute_pick`이 이미 도달 검증한 벨트 상공 컬럼에서 z만
120mm(extra_rise_mm) 더 올려 제시 높이로 씁니다(새 자세 탐색 위험
회피).

**과정에서 버그 2개 발견·수정(둘 다 로봇 안전에는 영향 없었음,
그리퍼 안 건드리고 안전하게 중단됐던 경로들이었습니다):**

- **버그 1**: `_execute_pick`이 도달 불가로 중단될 때 `_locked_class`
  를 안 풀어줘서, 물체가 화면에 계속 보이는 한(연속 미검출 조건을
  못 채움) 재시도 자체가 영구히 막히는 구조적 버그. 사용자가
  "로봇 안움직여"로 발견 -> abort 경로에 `_locked_class = None`
  추가로 수정.
- **버그 2**: 위 수정 후 재시도는 되지만, 이미 알려진 도달한계
  (590mm, 4일차 실측)를 코드가 몰라서 예측 x가 이를 넘겨도 매
  프레임 MoveLine을 반복 시도 -> NOT REACHABLE 알람을 20회 넘게
  반복(벨트가 안 멈추니 물체가 계속 더 밀려나가 상황 악화). ->
  `motion_timing.yaml`에 `max_reachable_x: 590.0` 추가, 예측이 이
  값을 넘으면 MoveLine 자체를 시도하지 않고 조용히 중단하도록 수정.

**3차 시도 실물 성공**: 파지(x=245.3mm) -> 상승 -> 벨트 정지 ->
제시 높이 120mm 추가 상승 -> 순응 모드 -> 2.9초 후 변위 11.0mm
감지 -> 그리퍼 오픈 -> 순응 해제 -> 원위치 복귀 -> 벨트 재가동,
전 과정 성공(사용자 확인). [전제] 오늘 1회 성공 -- 10회 연속
SAFE_OFF 0회 검증 기준은 아직 미충족.

## 3. 속도 상향 테스트 — 물리적으로 안전, 절감폭은 작음
====================================================================

연속파지의 가장 큰 장애물(confirmed~완료 17.6초)을 줄여보려고
이동속도를 올려봤습니다. 수평 vel=120->150/acc=40->50, 수직
vel=100->130/acc=40->50.

[실측] 물체 없이 먼저 재측정: SAFE_OFF/특이점 알람 없음
(`robot_state` 계속 정상), travel_time_sec 3.410->2.999s(-12%),
descent_time_sec 2.194->1.882s(-14%). 이후 페트병 핸드오버 2회를
새 속도값으로 재검증 -- 둘 다 정확한 위치에서 성공(예측 정확도
유지 확인).

**[정정] 절감폭이 기대보다 작습니다.** travel+descent+rise 합쳐서
약 1초 절감에 그쳤습니다 -- confirmed~완료 구간의 지배적 비중은
확정 지연(6~9초, CPU 추론 속도 ~1fps에 묶임)이라, 속도만 올려서는
목표(10초대)에 크게 못 미칩니다. GPU 분리는 여전히 보류 중이라
이 병목은 구조적으로 남아있습니다.

## 4. 순차 처리(캔+건전지) 재검증 — 캔 성공, 건전지는 다른 원인
====================================================================

HOME에서 출발해 캔+건전지 순차 처리를 새 속도로 재검증했습니다.

- **캔**: 확정(x=263.3mm) -> 파지(x=316.4mm) -> can_bin 배치까지
  완전 성공(무게 net=-20.4g, 정상 범위, can_bin 배치).
- **건전지 1차 시도**: 확정(x=511.6mm) -> 파지 시도(x=546.1mm,
  도달 가능 구간) -> 그런데 **실제로는 못 잡음**(하부만 건드림,
  사용자 확인) -> 빈 그리퍼로 battery_bin 배치 시퀀스만 수행.
  **이건 도달범위 문제가 아니라 순수 예측 오차입니다** -- 벨트
  진동으로 인한 건전지 특유의 속도 추정 노이즈(이전 세션에서도
  확인된 패턴)로 보이고, 기존 `prediction_bias_mm=5.0`(구 속도
  기준 튜닝값)이 새 속도 조건에선 부족했던 것으로 판단됩니다.
- **건전지 2차(같은 개체, 못 잡아서 계속 벨트에 남음)**: 위 3절의
  `max_reachable_x` 가드가 정확히 작동 -- x=625->818mm까지 계속
  밀려나가는 동안 MoveLine 시도나 알람 없이 매 프레임 깔끔하게
  스킵만 반복(로봇 안전 유지, 알람 스팸 없음). 최종적으로 벨트
  끝까지 흘러가 사용자가 직접 통에 넣었습니다.

## 5. 다음 단계 (진행 중, 참고용 공유)
====================================================================

사용자 판단으로 "시간이 걸려도 제대로 된 해결책"을 선택해 아래
두 가지를 지금 진행합니다 -- 의견 있으시면 다음 라운드에 반영
하겠습니다.

(1) 건전지 `prediction_bias_mm` 5->30mm로 상향 후 재검증(빠른
    실측 조정, 근본 원인 fix는 아님 -- CLAUDE.md에 이미 "국소
    완화책"으로 명시된 방식 연장).

(2) **순차 처리(다중 물체) 인덱싱 구현 착수.** 현재 `RecycleDetector.
    detect()`가 `max_det=1`이라 프레임당 최고-신뢰도 물체 하나만
    반환하고, `_pending_class`/`_locked_class`/`self._kf`도 전부
    "물체 1개" 기준 단일 상태입니다. 여러 물체를 동시에 추적하려면
    (a) `max_det`를 늘려 여러 검출을 동시에 받고, (b) 물체별로
    독립된 트래커(칼만필터+상태)를 두고, (c) 우선순위를 신뢰도가
    아니라 **벨트 진행방향(x가 가장 큰, 즉 도달범위에 가장 먼저
    걸릴 물체)**으로 정하는 방향으로 설계 중입니다. 규모가 있는
    변경이라 시간을 들여 구현 후 실물로 검증하겠습니다.
