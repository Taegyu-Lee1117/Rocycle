1. 요청1 — 1-4절 확인 결과
===============================================================

### 1-1. [실측] 서비스 존재 확인

```
ros2 interface list | grep -i -E "stop|halt|pause"
```
결과에 `dsr_msgs2/srv/MoveStop`, `dsr_msgs2/srv/MovePause`,
`dsr_msgs2/srv/MoveResume`, `dsr_msgs2/srv/DrlStop`,
`dsr_msgs2/srv/DrlPause`, `dsr_msgs2/msg/RobotStop`,
`dsr_msgs2/srv/SetSafeStopResetType` 전부 존재 확인.

**`MoveStop`의 실제 정의(`ros2 interface show`):**
```
int32 stop_mode
  # DR_QSTOP_STO(0) : Quick stop (Category 1, STO 포함)
  # DR_QSTOP(1)     : Quick stop (Category 2)
  # DR_SSTO(2)      : Soft Stop
  # DR_HOLD(3)      : HOLD stop
---
bool success
```
**[원문] 추정이 정확했다** — Doosan ROS2 패키지에 `MoveStop` 계열이
있다는 v66의 추론이 실측으로 확인됐다. 특히 `stop_mode=0`(STO
포함)은 두산 안전등급 체계상 **Category 1 정지**(안전 토크
차단)에 해당하는 코드로 보인다[추론, 두산 문서 대조 안 함] --
이게 맞다면 소프트웨어 명령이지만 안전 회로 수준의 정지 카테고리를
호출하는 것이라 실효성이 높을 가능성이 있다.

### 1-2. [실측] `dsr_controller2` 소스코드 확인 — 핵심 발견

`~/ws_cobot_pjt/ws_dsr/src/doosan-robot2/dsr_controller2/src/
dsr_controller2.cpp`를 직접 읽었다.

```cpp
cb_group_ = get_node()->create_callback_group(
    rclcpp::CallbackGroupType::MutuallyExclusive);
...
m_nh_srv_move_line = get_node()->create_service<MoveLine>(
    svc_prefix_ + "motion/move_line", movel_cb);
    // <- 콜백그룹 인자 없음 (노드 기본 콜백그룹)
...
m_nh_srv_move_stop = get_node()->create_service<MoveStop>(
    svc_prefix_ + "motion/move_stop", move_stop_cb,
    qos_profile, cb_group_);
    // <- 전용 MutuallyExclusive 콜백그룹(cb_group_)에 등록
m_nh_srv_move_resume = get_node()->create_service<MoveResume>(
    svc_prefix_ + "motion/move_resume", move_resume_cb);
    // (등록 코드 확인, cb_group_ 소속 여부는 같은 라인에 있어 동일
    //  그룹으로 보임)
```

**[실측] `move_line`은 노드 기본 콜백그룹, `move_stop`/`move_resume`
은 별도의 전용 콜백그룹(`cb_group_`)에 등록돼 있다 — 서로 다른
그룹이다.** 이건 두산 엔지니어가 **의도적으로 분리한 것으로
보인다**[추론] — 그렇지 않다면 정지 서비스를 굳이 별도 그룹에
둘 이유가 없다.

**단, 이것만으로 "인터럽트된다"고 결론 내릴 수 없다.** ROS2에서
서로 다른 콜백그룹이 실제로 동시에 실행되려면, 그 노드를 돌리는
**executor가 MultiThreadedExecutor여야 한다**(SingleThreaded면
콜백그룹이 여러 개여도 결국 한 번에 하나씩만 처리됨). `dsr_controller2`
는 `ros2_control_node`(controller_manager) 프로세스에 하드웨어
인터페이스 플러그인으로 로드되는데, **`controller_manager`가
실제로 어떤 executor로 도는지는 이 저장소(doosan-robot2) 소스에
없고 `ros2_control` 패키지(외부 의존성) 쪽 코드라 이번 조사
범위에서 확인 못 했다.** [확인 필요, 다음 순서 참고]

### 1-3. 결론 (반례 수용 + 남은 불확실성 명시)

**v65의 "원리적으로 불가능하다"는 표현은 과했다 -- 정정한다.**
v66 지적대로 `tracking_node`(우리 코드, 실제로 블로킹되는 곳)와
`dsr_controller2`(로봇 드라이버, MoveStop을 실제로 처리하는 곳)는
**별도 프로세스**이고, `move_stop`이 `move_line`과 별도 콜백그룹에
있다는 것도 실측(소스코드)으로 확인됐다 — 이 두 가지는 "UI가
`tracking_node`를 거치지 않고 `dsr_controller2`/`conveyor_node`를
직접 호출하면 우리 코드의 블로킹과 무관하게 전달될 수 있다"는
v66의 핵심 주장을 뒷받침한다.

**다만 "전달된다"(메시지가 도착한다)와 "그 순간 실제로 로봇
모션이 멈춘다"(콜백그룹이 진짜로 병렬 실행된다) 사이에는 여전히
하나의 확인되지 않은 연결고리가 있다** — controller_manager의
executor 종류. 이건 소스코드 열람이 아니라 **실측(실제 MoveLine
도중 MoveStop 호출)으로만 확인 가능**하고, 오늘은 로봇이 없어
보류한다(요청 사항 참고).

**컨베이어는 v66 1-3절 그대로 확실하다** — `conveyor_node`는
완전히 별도 프로세스이고 콜백그룹 문제 자체가 없다(단일 노드,
서비스 2개뿐). "벨트는 즉시 멈춘다"는 실측 없이도 아키텍처만
으로 확정 가능.

3. 2절 — `passed` 필드: 요청대로 제거
===============================================================
**[완료]** `passed_undetected`(미검출 통과 개수)로 바꾸는 대신,
**필드 자체를 뺐다** — v66 2-3절의 폴백 지침을 그대로 따름.

이유: 지금 파이프라인은 YOLO 클래스 검출 기반이라, "무언가

애초에 코드에 아무 이벤트도 안 생기므로 셀 수 있는 지점 자체가
존재하지 않는다. 클래스 무관 일반 물체 감지(모션/블롭 검출 등)를
새로 붙이면 가능하지만, 데모 임박 시점에 새 비전 파이프라인을
추가하는 건 범위 밖이라고 판단했다(원칙5). `/ui/state`에서
`passed`/`passed_undetected` 필드 자체가 빠졌다 — 상태판 UI에서도
이 항목을 제외할 것.

4. 3절 — `/ui/detections` 구현 완료
===============================================================
**[완료]** `tracking_node.py`에 `/ui/detections`(std_msgs/String,
JSON, 매 프레임) 발행 추가. dry-run 실행으로 검증:
```
{"ts": 1788832270.89, "w": 640, "h": 480, "items": []}
```
(합성 카메라라 학습된 클래스가 안 잡혀 items가 비어있는 게 정상 —
구조·타입은 확인됨.)

**원안 대비 한 가지 단순화 — 확인 요청:**
`locked` 필드를 원안("이번 프레임에 Pick 대상으로 선택된 그
트랙")이 아니라 **"pending_count가 확정 기준(min_consecutive_
frames)을 이미 넘긴 트랙 전체"**로 정의했다. 이유: 원안 정의는
`best`가 선택되는 딱 한 프레임에서만 참이었다가 바로
`_execute_pick`이 블로킹을 시작해버려(2-2절과 동일한 한계) 실제
UI에는 사실상 안 보인다. 지금 정의는 "확정까지 남은 프레임"
(`pending`/`required`)이 실시간으로 살아있는 동안, confirmed된
트랙엔 항상 `locked:true`가 붙어 여러 프레임에 걸쳐 관찰 가능
하다 — v66 3-1절의 원래 목적(확정 여부 표시)에 더 부합한다고
판단했다. 다른 의도였다면 알려달라.

`w`/`h`는 실제 프레임 크기(`frame.shape`)를 그대로 씀. 벨트
영역 밖(`on_belt=False`) 검출이나 평면 교차 실패
(`RayPlaneParallelError`) 검출도 `pending=0, locked=false`로
목록에 포함시켰다 — 브라우저 오버레이에서 "왜 이 물체는 안
잡히는지"를 보여주는 데 필요하다고 판단했다(v66에 명시는 없었지만
자연스러운 확장이라고 봄) — 불필요하면 제거 요청 바람.

```
[비상정지] 버튼 동작:
  1. /conveyor/stop 직접 호출 (확실히 즉시 정지)

  3. 화면 문구: "벨트는 즉시 멈춥니다. 로봇 정지는 시도만
     전달되며 즉시 멈춤이 확인되지 않았습니다 -- 위급 시 물리
     비상정지 버튼을 누르세요"
```
로봇 실동작 검증(요청 참고) 후 결과에 따라 문구를 확정/수정한다.

7. 요청4 — 반대 의견 답변
===============================================================

**"rosbridge가 tracking_node와 같은 프로세스는 아닌가"**
아니다 — 실측 확인. `ros2 node list`에 `/rosbridge_websocket`이
`/tracking_node`(오늘은 안 띄웠지만 구조상)와 별도 프로세스로
뜬다(이번 세션에서 각각 다른 PID로 직접 확인). v66 1-2절 판단이
맞다.

**"1-6절 노드 재시작이 적절한가"**
동의(위 2절 참고). 더 나은 자동 복구 방법(예: `_tracks`/`_holding`
만 선택적으로 리셋하는 서비스)도 생각해볼 수는 있으나, 정확히
어디까지 리셋해야 안전한지(로봇이 실제로 무엇을 들고 있는
상태인지 소프트웨어가 확신할 수 없음) 검증하는 데 드는 노력 대비
"사람이 재시작"이 압도적으로 단순하고 안전하다 — 원칙5·6과
일치. 자동 복구는 데모 이후 과제로 남기는 것을 제안.

**"detections 스키마에 빠진 것이 있는가"**
`w`/`h`/`cls`/`conf`/`bbox`/`anchor`/`pending`/`required`/`locked`
전부 구현했고, 추가로 벨트 밖/평면교차 실패 검출까지 포함시켰다
(4절 참고, 확인 요청). 그 외 빠진 것은 없다고 판단.
