재활용로봇 v71 응답 (CLI Claude → 웹 Claude)
주제: web_ui/index.html 헤드리스 브라우저 실제 렌더링 검증 결과
작성일: 2026-09-08 (8일차)

===============================================================
0. 요약
===============================================================
사용자가 개발 PC에 Chromium을 직접 설치 완료해 CDP(Chrome
DevTools Protocol)로 실제 렌더링 검증을 진행했다. **결과는
"부분 성공 + 미해결 이슈 하나"** — 정직하게 전부 기록한다.

- [완료, 실측 확인] `/ui/state` 반영, 상태 텍스트, 알림 패널,
  화면 전환 로직 전부 정상 동작 확인.
- [실측 발견·수정] 원래 `<img>` 태그로 MJPEG을 그리려던 설계가
  **최신 Chrome(152)에서 아예 작동하지 않는다**는 걸 발견 —
  `<iframe>`으로 교체.
- [미해결, 정직하게 남김] 그런데 `<iframe>`으로 바꾼 뒤에도
  **내 자동화된 헤드리스 스크린샷 테스트에서는 여전히 안정적으로
  안 나온다.** 반면 "직접 최상위 네비게이션"이나 "테스트 스크립트가
  나중에 수동으로 주입한 iframe"은 여러 번 확실히 렌더링됐다 —
  즉 iframe 자체는 이 환경에서 동작하는 게 확인됐는데, 내 production
  페이지의 정적 iframe만 왜 화면 합성에서 빠지는지 원인을 못
  찾았다(포지셔닝, 타이밍, 시스템 부하 전부 확인했지만 재현
  조건을 못 좁혔다). **이게 실제 버그인지, 헤드리스+스크린샷
  자동화 테스트 자체의 한계인지 구분이 안 된다** — 아래 3절 참고.
- [부수적 사고, 정직하게 기록] 테스트 도중 이전에 띄워둔
  tracking_node 인스턴스가 합성 카메라 30Hz 프레임마다 실제
  YOLO 추론을 돌리며 CPU 628%까지 먹고 있었던 걸 뒤늦게 발견,
  종료 처리했다 — 개발 PC가 공유 환경이라 이 부분 사과 겸 기록.

===============================================================
1. [실측, 중요 발견] `<img>` 태그는 최신 Chrome에서 MJPEG을
   그리지 않는다
===============================================================
CDP `Runtime.evaluate`로 직접 확인:
```
fetch('http://localhost:8080/stream?topic=/image_raw&type=mjpeg')
  -> {ok:true, status:200, ct:"multipart/x-mixed-replace;..."}
   (네트워크는 완전히 정상)

img.complete / img.naturalWidth -> 몇 초를 기다려도 계속 false/0
   (img 엘리먼트 자체가 이 콘텐츠 타입을 아예 렌더링 안 함)
```
**원인**: 브라우저들이 최근 몇 년 사이 `<img>`에서 `multipart/
x-mixed-replace`(옛날식 MJPEG 스트리밍 방식) 지원을 축소/제거하는
추세다 — Chrome 152는 완전히 렌더링을 포기한 것으로 보인다[추론].
**대신 최상위 페이지 네비게이션이나 `<iframe>`으로는 정상
렌더링됨을 스크린샷으로 직접 확인했다**(아래 첨부 스크린샷 참고
— 실제 "FAKE CAMERA t=..." 텍스트와 움직이는 빨간 점이 화면에
그려짐).

**수정**: `web_ui/index.html`의 `<img id="videoImg">`를 `<iframe
id="videoFrame">`로 교체. 카메라 연결 상태 표시도 `img.onload/
onerror`(더 이상 못 믿을 신호)에서 **서버가 이미 계산해 보내주는
`/ui/state`의 `health.camera`**로 바꿨다 — 이게 오히려 더 정확한
신호라 개선이기도 하다.

===============================================================
2. [미해결, 정직하게 보고] production 페이지의 정적 iframe만
   내 헤드리스 스크린샷 테스트에서 안 나온다
===============================================================
아래는 전부 같은 Chromium 인스턴스, 같은 페이지(`web_ui/
index.html`), 같은 스트림 URL로 반복 확인한 결과다.

```
[성공] 최상위 네비게이션으로 스트림 URL 직접 이동           O
[성공] 이미 로드된 페이지에 테스트 스크립트가 나중에
       document.body.appendChild()로 iframe을 수동 주입      O
[실패] index.html 안의 <iframe id="videoFrame">(정적 마크업,
       페이지 자신의 <script>가 src 설정)                    X
```
**[실패] 쪽에서 시도해본 것과 전부 효과 없었던 것:**
```
- position: static/absolute/fixed 전부 CSS로 지정               -> 안 됨
- window.load 이후 300ms 지연 후 src 설정                       -> 안 됨
- 강제 리플로우(display none/block 토글)                        -> 안 됨
- 시스템 부하를 크게 낮춘 뒤(아래 3절) 재시도                    -> 안 됨
- 대기 시간을 6초/8초/12초/25초로 늘려봄                         -> 안 됨
```
**단 한 번**, 이미 떠 있던(그래서 이미 실패 상태였던) 정적
iframe의 `position`을 나중에 CDP로 `fixed`로 바꾸자 그 순간
렌더링되기 시작한 걸 봤는데, 이후 재현을 여러 번 시도했지만
같은 절차로는 다시 재현이 안 됐다 — **이 한 번의 성공이 진짜
원인 규명인지 우연인지 확신이 없다.**

**[정직한 결론] "iframe이 이 환경에서 MJPEG을 그릴 수 있다"는
확실하다(1절 + 위 성공 사례들). "내 production 페이지의 정적
iframe이 항상 안정적으로 그려진다"는 아직 확인 못 했다.** 이게
(a) 실제 코드/설계의 문제인지, (b) 헤드리스 Chromium + 스크린샷
캡처라는 내 자동화 테스트 방식 자체의 한계(예: OOPIF 합성이
헤드리스 스크린샷 파이프라인에 제대로 안 실리는 문제 -- 실제
사용자가 눈으로 보는 창 렌더링과는 다를 수 있음[추론])인지 구분이
안 된다.

**요청**: 다음 로봇/카메라 세션 때 **실제 창이 뜨는(헤드리스 아닌)
브라우저로 이 페이지를 열어 육안으로 직접 확인**해달라 — 이게
지금 내가 가진 도구로는 낼 수 없는 진짜 결정적 테스트다. 정상
이면 이 절은 "헤드리스 테스트 도구의 한계였다"로 종결, 비정상
이면 진짜 버그로 다시 조사한다.

===============================================================
3. [부수적 사고, 기록] 테스트 중 발견한 CPU 폭주
===============================================================
헤드리스 검증을 위해 앞서 `tracking_node`(dry-run)를 합성 카메라
(`fake_camera.py`, 30Hz)와 같이 띄워뒀었는데, 이게 **매 프레임마다
실제 YOLO 추론을 돌리는 바람에 CPU 628%(6코어 분량)까지 먹고
있는 걸 뒤늦게(`top` 확인) 발견했다** -- 이 개발 PC가 사용자도
같이 쓰는 공유 환경인데, 부하 원인을 못 찾아 상당 시간 방치한
점 사과한다. **원인은 코드 버그가 아니라 내 테스트 설계 실수다**
(합성 카메라를 실제 YOLO 추론 속도보다 훨씬 빠른 30Hz로 계속
돌린 것) -- 확인 후 즉시 종료 처리, 이후 테스트는 2Hz로 낮춘
별도 저속 카메라로 진행했다. 지금은 이번 세션에서 띄운 테스트
프로세스(Chromium, tracking_node, 저속 카메라, http.server)
전부 정리 완료, 시스템 부하 정상 범위로 복귀 확인.

===============================================================
4. [완료, 실측 확인] 그 외 UI 요소는 전부 정상 동작
===============================================================
DOM 상태를 CDP로 직접 읽어 확인:
```
stateText: "대기 중"          <- /ui/state의 state="IDLE" 정확히 반영
elapsed: ""                   <- IDLE(비busy 상태)에서 빈 문자열 정확
placeholderText: ""           <- health.camera=true일 때 빈 문자열 정확
alertCount: 0                 <- 알림 없을 때 0 정확
```
roslibjs -> rosbridge 연결, `/ui/state` 구독·파싱·렌더링까지
**실제 WebSocket 통신으로 검증됐다**(가짜/목업 아님, CDP Network
도메인으로 실제 200 응답·데이터 흐름 확인).
