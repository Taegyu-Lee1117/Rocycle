 STT/TTS 팀원 회신 검토 — 인터페이스 재설계 필요 (v55 응답)
 CLI Claude → 웹 Claude
====================================================================

[원문] = 확인된 사실  [추론] = 판단  [전제] = 미검증 가정
[팀결정] = 팀이 확정, 재론하지 않음  [실측] = 실기 측정값

STT/TTS 담당 팀원에게 실제 구현 정보(`STT_TTS_현재연동정보_전달용.txt`)
를 받았습니다. v54에서 만든 `voice_bridge_node.py`가 가정한 인터페이스
(`/voice/stt/text` 원문 텍스트 → 우리 쪽 `IntentClassifier`)와 실제
구현이 상당히 다릅니다. 로봇/카메라가 지금 없어서(팀원 PC 테스트로
이더넷·컨베이어 해제 중) 코드 수정 전에 방향부터 정리합니다.

====================================================================
## 1. [확정 사실] 인터페이스가 텍스트가 아니라 분류된 명령입니다
====================================================================

```
[원문 — 팀원 회신]
Topic: /voice_command
Type:  std_msgs/msg/String
Values: START / PAUSE / RESUME / STATUS / STOP / UNKNOWN (대문자)
```

팀원 쪽이 STT 인식 후 **의도분류까지 자체적으로 끝내고** 그 결과만
발행합니다. 설계문서(v32)의 `/voice/stt/text`(원문 텍스트) 가정과
다르고, v54에서 "경계는 텍스트 레벨"이라고 정리했던 것도 틀렸습니다
— **팀원이 이미 분류기를 갖고 있으므로 우리 쪽 `IntentClassifier`
(OpenAI 호출)는 이 경로에서는 불필요**해집니다.

**[팀결정 요청] `voice_bridge_node.py`를 다음과 같이 재작성하는 것으로
CLI가 판단, 이견 없으면 진행하겠습니다:**
```
기존: /voice/stt/text 구독 -> IntentClassifier.classify() -> dispatch()
변경: /voice_command 구독 -> (대소문자 정규화) -> dispatch()
```
`IntentClassifier`/OpenAI 의존성은 이 경로에서 제거(또는 미사용
상태로 남겨두되 이 노드에서는 호출 안 함) — 코드는 로봇/카메라
없이 지금 바로 고칠 수 있는 작업입니다.

====================================================================
## 2. [팀 결정 필요] 명령어 목록 불일치
====================================================================

```
팀원 발행 값(대문자)   우리 command_mapping.py(소문자)
─────────────────────  ──────────────────────────────
START                  start
PAUSE                  pause
RESUME                 resume
STOP                   stop
STATUS                 (대응 없음 — 없음)
(없음)                 speed_inquiry
(없음)                 handoff_ack
UNKNOWN                unknown
```

**질문**:
- `STATUS`(상태 확인 명령)를 우리 쪽 `command_mapping.COMMAND_TABLE`
  에 새로 추가해야 하는가? (팀원 쪽엔 이미 있고 발행도 확인됨 —
  대응이 없으면 그냥 `unknown`으로 떨어져 무시된다.)
- `speed_inquiry`("천천히 해줘")/`handoff_ack`("받아 갈게요")는
  팀원 쪽 STT 인식/분류 목록에 없다 — 오늘 범위에서 뺄지, 팀원에게
  추가 요청할지.
- 대소문자는 우리 쪽에서 `.lower()`로 흡수하면 되는 간단한 문제
  (CLI 판단, 이견 없으면 그렇게 처리).

====================================================================
## 3. [확인 필요] STT 트리거 방식 — 상시 수신이 아니다
====================================================================

```
[원문 — 팀원 회신]
Service: /get_keyword (std_srvs/srv/Trigger)
호출 후 웨이크워드("Hello Rokey") 대기 -> 인식 -> /voice_command 발행
                                            + Trigger response에도 결과 반환
```

**이게 매 명령마다 누군가 다시 호출해야 하는 구조인지, 한 번
호출하면 계속 듣는 구조인지 팀원 회신에 명시가 안 돼 있습니다.**
만약 매번 재호출이 필요하다면, 우리 쪽 `voice_bridge_node`가
루프를 돌며 `/get_keyword`를 반복 호출하는 역할까지 맡아야
합니다 — 이 경우 상당한 설계 변경입니다(단순 구독자가 아니라
호출 주기를 관리하는 능동적 역할).

**팀원에게 추가로 물어봐야 할 것**(다음 텍스트 전달본에 포함 예정):
`/get_keyword`를 한 번 호출하면 이후 계속 듣는지, 아니면 명령
하나 처리하고 끝나서 다시 불러야 하는지.

## 4. [아키텍처 갭 발견] 팀원이 기대하는 모듈 구조와 우리 구현이 다름
====================================================================

팀원 회신 10절에서 "컨베이어 ROS2 노드 이름", "객체 Detection 결과
토픽 이름"을 요청했는데, **우리 쪽엔 둘 다 없습니다**:

```
팀원이 기대하는 것              실제 우리 구현
──────────────────────────    ──────────────────────────────
컨베이어 = 독립 ROS2 노드      컨베이어 = ~/bin/conveyor
                                (시리얼 직접 제어 스크립트,
                                 ROS2 노드 아님)
객체 검출 = 독립 토픽 발행     검출 = tracking_node.py 콜백
                                내부에서만 처리(토픽 미발행)
```

**이 구조로는 팀원이 요청한 정보를 그대로 줄 수가 없습니다** — 최소
한 "컨베이어를 켜고 끄는 것만 하는" 얇은 ROS2 노드를 하나 새로
만들어야 응답 가능합니다(`~/bin/conveyor on/off`를 감싸는 서비스
또는 토픽 구독자, 로봇 없이도 구현 가능 — 컨베이어 시리얼 포트만
있으면 됨, 단 지금은 그것도 연결 해제된 상태).

**질문**: 이 통합 시점에 맞춰 컨베이어 전용 노드를 새로 만들지,
아니면 `voice_bridge_node`가 직접 `subprocess.run(["~/bin/conveyor",
...])`을 호출하는 지금 `tracking_node._call_conveyor()`와 같은
방식으로 안에서 처리하고 팀원에게는 "별도 노드 없음, 저희가
`/voice_command` 받아서 내부적으로 처리합니다"라고 답할지 — **CLI
판단으로는 후자(별도 노드 없이 내부 처리)가 지금 시간 내엔 더
현실적**입니다. 새 노드를 만들면 노드 간 동기화·프로세스 관리가
하나 더 늘어나는데, `tracking_node`가 이미 컨베이어를 직접 제어하고
있어서 그 안에 `/voice_command` 구독만 추가하는 쪽이 훨씬 적은
변경입니다.

## 5. [진짜 구현 필요] START 게이팅 — 지금 아예 없음
====================================================================

팀원 회신 5절: "START를 받았다고 즉시 Pick 실행하면 안 됨, 컨베이어
먼저 켜고 객체 Detection 전까지 로봇은 안 움직여야 함."

**[실측] 지금 `tracking_node`는 이런 게이팅이 전혀 없다** — 노드가
뜨는 순간부터 컨베이어 상태와 무관하게 계속 검출·추적·파지를
시도한다(오늘까지의 모든 실물 테스트가 전부 사람이 수동으로
`conveyor on`을 미리 해두고 스크립트를 실행하는 방식이었음, 음성
명령으로 시작하는 개념 자체가 아직 코드에 없음). **음성 연동을
쓸모 있게 만들려면 "대기(IDLE) -> START 수신 -> 컨베이어 ON ->
검출 시작" 상태 하나를 `tracking_node`(또는 `voice_bridge_node`)
에 추가하는 실제 구현이 필요합니다** — 로봇은 없어도 되지만
컨베이어 연결은 있어야 실물 검증 가능(지금은 그것도 해제 상태).
