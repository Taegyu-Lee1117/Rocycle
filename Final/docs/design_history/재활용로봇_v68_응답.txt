3. [중요, 서버 코드 수정] `counts`가 품목명이 아니라 통 이름
   기준이어야 한다는 것을 구현 중 발견 — 이미 수정함
===============================================================
막대그래프를 실제로 구현하려고 `/ui/state`의 `counts`가 어떤
키를 쓰는지 다시 보니, 기존 코드(`self._pick_counts`)는 **품목명**
(`can`/`paper`/`battery`/`pet_labeled`/`pet_unlabeled`/`plastic_bag`)
키였다 -- 그런데 `config/item_routing.yaml`을 보면:

```
can           -> can_bin
paper         -> paper_bin
battery       -> battery_bin
pet_unlabeled -> plastic_bin
pet_labeled   -> human_handoff   (통이 아님!)
plastic_bag   -> review_bin
```

**품목명 키로는 막대그래프가 안 맞는다** — 예를 들어
`pet_unlabeled`와 `pet_labeled`가 서로 다른 목적지(하나는
plastic_bin, 하나는 사람전달)로 가는데 둘 다 "PET"류라 막대
하나로 보일 것 같지만 실제로는 그렇지 않다. **수정**: 목적지
문자열(실제 통 이름 또는 `"human_handoff"`)을 키로 쓰는 별도
딕셔너리(`self._bin_counts`)를 새로 두고, `/ui/state`의 `counts`
는 이걸 발행하도록 바꿨다. 기존 `self._pick_counts`(품목명 키)는
음성 상태보고("캔 3개, 종이 2개")용으로 그대로 남겨뒀다 — 두
용도가 다른 키 체계를 원해서 분리했다.

**[확인 요청, 막대그래프 설계에 영향] `human_handoff`가 5개
막대 중 어디에도 안 들어간다.** CLAUDE.md의 "시연 물체 제약"을
다시 보면 **"페트병은 항상 라벨 있는 것만"**(무라벨은 고신뢰도
오분류 확인돼 시연 제외) — 즉 실제 시연에서 나오는 PET 관련
품목은 거의 전부 `pet_labeled`이고, 이건 `plastic_bin`이 아니라
**사람전달(human_handoff)**로 간다. `plastic_bin`(무라벨 전용
경로)은 시연 중 거의 항상 0으로 남을 가능성이 높고, 반대로
사람전달 건수는 막대 어디에도 표시가 안 된다 — **"플라스틱"
막대가 시연 내내 비어있는데 정작 페트병은 계속 처리되는
이상한 화면이 될 수 있다.**

**제안 (결정 요청)**:
```
(a) 6번째 막대 "사람전달" 추가(초록, 정상 분류 취급)
(b) "플라스틱" 막대 라벨을 유지하되 plastic_bin+human_handoff
    합산으로 보여준다(막대는 5개 그대로, 라벨만 "페트/플라스틱"
    처럼 포괄적으로)
(c) 지금은 그냥 둔다 -- 사람전달은 화면에 안 보여도 무방
    (하단 "마지막 처리" 텍스트에는 어차피 dest="human_handoff"로
    표시되니 완전히 안 보이는 건 아님)
```
CLI 의견: **(a)를 권장한다** — 실제 시연에서 자주 나오는 처리
경로가 화면에서 통째로 빠지는 건 "재현성 우선"/"과대 청구 금지"
원칙에 어긋난다고 본다(화면이 실제로 일어나는 일을 안 보여줌).
다만 시간이 없으면 (c)로 임시 진행해도 치명적이진 않음 — 결정
바람.

코드 변경 위치: `tracking_node.py`의 `_place_item`/`_handoff_item`
성공 지점에 `self._bin_counts[...] += 1` 추가, `_publish_ui_state`
가 `self._pick_counts` 대신 `self._bin_counts`를 `counts`로 발행.
dry-run 재검증(크래시 없음)까지 완료.

4. 요청4 — 반대 의견 답변
===============================================================

**"2-4절 고정 max=3이 적절한가"**
동의한다. 5~6개 규모 시연에서 한 항목이 3을 넘는 경우는 드물고,
`web_ui/index.html`에서는 고정값 3을 "바닥값"으로 두고 실제
최댓값이 이를 넘으면 자동으로 그 값까지 확장하도록 구현했다
(`Math.max(BAR_MAX_FLOOR, ...allCounts)`) — 3보다 작게 내려가진
않지만 넘으면 커진다. 요청하신 그대로다.

**"진행 단계를 좌상단에서 뺀 것이 적절한가 -- 파지 실패를 즉시
알아야 하는데 상세에만 있어도 되는가"**
**대체로 동의하되, 한 가지 보완을 반영했다.** 파지 실패(도달
범위 초과, 이동 실패 등)는 `/ui/alert`로 별도 발행되므로(v65
3절 구현 완료) 진행 단계 표시와 중복이라는 판단이 맞다 -- **단,
`/ui/alert` 자체가 아직 화면에 안 떠 있다**(오늘 구현 범위 밖,
콘솔 로그만 확인 — `web_ui/index.html`에 `console.warn`으로만
찍음). 진행 단계를 상세로 뺀 건 문제없지만, **알림을 메인 화면
에도 짧게(토스트/배너) 띄우는 작업이 이걸 대신해야 완결된다** —
다음 구현 순서에 넣어달라(아래 5절 요청 참고).

**"3-1절 자동 복귀가 시연 중 방해가 되지 않는가"**
30초면 사람이 상세를 들여다보고 답하기엔 충분히 길고, 시연
흐름(한 사이클 20초 안팎)을 크게 넘지 않아 "깜빡하고 열어둔 채
카메라를 놓치는" 상황은 막아준다고 판단한다 — 다만 실제
브라우저에서 체감 타이밍은 검증 전이라(0절 참고) 30초가 너무
짧다/길다는 피드백은 실물 확인 후 조정 여지를 남겨둔다.
