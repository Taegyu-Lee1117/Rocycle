## 2. 발견된 버그 2건
====================================================================

### 2-1. `find_checkerboard_pose()` 호출부의 불필요한 역행렬

```python
R_cam2checker, t_cam2checker = find_checkerboard_pose(...)  # 실제로는
                                                              # solvePnP가
                                                              # checker2cam을
                                                              # 반환함(아래)
T_cam2checker = np.eye(4)
T_cam2checker[:3, :3] = R_cam2checker
T_cam2checker[:3, 3] = t_cam2checker.flatten()
T_checker2cam = np.linalg.inv(T_cam2checker)  # ← 버그: 이미 checker2cam인
                                                #   것을 다시 뒤집음
```

`cv2.solvePnP(objp, corners, ...)`가 반환하는 (R,t)는 정의상
`P_camera = R @ P_object + t` — 즉 **이미 그 자체로 "checker2cam"
변환**이다. 그런데 코드가 이 결과를 "T_cam2checker"라고 잘못
이름 붙이고, 다시 `inv()`해서 "T_checker2cam"이라 부른다 — 실제로는
반대 방향(T_cam2checker)이 되어버린다. 변수명이 실제 의미와
뒤바뀐 전형적인 버그.

### 2-2. 커스텀 `Calibrate()` AX=XB 솔버 자체가 부정확

`logR()` + 벡터 외적으로 회전을 먼저 풀고 이어서 이동을 최소자승
으로 푸는 커스텀 구현인데, **노이즈가 전혀 없는 가상의 정답
데이터를 넣어도 완전히 틀린 값을 반환한다**(회전오차 94°, 위치
오차 908mm — 검증 스크립트로 재현 확인). 어느 알려진 논문의
구현인지 특정하지 못했고, 구현 자체에 결함이 있는 것으로 판단해
**OpenCV 내장 `cv2.calibrateHandEye()`로 교체**했다.

## 3. 검증 방법
====================================================================

**정답을 아는 가상 데이터**(임의의 T_cam2base, T_checker2gripper를
정하고, 그로부터 로봇 자세·체커보드 관측치를 역산해서 생성)로
두 함수를 각각 테스트:

```
기존 Calibrate()        : 회전오차 94°, 위치오차 908mm  (완전 실패)
cv2.calibrateHandEye()
  (2-1 버그도 수정한 뒤) : 회전오차 0.000001°, 위치오차 0.0000000005mm
                          (사실상 완벽 복원)
```

## 4. 실제 데이터로 재계산한 결과
====================================================================

기존에 촬영해뒀던 3개 샘플셋(1차 9장, 2차 12장, 3차 10장)에
수정된 알고리즘만 적용해 재계산:

```
1차(9샘플, 회전다양성 4도)   : tilt 38.09°, translation 거의 동일
2차(12샘플, 회전다양성 42도) : tilt 38.35°, translation 거의 동일
3차(10샘플, Y범위 확장)      : tilt 47.82°  ← 이것만 다름
```

**1차와 2차가 수정된 알고리즘으로는 거의 같은 값(tilt 0.26도
차이)에 수렴한다** — 이게 결정적 증거다. 회전 다양성이 부족했던
1차 데이터로도, 다양했던 2차 데이터로도 "같은 정답"이 나온다는
건 **알고리즘이 문제였지 데이터(회전 다양성) 문제가 아니었다**는
뜻이다. (3차만 다른 이유는 [추론] 촬영 중 체커보드 크레이스
(접힌 자국)가 있는 샘플들이 섞여 solvePnP 정확도가 떨어졌을
가능성 — 원인 미확정.)

2차(12샘플) 결과를 최종 채택해 배포했고, 벨트 위 펜 마킹으로
재검증 중이다(결과는 다음 보고에서).

## 5. 반성 — CLI의 두 번의 오진단
====================================================================

1차 실패 직후 "회전 다양성 부족"으로 진단하고 2차를 재작업한 것,
2차 실패 후 "extrapolation으로 인한 증폭"으로 진단하고 3차를
재작업한 것 — **둘 다 그럴듯했지만 틀렸다.** 두 진단 모두 "더
많이/다양하게 찍으면 나아질 것"이라는 방향으로만 움직였는데,
근본 원인이 알고리즘 버그였으므로 데이터를 아무리 다양하게
모아도 고쳐지지 않았을 것이다.

**교훈**: 반복된 실패 패턴(세 번 다른 접근, 세 번 다 큰 오차)이
보이면, "데이터를 더 모은다"보다 "이미 있는 데이터로 알고리즘
자체를 가상 정답값으로 검증한다"를 더 일찍 시도했어야 한다.
